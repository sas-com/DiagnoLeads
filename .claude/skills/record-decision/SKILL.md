# record-decision：MemoryBank に記録する

どれも公開リポジトリに入る。

- 接続情報・キー・社外秘（取引先名・単価・営業の手引きの本文）は書かない
- 「最終更新」の行は書かない（並行するセッション同士の衝突の元になる）

## 決定（`.factory/memory/decisions/`）

1. 同じ話題の決定がないか探す：`bun run memory:index` または `grep -rl '<言葉>' .factory/memory/decisions/`
2. `<今日の日付>-<英語の短い名前>.md` を作る。先頭の項目と本文の形は `.factory/memory/decisions/README.md` に従う
   - `title` と `paths` の値は `"` で囲む
   - `paths` には、その決定が縛るコードだけを書く。広すぎるパスは付けない
   - 本文は `### [分類] 題名` の見出しと、日付・決定・理由・却下案・ルールの箇条書き。オーナーの判断なら、そう書く
3. 置き換えるとき
   - 古い決定は消さない。`status: superseded` にし、`superseded_by: [<新しい id>]` を書く
   - 一部だけ変えるときは、どこを変えたかを新しい決定に書く
4. 確かめる
   - `bun run memory:index` の索引に出る
   - `bunx vitest run test/unit/claude-hooks` が通る（先頭の項目の形と、`paths` に当たるファイルがあることを検査する）

## 違反（`.factory/memory/violations.md`）

1. 「違反記録」の末尾に書く：重大度（CRITICAL / HIGH / MEDIUM）・日付・違反した原則・状況・影響・原因・対応・再発防止
2. 「統計」の表を更新する
3. 再発防止策を仕組みに入れる
   - 機械で判定できるもの：フック。ルールは `.claude/hooks/lib/` に書き、テストを `test/unit/claude-hooks/` に足す
   - 判断が要るもの：CLAUDE.md の「毎回守ること」

## 学び（`.factory/memory/learnings.md`）

学びは差分で育て、月1回の見直しで整理する（決定 `2026-11-12-memory-ace-grow-and-refine`）。

1. 振り返る：PR のレビューの指摘・CI の失敗・手戻り・オーナーの訂正があったら、次の作業でも使える教訓を1つずつ取り出す。その PR だけの事情や、顧客固有の情報は教訓にしない。原則違反は上の「違反」に書き、学びには重ねない
2. 探す：`grep -n '<言葉>' .factory/memory/learnings.md` で同じ学びを探す
3. 同じ学びか判定する：読む人が取る行動が既存の項目と同じなら、同じ学び。対象・条件・例外が違えば別の学び
   - 固有の名前（ファイル名・画面名）を外しても書けるときは、1段だけ一般化してから比べる。一般化した文から元の行動を導けないなら、一般化しすぎ
4. 差分で足す
   - 別の学びなら、分野の節に日付・状況・原因・解決策・教訓の項目を1つ足す（「評価」の行は書かない。月1回の見直しで足す）
   - 同じ学びなら、新しく足さない。今回の例が既存の状況・解決策に無いときだけ1行追記する
   - ファイル全体や節をまとめて書き直さない。教訓は短く言い直さない（具体的な手順・数字・ファイル名を残す）。長くなった経緯は PR へのリンクに置き換えてよい
5. 使った学びを PR に書く：学びに従って作業したら、PR の本文の「役立った学び／外れた学び」の節（PR テンプレートにある）に、`- 役立った：[分類] 題名` か `- 外れた：[分類] 題名（理由）` を1行ずつ書く。見出しは `learnings.md` の「### 」より後ろをそのまま写す
   - `learnings.md` の「評価」の数は、作業の PR では変えない（並行する PR が同じ行を変えて衝突するため）。毎月1日に開く見直しの Issue で数える（`.factory/memory/README.md` の「メンテナンス」）
