# ワークフローエンジン選定の評価（DiagnoLeads 向け）

> 作成日: 2026年10月21日 / 参照日: 2026年10月21日
> 本スコアは AI による定性評価です。最終判断は PoC の結果と関係部門の確認を踏まえて行ってください。

## 要約

- MIRAI 向け（Java 前提）の評価を、本リポジトリ（TypeScript / Next.js / Vercel / Postgres）の前提で採点し直しました。「Java親和性」は「スタック親和性」に置き換えています。
- 結果は **Inngest が87点で首位**、Vercel Workflows が84点、Trigger.dev が81点です。Java 前提で首位だった Temporal は、Vercel 上で常駐ワーカーを持てない点で71点に下がります。
- Claude 親和性の重みを0にしても上位3候補の順位は変わりません。Inngest と Vercel Workflows の2案で PoC を行うことを提案します。
- 費用ゼロ（新しい契約・サーバーなし）を条件にする場合は、自作エンジンを既存の Postgres と定期実行で永続化する **A案** を推奨します（[7章](#7-費用ゼロで実現する場合a案自作エンジンの永続化)）。

## 0. 本書で扱う「ワークフロー」

「ワークフロー」は意味の広い言葉です。本書では次のように定義します。

> **本書のワークフロー**：リードの状態変化（作成・更新・ステータス変更など）を起点に、待機を挟んで複数の処理（メール送信、通知、リードの更新など）を順に実行し、途中で止まっても続きから再開できる自動処理。系統としては耐久実行型（付録A.1）。

**対象外**：申請・承認ワークフロー、BPM（業務プロセス管理）、データ処理のバッチ、開発の自動化（CI/CD）。承認と BPM との関係は付録A.5・A.6 にまとめています。

### 「ワークフロー」が指しうるもの

| 意味 | 指すもの | 代表例 | 本書 |
|---|---|---|---|
| 業務の流れ全般 | 仕事の手順そのもの（ビジネス用語） | 「受注のワークフローを見直す」 | 対象外 |
| 申請・承認 | 稟議、経費精算、休暇申請などの電子化 | 承認ワークフロー製品 | 対象外 |
| 業務プロセス管理（BPM） | 人とシステムを含む業務プロセスの設計・実行・改善 | Camunda、Flowable | 対象外 |
| **システム間の処理連携** | **長い処理を確実に最後までやり切る** | **Temporal、Inngest** | **対象** |
| データ処理の流れ | 集計・変換バッチの依存関係と定期実行 | Airflow | 対象外 |
| ノーコード自動化 | SaaS 同士を「トリガー → アクション」でつなぐ | Zapier、n8n | 対象外 |
| 開発の自動化（CI/CD※） | テスト・ビルド・デプロイの手順 | GitHub Actions | 対象外 |
| 開発の進め方 | チームの作業手順 | SprintPath の開発フロー | 対象外 |
| AI エージェントの流れ | AI の呼び出しとツール実行を順に組む | エージェントのワークフロー | 対象外 |

※CI/CD：コードの変更ごとにテストやデプロイを自動で行う仕組み。

本リポジトリの中だけでも、少なくとも次の4つの意味が混在しています。議論のときは、どれを指しているかをそろえてください。

| 場所 | 意味 |
|---|---|
| `.github/workflows/` | 開発の自動化（GitHub Actions） |
| `docs/WORKFLOW.md` | 開発の進め方 |
| `lib/workflow/`、`workflows` テーブル | リードの自動化（**本書の対象**） |
| Zapier 連携 | ノーコード自動化（外部側） |

## 1. 前提：今のワークフロー機能の状態

| 項目 | 現状 | 根拠 |
|---|---|---|
| 定義の保存 | できる（`workflows` テーブル、tRPC の CRUD） | `lib/features/workflows/api/router.ts` |
| 実行 | **アプリから呼ばれていない** | `lib/workflow/engine.ts` の `WorkflowEngine` を import している箇所がない |
| 実行の記録 | テーブルはあるが、書き込む処理がない | `lib/db/schema.ts` の `workflowExecutions` |
| 状態の保持 | メモリ上のみ（再起動・デプロイで消える） | `WorkflowEngine.executions`（`Map`） |
| 待機（delay） | 実際は最大100ミリ秒で打ち切り | `engine.ts` の `executeDelay` |
| ジョブキュー | メモリ上のみ（BullMQ 等への置き換えを想定したコメントあり） | `lib/jobs/queue.ts` |
| 定期実行 | Vercel Cron（2本）。関数の実行時間は30秒まで | `vercel.json` |

「リード作成の3日後にフォローメール」のような、時間をまたぐ処理を確実に動かす仕組みはまだありません。そのため候補には、何もしない案ではなく「自作エンジンを Postgres + Vercel Cron で永続化する案」を比較対象として入れています。

## 5. 採点理由

### スタック親和性・運用負荷

- **Inngest（5／4）**：関数を Next.js の Route Handler として公開し、Inngest 側が呼び出す方式のため、Vercel の関数のまま動かせます。ステップごとに関数を呼び直すので、30秒の制約を受けにくい構成です。
- **Vercel Workflows（5／5）**：`"use workflow"` / `"use step"` の指定で関数を耐久化（※途中の状態を保存し、失敗や再デプロイのあとも続きから再開できる）でき、すでに使っている Vercel の中で完結します。新たな契約先が増えません。
- **Trigger.dev（3／4）**：タスクは Trigger.dev 側の実行環境で動くため、Vercel とは別にデプロイが必要です。そのぶん長時間の処理には強いです。
- **Temporal（2／2）**：ワーカー（※ワークフローを実際に実行する常駐プロセス）を常時動かす必要があり、Vercel のサーバーレス関数では動かせません。Temporal Cloud を使っても、ワーカーの置き場所は別に用意する必要があります。
- **Upstash Workflow（4／4）**：Next.js から使え、Upstash はすでに Redis で利用しています（`@upstash/redis`）。
- **自作（4／2）**：構成上の追加はありませんが、永続化・再開・リトライ・待機をすべて自分で作り、保守し続ける必要があります。

### 状態管理・補償処理

- **Temporal（5）**：実行履歴をもとに状態を再現する方式で、補償処理（※途中で失敗したとき、済んだ処理を取り消す処理）の実装例も豊富です。
- **Inngest／Vercel Workflows／Trigger.dev（4）**：ステップ単位の保存・自動リトライ・長時間の待機・外部イベントの待ち受けがそろっています。補償処理はコードで書く必要があります。
- **Upstash Workflow（3）**：ステップ実行と待機はできますが、上記3候補に比べると運用画面や待ち受けの機能が少なめです。
- **自作（1）**：現状はメモリ上のみで、待機も100ミリ秒で打ち切られます。

### Claude親和性

- **Inngest（5）**：Claude Code 向けの公式プラグインと Agent Skills を提供しています。ローカルの Dev Server に MCP エンドポイントが組み込まれ、関数の一覧・テストイベントの送信・実行の確認ができます。クラウド側にも、デプロイ済みの関数・実行履歴・トレースを扱う MCP があります。
- **Trigger.dev（5）**：公式の MCP サーバー（プロジェクトの初期化・タスクの起動・デプロイ・デバッグ）と、Claude Code 向けのルールとサブエージェントを提供しています。
- **Temporal（5）**：MIRAI 版の評価と同じく、Claude Code 向けの公式プラグインとドキュメント用の MCP があります。TypeScript SDK でも同じく使えます。
- **Vercel Workflows（4）**：Vercel の公式 MCP は本セッションでも利用できており、デプロイやログは Claude から見られます。ただし、ワークフローの実行単位の参照・操作が MCP でできるかは、今回の調査では確認できませんでした。記述は通常の TypeScript 関数のため、生成・レビューはしやすいです。
- **Upstash Workflow（3）**：Upstash の公式 MCP はありますが、対象は主に Redis などのアカウント管理で、Workflow の実行を扱えるかは確認できませんでした。
- **自作（3）**：コードがリポジトリ内にあるので Claude が直接読み書きできますが、稼働中の実行を参照する手段は自分で作る必要があります。

### ライセンス・コスト、長期保守性

- 価格は従量制で、利用量と契約プランで大きく変わるため、本書では金額を比較していません。PoC で想定実行数をもとに試算します。
- **Temporal（長期保守性5）**：採用実績が多く、OSS（MIT ライセンス）として長く続いています。
- **Vercel Workflows（長期保守性3）**：一般提供（GA）になって日が浅く、API の変更が続く可能性があります。マネージド版は Vercel への依存が強くなります（WDK 自体はオープンソース）。

## 6. 提案

1. Inngest と Vercel Workflows の2案で PoC を行う。題材は既存のトリガー `lead_created` → 「3日待ってフォローメール、反応がなければ Slack で担当者に通知」とする（待機・外部イベント待ち・通知を一度に確かめられる）。
2. PoC では「Vercel の30秒制約の中で動くか」「実行の様子を運用画面と Claude（MCP）の両方から追えるか」「想定実行数での月額」の3点を比べる。
3. 採用が決まったら、ワークフロー定義（`workflows` テーブルの形）はそのまま使い、実行と永続化の部分だけを採用したエンジンに置き換える。決定は `.factory/memory/decisions.md` に記録する。

### 期待効果

- 時間をまたぐ自動化（フォローメール、再接触の通知など）を、デプロイや障害で途切れずに動かせるようになります。
- Inngest／Trigger.dev を採用した場合、関数の作成からテスト実行・実行結果の確認までを Claude Code の中で続けて行えます。

### 想定リスク

- **リードの個人情報の扱い**：Inngest／Trigger.dev／Upstash では、ステップの入出力（リードの氏名・メールアドレス等）が外部サービスに保存されます。保存先の地域・保存期間・契約上の扱いを、**情報システム部門に確認**する必要があります。ステップには ID だけを渡し、本体は自社の DB から読む設計にすると影響を小さくできます。Vercel Workflows は既存の契約先の中で完結しますが、同じ確認は必要です。
- **評価の陳腐化**：各製品の AI 対応は変化が速く、半年程度で評価が変わる可能性があります。
- **重みの前提**：Claude親和性の重み10は「AI 活用を進める方針」を前提にしています（重みを0にしても上位の順位は変わらないことは上記のとおりです）。

## 7. 費用ゼロで実現する場合：A案（自作エンジンの永続化）

### 7.1 結論

外部サービスや OSS のサーバーを使わず、**既存の Postgres（`workflow_executions` テーブル）と定期実行だけで、実行を保存しながら1ステップずつ進める**形にします。

4章の点数（54点）は「機能をすべて自分で作る」前提の評価です。対象を「リードの状態変化を起点に、待機を挟んで数個のアクションを順に実行する」に絞れば、作る範囲は限られます。

### 7.2 OSS で実現する案との比較

| 案 | ライセンス | 追加のサーバー | 費用 | 運用の手間 |
|---|---|---|---|---|
| **A. 自作エンジンの永続化** | 自社コード | 不要 | ほぼゼロ | 小（開発・保守は自分で） |
| B. Postgres 上のジョブキュー（pg-boss、graphile-worker） | MIT | 常駐ワーカーが必要 | 小さなサーバー代 | 中 |
| C. Inngest の自前運用 | SDK は Apache 2.0、サーバーは SSPL | Inngest サーバー＋DB | サーバー代 | 中〜大（管理画面に認証なし、公式サポートなし） |
| D. Trigger.dev の自前運用 | Apache 2.0 | Docker 一式 | サーバー代 | 大 |
| E. Temporal の自前運用 | MIT | サーバー＋DB＋ワーカー | サーバー代 | 大 |

B〜E は、どれも常時動き続けるプロセスが必要で、Vercel のサーバーレス関数（1回30秒まで）の上では動かせません。

### 7.3 前提となる現状（コードから確認した事実）

| 項目 | 現状 | 影響 |
|---|---|---|
| 定義の形が2つある | DB と tRPC は「トリガー＋条件（AND）＋アクションの並び」の平らな形（`lib/db/schema.ts`）。`lib/workflow/` はノードとエッジの図の形で、条件の演算子名も違う（`equals` と `eq` など） | どちらかに一本化が必要。**DB 側の平らな形を正とする**（CRUD が動いているのは DB 側、図の形はどこからも使われていない） |
| 編集画面 | ない（tRPC の `workflows` ルーターのみ） | MVP では設定は API か投入スクリプトで行う |
| トリガーの発火 | リード作成やステータス変更の処理から、ワークフローを呼ぶ処理がない。Webhook の `lead.created` 等も、テスト送信以外では呼ばれていない | 発火する箇所を各処理に足す必要がある |
| 実行履歴 | `workflow_executions` の `status` は `success / failed / skipped` のみ。書き込む処理はない | 待機中・取り消しを表せるように列を追加する。既存データがないので変更しやすい |
| 同じ方式の前例 | Webhook の再送（`processWebhookRetries`）が、`FOR UPDATE SKIP LOCKED` での取り出し、処理中の印（リース）、20秒の時間予算を、日次の定期実行の中で実装済み | **この実装をなぞる**ことで、新しい方式を持ち込まずに済む |
| 定期実行 | Vercel Cron が2本、いずれも1日1回（`vercel.json`）。認証は `isCronRequest`（`CRON_SECRET`） | 待機の細かさは実行頻度で決まる（7.5 の決めること①） |
| 送信の部品 | メール（`lib/features/email/email-service.ts`）、組織メンバーへの通知（`notifyOrganizationMembers`）、Webhook（`triggerWebhooks`）が既存 | アクションは既存の部品を呼ぶだけにする |

| F8 | 停止と取り消し | 各ステップの前にワークフローの状態（`paused / disabled`）とリードの存在を確かめ、該当すれば `cancelled` にする。アクションの前に条件を再評価する「停止条件」（例：ステータスが商談化に変わっていたら止める）を設定できるようにする | F4 | 3 |
| F9 | 定期実行の登録 | `vercel.json` にランナーを登録し、`isCronRequest` で守る。実行頻度は 7.5 の決めること①に従う | F4 | 1 |
| F10 | テスト | 条件判定、発火、取り出し（同時に2本動いても同じ行を取らない）、待機、リトライ、取り消しのユニットテストと、DB を使う統合テスト。目標カバレッジは Core 層の 80% | F1〜F9 | 5 |

フェーズ1の合計は目安で35ポイントです。Ship Small の原則に従い、F1+F2、F3、F4+F9、F5+F6、F7+F8 の単位で PR を分けることを想定しています。

#### フェーズ2：運用と画面

| ID | 機能 | 内容 | 目安 |
|---|---|---|---|
| F11 | 実行履歴の画面 | 既存の `listExecutions` / `getStats` を使い、実行の一覧・状態・失敗理由・次に動く時刻を見られる画面（shadcn/ui） | 5 |
| F12 | ワークフローの編集画面 | トリガー・条件・アクション（待機を含む）を設定する画面。UI 文字列は `locales/` に定義 | 8 |
| F13 | 滞留の検知と掃除 | リースが切れたまま止まっている実行の検知と通知。古い実行履歴を定期的に削除（Webhook 配信の掃除と同じ方式） | 3 |
| F14 | スケジュールトリガー | `cronExpression` による定期起動（`scheduled` トリガー） | 3 |
| F15 | 手動での再実行・取り消し | 失敗した実行の再試行と、待機中の実行の取り消しを画面と API から行う | 3 |

#### 対象外（必要になった時点で外部エンジンへの移行を再検討）

- 分岐の合流・並列実行・ループ（`lib/workflow/` の図の形が持っていた機能）
- 任意のスクリプト実行（`run_script`）と AI 処理（`ai_process`）のアクション
- 外部イベントを待つ処理（例：メールの返信待ち）。MVP では、F8 の停止条件で「状態が変わったら止める」までにする

### 7.5 着手前に決めること

1. **定期実行の頻度**：Vercel の Hobby プランは定期実行が1日1回までです。「3日後」程度なら1日1回でも足りますが、数分単位の精度が要るなら、Pro プランにするか、DB 側の定期実行機能で毎分ランナーを呼ぶ必要があります。どのプランで運用しているかの確認が必要です。
   - **案：Supabase の pg_cron + pg_net で毎分呼ぶ**（2026年10月21日に Supabase の管理画面の情報で確認）
     - `diagnoleads-v2` プロジェクトでは pg_cron（1.6.4）と pg_net（0.19.5）が使える状態で、まだ有効にしていません。Vault（秘密情報の保管）は有効済みです。
     - 仕組み：pg_cron に「毎分 `/api/cron/run-workflows` を呼ぶ」ジョブを登録し、pg_net で呼び出します。`CRON_SECRET` は Vault から読み、API 側は今と同じ `isCronRequest` で確認します（アプリの変更は不要）。
     - 費用：pg_cron・pg_net に追加料金はありません。Vercel 側の関数呼び出しが月に約4万3千回増えるため、Vercel の無料枠に収まるかを使用量の画面で確認します。
     - 効果：Vercel の Hobby プランのままでも、待機の遅れを最大で約1日から約1分に縮められます。
     - リスク：Supabase は**無料プラン**で、7日間ほとんど使われないとプロジェクトが自動で一時停止されます（停止中はアプリも DB に接続できない）。これはワークフローに限らず本番運用全体の課題で、本番では Pro プラン（月額 $25）への移行を検討します。また、pg_net の呼び出し結果は6時間しか残らないため、失敗の記録はアプリ側の `reportServerError` で取ります。
     - 拡張機能の有効化とジョブの登録はマイグレーションで行い、リポジトリに残します。
2. **図の形（`lib/workflow/`）の扱い**：削除するか、将来に向けて残すか。使われていないため、削除を推奨します。
3. **停止条件の初期値**：どのステータスに変わったら自動のフォローを止めるか（営業と確認が必要）。

### 7.6 期待効果・想定リスク

- **期待効果**
  - 新しい契約先・サーバー・月額費用なしで、時間をまたぐ自動化が動きます。
  - リードの個人情報が外部サービスに出ないため、情報システム部門への確認が軽く済みます。
  - Webhook 再送と同じ方式なので、読む人・直す人（Claude を含む）の負担が増えません。
- **想定リスク**
  - 待機の精度は定期実行の頻度に左右されます（1日1回なら最大で約1日遅れる）。
  - 処理件数が増えると、1回20秒の時間予算に収まらず滞留する可能性があります。F13 の滞留検知で早めに気づけるようにし、目安を超えたら外部エンジン（4章の上位案）への移行を検討します。
  - 運用画面（F11）ができるまでは、実行の状況は DB を直接見るしかありません。

## 付録A. ワークフローエンジンの機能と A案の範囲

### A.1 ワークフローエンジンとは

複数の手順からなる業務の流れを定義どおりに進め、**途中で止まっても続きから再開できるよう、状態を保存しながら実行する仕組み**です。大きく2系統あります。

| 系統 | 代表例 | 主な対象 | 流れの書き方 |
|---|---|---|---|
| 業務プロセス型（BPM※） | Camunda、Flowable、Operaton | 人の承認・作業を含む業務（申請→承認→差し戻し） | BPMN（※業務フローを描く国際標準の図）を XML で保存 |
| 耐久実行型（Durable Execution） | Temporal、Inngest、Vercel Workflows | システム間の長い処理（待機を挟む通知、外部連携） | プログラムのコード |

※BPM（Business Process Management）：業務の流れを定義・実行・監視・改善する考え方。

MIRAI 版の評価で Flowable／Operaton が候補に入っていたのは業務プロセス型の需要があったためです。本書（DiagnoLeads）で上位に来たのは耐久実行型です。

### A.2 担う機能

| 分類 | 機能 | 内容 | DiagnoLeads での例 |
|---|---|---|---|
| 流れの制御 | 順次・分岐・並列・合流・繰り返し | 定義した順に手順を進め、条件で分け、並べて動かし、揃うのを待つ | スコア80以上なら担当者に通知、未満ならナーチャリングメール |
| 状態の保持 | 永続化と再開 | どこまで進んだかを保存し、障害や再起動・デプロイのあとも続きから動く | デプロイを挟んでも「3日後のフォロー」が消えない |
| 時間 | 待機・期限・タイマー | 指定の時刻まで待つ。期限を過ぎたら別の処理に回す | 3日後にフォローメール |
| 外部との待ち合わせ | イベント待ち | 外部からの通知や返信が来るまで止まって待つ | 相談申込が来たらフォローを止める |
| 失敗への対応 | リトライ・タイムアウト | 一時的な失敗を自動で再試行し、上限を超えたら失敗として扱う | メール送信や Webhook の失敗を再送 |
| 失敗への対応 | 補償処理（Saga※） | 途中で失敗したとき、済んだ手順を逆順に取り消して整合をとる | 外部 CRM への登録に失敗したら、付けたタグを外す |
| 人の関与 | ユーザータスク | 担当者に作業や承認を割り当て、完了を待つ（主に BPM 型） | 高スコアのリードの割り当てを営業責任者が承認 |
| 二重実行の防止 | 冪等性の確保 | 同じ手順が2回動いても結果が変わらないようにする | 同じフォローメールを2回送らない |
| 版の管理 | 定義のバージョン管理 | 実行中の案件は旧版のまま、新しい案件から新版で動かす | 待機日数を変えても、待機中のリードには影響させない |
| 流量の制御 | 同時実行数・流量の制限 | テナントごとや外部 API ごとに、同時に動く数を抑える | 1組織の大量取り込みが他の組織の処理を詰まらせない |
| 運用 | 可視化・監視・手動操作 | 実行中の一覧、各案件の今の位置、失敗理由、再実行・取り消し | どのリードのフォローがどこで止まっているか画面で分かる |
| 監査 | 実行履歴の保存 | いつ・何を実行したかを残す | 自動で送ったメールの履歴 |

※Saga：長い処理を小さな手順に分け、失敗時には各手順の「取り消し処理」で戻す設計の型。

### A.3 A案（MVP）でカバーする範囲

| 機能 | A案 | 補足 |
|---|---|---|
| 順次実行 | ○ | アクションの並び |
| 分岐 | △ | 開始時の条件と停止条件のみ。途中で道を分けることはできない |
| 並列・合流・繰り返し | × | 対象外 |
| 永続化と再開 | ○ | F2・F4 |
| 待機 | ○ | 精度は定期実行の頻度しだい（pg_cron なら約1分） |
| イベント待ち | △ | 「状態が変わったら止める」まで（F8） |
| リトライ | ○ | F7 |
| 補償処理 | × | 対象外。リードの更新程度なら不要と判断 |
| ユーザータスク | × | 対象外 |
| 二重実行の防止 | ○ | F6 |
| 定義のバージョン管理 | × | 必要になれば、実行の開始時に定義を写して保存する方式で追加できる |
| 流量の制御 | △ | 1回の取り出し件数と時間予算で抑える程度 |
| 可視化・手動操作 | △ | フェーズ2（F11・F15） |
| 実行履歴 | ○ | `workflow_executions` |

### A.4 期待効果・想定リスク

- **期待効果**：当面の用途（リードの状態変化を起点にした自動フォロー）なら、○の機能だけで足ります。作る量を抑えたまま、確実に動く仕組みにできます。
- **想定リスク**：「承認を挟む」「途中で道を分けて合流する」「失敗時に取り消す」といった要件が出てきたら、A案の延長では作る量が急に増えます。そのときが、4章の上位案（Inngest など）への移行を考える目安です。

### A.5 BPM との関係

**BPM はワークフローエンジンの機能ではなく、向きは逆で、ワークフローエンジンが BPM の一部です。**

- **BPM** は、業務の流れを「設計 → 実行 → 監視 → 改善」と回し続ける**管理の考え方**で、ソフトの機能名ではありません。
- **ワークフローエンジン**は、そのうちの「実行」を担う部品です。
- BPM を支えるソフト一式を **BPMS**（BPM Suite）と呼び、エンジンはその中心部品です。

| BPMS の部品 | 役割 | ワークフローエンジンとの関係 |
|---|---|---|
| モデラー | BPMN で業務フローを図に描く | エンジンに渡す定義を作る道具 |
| **プロセスエンジン（＝ワークフローエンジン）** | 定義どおりに実行し、状態を保存する | **これがワークフローエンジン** |
| タスク管理（タスクリスト） | 担当者に承認・作業を割り当て、画面で処理させる | エンジンの「ユーザータスク」を人が操作する画面 |
| ルールエンジン（DMN※） | 「与信額がいくら以上なら部長承認」のような判断表を管理する | エンジンが分岐のときに呼び出す |
| 監視（BAM※） | 処理件数・滞留・所要時間をリアルタイムに見る | エンジンの実行履歴を集計して表示 |
| 分析・改善（プロセスマイニング等） | 実績からボトルネックを見つけ、フローを直す | エンジンの履歴を分析し、モデラーでの修正につなげる |

※DMN（Decision Model and Notation）：判断ルールを表で定義する国際標準。BPMN と組で使われます。
※BAM（Business Activity Monitoring）：業務の進み具合をリアルタイムに監視する仕組み。

| 製品 | 位置づけ |
|---|---|
| Camunda 8 | BPMS に近い（モデラー、エンジン、タスクリスト、監視画面、DMN が揃う） |
| Flowable／Operaton | BPMN・DMN を実行できるエンジンが中心。画面は一部あり、足りない部分は自作 |
| Temporal／Inngest | ワークフローエンジンのみ（耐久実行型）。BPMN、タスク画面、DMN はない |
| A案 | ワークフローエンジンの基本機能のみ |

DiagnoLeads は自動フォローが中心で人の承認フローがないため、エンジンだけで足ります。一方、MIRAI のように受注の承認や与信判断など人の判断を挟む業務プロセスでは、BPMN・DMN・タスク管理まで揃う製品のほうが向いています（MIRAI 版の評価で Flowable／Operaton／Camunda が候補に残った理由）。

### A.6 承認ワークフローとの関係

承認ワークフローは、ワークフローエンジンに完成品の機能として入っているわけではなく、**部品を組み合わせて作るもの**です。

| 種類 | 承認の扱い |
|---|---|
| 業務プロセス型（Camunda、Flowable、Operaton） | ユーザータスク・分岐・タイマーで承認の流れを組める。承認画面は製品によって一部ある |
| 耐久実行型（Temporal、Inngest） | 人の操作をイベントとして待つことはできる。承認ルートの管理や画面はすべて自作 |
| 承認ワークフロー製品（稟議・経費精算などの SaaS） | 承認に特化した機能が最初から揃っている |
| A案 | 対象外 |

| 承認に必要な機能 | BPM 型エンジンが用意するもの | 自分で作る部分 |
|---|---|---|
| 承認者への割り当て | ユーザータスク（担当者・グループの指定） | 組織・役職マスタとのつなぎ込み |
| 承認ルート（課長 → 部長 など） | 順に並べたタスクと分岐 | 金額や部署でルートを変える条件 |
| 承認・却下・差し戻し | 分岐（ゲートウェイ）で流れを戻す | 差し戻し先の選び方 |
| 合議（複数人の並行承認） | 並列実行と合流 | 「全員一致」か「過半数」かの判定 |
| 期限切れの督促・上位者への回送 | タイマー | 督促の文面と通知手段 |
| 代理承認・不在時の転送 | ほぼない | 代理人設定の管理 |
| 承認画面・受信箱 | 製品によって簡易なタスク一覧がある | 業務に合わせた画面 |
| 承認の証跡 | 実行履歴 | 監査で求められる形への出力 |

承認を本格的に扱うなら「BPM 型エンジン＋自作の画面と組織マスタ連携」か「承認ワークフロー製品」の二択になります。基幹システムの中で業務データと一体で承認を回すなら前者、社内の稟議や経費精算なら後者が一般的です。
