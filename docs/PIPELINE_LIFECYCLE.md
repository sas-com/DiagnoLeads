# リードのライフサイクルと段階の対応表

リードの「段階」を表す値は、いくつもの軸（列）に分かれている。この文書は、それらを1本のライフサイクルに当てはめ、各集計がどの軸を数えているかを示す（#444、Epic #430）。値の定義はコードの側が正本で、この文書と食い違ったらコードに合わせて直す。

## 1. ライフサイクル（1本）

```
リード ─→ MQL ─→ 商談（見極め） ─[SQL判定：適格]→ 商談（課題の確認 → 提案 → 条件の調整） ─→ 受注 / 失注
  │       │       ↑                    └[不適格]→ 失注（理由付き）
  │       │       └─ アポ・紹介など、MQL を経ずに入ってよい
  └───────┴─→ 再育成（ナーチャリング） ─→ 条件がそろえば MQL か商談（見極め）に戻る
```

SQL は段ではなく、見極めの出口の判定（関門）。SQL判定が「適格」のリードが、課題の確認から先に進む。

| 段 | 入る条件 | 出る条件 |
|---|---|---|
| リード | リードができたとき（診断の回答・CSV の取り込み・手入力・顧客探しからの引き継ぎ） | MQL になる、商談（見極め）に入る、再育成か失注にする |
| MQL | 診断の MQL段階が「関心あり」、または MQL判定日（`mql_qualified_at`）が入ったとき。「適合」は MQL の手前（MQL候補） | 初回商談の日時が確定する |
| 商談（見極め） | 初回商談の日時が確定したとき（商談を作る。決定：#444 のコメント 2026-10-24）。代行のアポ・紹介・既存顧客など診断のないリードは、MQL を経ずにここに入ってよい | 初回ヒアリングの後の SQL判定。適格なら課題の確認へ、不適格なら失注（理由付き）で閉じる |
| 商談（課題の確認〜条件の調整） | SQL判定が「適格」（`sql_decision = qualified`）。課題の確認へ進める前に SQL判定を記録する（今はシステムでは強制しない。漏れると獲得元・代行の SQL数が少なく出る） | 商談が受注か失注で閉じる |
| 受注 | 商談が受注になったとき。AX 移行は段階的に売る（現行調査 → 移行 → AX 化）ので、次の商談が続くことがある。一度受注したリードは、次の商談を進めている間も状態は成約のまま | ― |
| 失注 | すべての商談が失注になったとき、または失注の理由を付けて閉じたとき。「保留」は失注ではない（#445）。時期を理由に失注したリードは、動くべき時期で再接触を追う（#151） | 動くべき時期が来て、再び商談（見極め）になる |
| 再育成 | 商談の前のリードが、時期・予算・保留などで今は進まないとき。次の行動か動くべき時期が必要（#446） | 条件がそろえば MQL か商談（見極め）に戻る |

商談を持つリードを再育成に戻す規則（止まった商談を時期で失注にして、リードをナーチャリングにするか）は未決。#444 の2つ目の PR（商談から状態を毎回計算する）で決める。それまでは、止まった商談は開いたままにするか、時期を理由に失注にする（`lib/features/deals/types/pipeline.ts` の失注の理由に「保留」はない）。

## 2. 軸ごとの対応表

### 2.1 リードの状態（`leads.status`）

定義は `lib/features/leads/types/pipeline.ts` の `LEAD_STATUSES`。

| 値 | 表示 | 段 |
|---|---|---|
| `new` | 新規 | リード・MQL（商談の前） |
| `nurturing` | ナーチャリング | 再育成 |
| `negotiating` | 商談中 | 商談（見極め〜条件の調整） |
| `won` | 成約 | 受注。次の商談（移行・AX 化）を進めている間も `won` のまま。次の商談の進み具合は `deals.stage` と `deal_phase` で見る |
| `lost` | 失注 | 失注 |

`leads.has_negotiated`（商談済み）は、一度でも商談に入ったリードに付く印で、状態が戻っても消えない。

### 2.2 商談フェーズ（`leads.deal_phase`）

定義は同じファイルの `DEAL_PHASES`。初めて入った日を `leads.deal_phase_reached_at` に残す。

| 値 | 表示 | 段 |
|---|---|---|
| `initial_hearing` | 初回ヒアリング | 商談（見極め） |
| `simple_diagnosis` | 簡易診断 | 商談（課題の確認） |
| `proposal` | 提案 | 商談（提案・条件の調整） |
| `survey_won` | 現行調査受注 | 受注（1段目） |
| `migration_won` | 移行受注 | 受注（2段目） |
| `ax` | AX化 | 受注（3段目） |

### 2.3 MQL段階と MQL判定日

診断の回答からの段階は `lib/features/leads/mql-level.ts`（`leadMqlLevel`。回答だけを読む）。MQL判定日のあるリードを関心ありとみなすのは、一覧と分析の `listMqlLevel`（`lib/features/leads/api/list-sql.ts`）。見込みの指標はこれに一本化した（決定 `2026-10-24-mql-level-over-score`）。

| 値 | 表示 | 段 |
|---|---|---|
| `interest`、または MQL判定日あり（`listMqlLevel`） | 関心あり（MQL） | MQL |
| `fit` | 適合 | リード（MQL候補） |
| `none` | 対象外 | リード（育成か失注の候補） |
| なし（診断なし） | 診断なし | リード（手入力などは MQL のチェックで判断する） |

### 2.4 SQL判定（`leads.sql_decision`）

定義は `pipeline.ts` の `SQL_DECISIONS`。

| 値 | 表示 | 意味 |
|---|---|---|
| `qualified` | 適格 | 見極めを抜けた（SQL）。課題の確認〜条件の調整と重なる |
| `not_qualified` | 不適格 | 失注（理由付き）で閉じる |
| なし | 未判定 | 見極めの前・途中 |

### 2.5 商談のステージ（`deals.stage`、#435）

定義は `lib/features/deals/types/pipeline.ts`（#435 のマージ後）。確度はステージに入ったときの初期値で、担当が商談ごとに変えられる（初期値は営業に確認する）。

| 値 | 表示 | 確度 | 段 | リードの商談フェーズ |
|---|---|---|---|---|
| `qualification` | 見極め | 10% | 商談（見極め） | 初回ヒアリング |
| `discovery` | 課題の確認 | 20% | 商談（課題の確認） | 簡易診断 |
| `proposal` | 提案 | 40% | 商談（提案） | 提案 |
| `negotiation` | 条件の調整 | 70% | 商談（条件の調整） | 提案 |
| `won` | 受注 | 100% | 受注 | 商談の種類で決まる（現行調査 → 現行調査受注、移行 → 移行受注、AX 化 → AX化）。保守・運用とその他の受注は変えない |
| `lost` | 失注 | 0% | 失注 | 変えない |

商談からリードへの反映は `lib/features/deals/lead-sync.ts` にだけ書く。商談を持つリードの状態と商談フェーズは商談から決まり、手では変えない（#444 の2つ目の PR で入れる）。

### 2.6 顧客探しの段階（`prospects.stage`、#265）

定義は `lib/features/prospects/types/schemas.ts` の `PROSPECT_STAGES`。顧客探しは、SAS のメンバーが話した相手をリードにする前に書く一覧で、値は表計算の選択肢に合わせてある。リードに引き継いだ（`prospects.lead_id` が入った）後はリードと商談の側が正で、顧客探しの段階は更新しない（仮の運用）。

| 値・項目 | 表示 | 当たる段（目安） |
|---|---|---|
| `interest` | 1 関心確認 | リードの前（引き継ぐとリード） |
| 商談日（`meeting_on`）が入った | ― | 商談（見極め）を作る時点 |
| `quick_diagnosis` | 2 簡易診断 | 商談（課題の確認） |
| `spec_survey` | 3 現行仕様調査 | 受注（1段目：現行調査）。営業に確認する |
| `proposal` | 4 移行提案 | 商談（提案。移行の商談） |
| `contract` | 5 契約 | 受注（2段目：移行）。現行調査だけの契約もあり得るので、営業に確認する |
| `nurturing` | 育成 | 再育成 |
| `dropped` | 見送り | 失注 |

顧客探しの段階とリードの状態は自動では連動しない。

## 3. 集計がどの軸を数えているか

| 集計 | 場所 | 数えている軸 |
|---|---|---|
| ダッシュボードのパイプライン（状態ごとの件数） | `lib/features/analytics/dashboard.ts` | `leads.status` |
| ダッシュボードの MQL | 同上 | MQL判定日が期間内のリード（関心ありでも判定日がなければ数えない。判定日を自動で入れるのは AX 診断の送信だけ）。適合は MQL に足さず、期間内の AX 診断の適合（判定日なし）を注記で出す |
| 分析の上部の KPI・MQL段階の内訳 | `lib/features/analytics/api/router.ts`（`getOverview`） | 全期間。`leads.status`（成約率）、MQL段階と MQL判定日（`listMqlLevel`）。ダッシュボードの MQL（期間内の流れ）とは数が合わない |
| 分析のファネル | 同上（`getConversionFunnel`） | `leads.status` と `leads.has_negotiated`。新規 → ナーチャリング → 商談中 → 成約を順の段として数え、後の段に進んだリードは前の段にも数える。このナーチャリングは旧来の段の意味で、1章の再育成とは違う |
| 獲得元・代行会社別の費用 | `lib/features/analytics/lead-sources.ts` | `leads.sql_decision`（SQL）、`leads.status`（成約） |
| 代行の契約別ファネル | `lib/features/agency-contracts/report.ts` | アポ（リード）→ 商談の実施（`has_negotiated` か商談フェーズの日付）→ SQL（`sql_decision`）→ 現行調査受注 → 移行受注（`deal_phase_reached_at`） |
| 段階的な納品の集計 | `lib/features/delivery-reviews/report.ts` | `deal_phase_reached_at`（現行調査受注 → 移行受注 → AX化） |
| 売上予測（#437） | `lib/features/deals/`（#437 のマージ後） | `deals.stage` と確度・金額 |
| 顧客探しの集計 | `lib/features/prospects/summary.ts` | `prospects.stage`、商談日（`meeting_on`）、次の行動（`next_step`。見送りの数はこちらで数える） |

## 4. 未決の点

- 商談を持つリードを再育成に戻す規則（1章）。#444 の2つ目の PR で決める
- SQL判定の記録を、商談のステージを課題の確認へ進める条件にするか（今は強制しない）
- 分析のファネルのナーチャリングを、1章の再育成に合わせて数え直すか
- 営業部門に確認する：顧客探しの「3 現行仕様調査」「5 契約」が受注のどの段に当たるか、確度の初期値（10・20・40・70）
