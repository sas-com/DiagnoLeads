# リードのライフサイクルと段階の対応表

リードの「段階」を表す値は、いくつもの軸（列）に分かれている。この文書は、それらを1本のライフサイクルに当てはめ、各集計がどの軸を数えているかを示す（#444、Epic #430）。値の定義はコードの側が正本で、この文書と食い違ったらコードに合わせて直す。

## 用語：MQL と SQL

一般には、見込み客を「リード → MQL → SQL → 商談 → 受注」の順に絞り込む。MQL はマーケティングの活動から「営業が追う価値がある」と判断した見込み客、SQL は営業が話したうえで「商談として進める価値がある」と判断した見込み客。DiagnoLeads では、それぞれ次のように決める（#832）。

一般の順と違い、DiagnoLeads では SQL判定を商談の前に置かない。初回ヒアリングの前には判定できないため、初回商談を商談（見極め）として作り、その出口で SQL を判定する（決定 `2026-10-25-lead-lifecycle` の却下案）。

| | MQL | SQL |
|---|---|---|
| 正式名 | Marketing Qualified Lead | Sales Qualified Lead |
| ライフサイクルでの位置 | 段の1つ（リードの次） | 段ではなく、商談（見極め）の出口の判定（関門）。分析のファネルでは、適格のリードを1段として数える（3 を参照） |
| 判定する人 | 診断（AX 移行診断と、診断ビルダーで作った診断）が回答から自動で判定する。マーケティングがパイプラインのカードの MQL のチェックで付けることもできる（診断のないリードはこちら） | 営業 |
| 判定の時期 | 診断の送信のとき。AX 移行診断では、結果の画面での相談の申込・追加の質問・別のシステムの診断で、段階が上がることがある。診断による自動の判定で段階が下がることはない。MQL のチェックを外すと MQL判定日は消えるが、回答から決まる段階は変わらない | 初回ヒアリングの後。リードの画面で記録・変更できる。商談を見極めから先へ動かすとき、未判定なら画面で聞く（API は拒まず、応答の `sqlUndecided` で知らせる。#801） |
| 判定の根拠 | AX 移行診断：必須条件（業種 × システム × 企業規模）をすべて満たせば適合（MQL候補。MQL には数えない）。加えて強いシグナルが1つ以上あれば関心あり（MQL）。必須条件が欠ければ対象外。企業規模は、対象の範囲の外を答えたときだけ欠ける。強いシグナルは、相談の申込・保守期限（ホストは期限だけで当たる。Access のサポート終了は、業務への影響・利用人数・外部データなどと重なったときだけ当たる）・決裁に関わる立場・切り替えの時期。Access は業種と企業規模を問わない。条件は `lib/features/diagnostics/ax-migration/config.ts` の `mql`。診断ビルダーの診断は、診断ごとの MQL ルール（必須条件・強いシグナル・最低スコア）で同じ3段階を決める | ヒアリングで確かめた内容 |
| 値 | MQL段階：`interest`（関心あり＝MQL）・`fit`（適合＝MQL候補）・`none`（対象外） | `qualified`（適格）・`not_qualified`（不適格）・なし（未判定） |
| 保存先 | 段階は、AX 移行診断がリードの `responses.axMigration.mql`、診断ビルダーの診断が `responses.diagnosis.mqlLevel`。両方あれば高いほうがリードの段階。MQL判定日は `leads.mql_qualified_at`。診断が自動で付けるのは、関心ありで判定日がまだないときだけ（先に付いた日は変えない）。カードの MQL のチェックでも付く | SQL判定は `leads.sql_decision`、SQL判定日は `leads.sql_decided_at` |
| 判定の後 | 初回商談の日時が確定したら、商談（見極め）に入る | 商談の画面で適格にすると、営業が動かした先のステージ（ふつうは課題の確認）へ進む。不適格にすると、失注の理由を付けて商談を閉じる。リードの画面で判定を記録しても、リードの状態は変わらない。時期を理由に失注したリードは、動くべき時期で再接触を追う（#151） |

- AX 移行診断の結果にある `sqlSignals`（`lib/features/diagnostics/ax-migration/evaluate.ts`）は、SQL判定の手がかりとして営業に見せるもので、SQL判定そのものではない。画面では「商談化の兆しあり」、営業への通知では「SQLの手がかり」と出る。回答者の自己申告から、「①システムの規模が分かる（AS/400 と ACOS は言語も。Access はツールの数と画面・帳票の数）」「②課題を感じている（保守期限・サポート終了を含む）」の両方と、「③切り替えの時期が1年以内か1〜2年」「④経営層・情報システムの責任者か担当者・業務部門の管理職（決裁者か情報システムに届く立場）」のどちらかがそろうと、手がかりありになる。条件は `config.ts` の `sqlTimelines` と `decisionAccessRoles`
- 代行のアポ・紹介・既存顧客など、診断のないリードは、MQL を経ずに商談（見極め）に入ってよい。分析のファネルでは、MQL を経ずに商談に入ったリードも MQL に数える
- MQL段階・MQL判定日・SQL判定の値と段の対応は、2.3 と 2.4 にある
- この文書と画面の「SQL」は Sales Qualified Lead を指し、データベースの問い合わせ言語の SQL とは別物。コードには両方の意味の SQL がある。Sales Qualified Lead の意味は `sqlDecision`・`sql_decision`・`sqlSignals`・`sqlUndecided`・`costPerSql` など。問い合わせ言語の意味は、drizzle の `sql`・型の `SQL`・`lib/features/leads/api/list-sql.ts`（一覧のための問い合わせを組み立てるファイル）など

## 0. 3つの機能の役割と、入力する場所

顧客探し・リード・商談は分けたまま、同じことを入力する場所を1か所に集約する（決定 `2026-10-28-consolidate-input-places`、Epic #856）。下の「入力する場所の正本」は決めた形で、子 Issue（#852〜#855）で順に合わせる。合わせるまでは、今の動き（1 以降の節）が正。

### 0.1 役割

| 機能 | 役割 | 書く人 | 終わり |
|---|---|---|---|
| 顧客探し（`prospects`） | 話した相手を、リードにする前に書く簡単な一覧。社員が書く行は氏名・連絡先を持たない（会社名・部署・役職・苗字まで）。代行のコールの報告の行もここに入る | 社員全員。段階・営業担当・代行の行は、設定を変えられる人（owner・admin）が書く | リード化（`prospects.lead_id`）・パス・見送り・契約。リード化の後の進み具合はリードと商談で見る |
| リード（`leads`） | 見込み客1人の記録。メールアドレスが必須。診断の回答・連絡先・MQL段階・SQL判定・次の行動（タスク）・活動の履歴を持つ。商談の前の段のうち、新規・再育成はリードの状態で、MQL は MQL段階で表す | リードを編集できるメンバー（診断の回答・CSV の取り込み・顧客探しのリード化からも作られる） | 受注か失注 |
| 商談（`deals`） | 1つの案件（現行調査・移行・AX 化など）。ステージ・確度・金額・受注予定日・担当を持ち、予測とボードはこれで数える。1つのリードに商談が複数つくことがある | 商談を編集できるメンバー | 受注か失注。リードの状態と商談フェーズは、商談から計算する写し（2.5）。リードの失注理由が空のときは、商談の失注理由が入る |

### 0.2 入力する場所の正本

| 項目 | 正本（入力する場所） | ほかの場所の扱い | Issue |
|---|---|---|---|
| 次の行動 | リード化の後は、リードのタスク（`lead_tasks`）。リードと商談の画面から作り、「今日」の画面からも完了にできる | 商談の「次の一手」（`deals.next_step`）は入力をやめ、既存の文はメモとして読む。顧客探しの次回アクションは、リード化の前の記録 | #853 |
| 段階 | 商談の前はリードの状態と MQL段階、商談の後は商談のステージ（SQL判定は見極めの出口） | 顧客探しの段階は、リード化の前の記録。リード化した行は集計の段階から外し、「リード化済み N 件」として分ける | #852 |
| 見込みの度合い | 商談の確度。商談の前の見込みは MQL段階（2.3） | ヒアリングの A/B/C は、確度の初期値に使う（対応は営業に確認する） | #855 |
| 商談の作成（初回商談日） | 初回の打ち合わせが確定したら、商談（見極め）を自動で作る。入口（打ち合わせの確定・顧客探しの商談日・代行のアポ）は3つとも残し、どの入口から入っても商談は1件 | 商談を手で作り忘れて、予測とボードから漏れることをなくす。入口を足すときは、#854 の作成の処理を通す | #854 |

### 0.3 統合しないもの

- 顧客探しをリードに統合する：顧客探しは、社員全員が氏名・連絡先なしで書ける一覧。リードはメールアドレスが必須なので、リードに寄せると、メールアドレスを知らない相手を書けなくなる
- リードの状態を廃止して商談だけにする：商談は初回の打ち合わせが確定してから作るので、その前の新規・再育成を表す場所がなくなる。商談を持つリードの状態は商談から計算する写しで、二重に入力する場所ではない
- 担当を1列にまとめる：顧客探しの営業担当・リードの担当・商談の担当は別の列で、1つのリードに商談が複数つく。担当は既定で引き継ぐので（顧客探しからリードにすると営業担当がリードの担当になり、商談の担当の既定はリードの担当）、分けたままでも入力は1回で済む。商談の担当とリードの担当が違うときに、商談の次の行動を誰に出すかは #853 で決める

## 1. ライフサイクル（1本）

```
リード ─→ MQL ─→ 商談（見極め） ─[SQL判定：適格]→ 商談（課題の確認 → 提案 → 条件の調整） ─→ 受注 / 失注
  │       │       ↑                    └[不適格]→ 失注（理由付き）
  │       │       └─ アポ・紹介など、MQL を経ずに入ってよい
  └───────┴─→ 再育成（ナーチャリング） ─→ 条件がそろえば MQL か商談（見極め）に戻る
```

SQL は段ではなく、見極めの出口の判定（関門）。SQL判定が「適格」のリードが、課題の確認から先に進む。

| 段 | 入る条件 | 出る条件 |
|---|---|---|
| リード | リードができたとき（診断の回答・CSV の取り込み・手入力・顧客探しからの引き継ぎ） | MQL になる、商談（見極め）に入る、再育成か失注にする |
| MQL | 診断の MQL段階が「関心あり」、または MQL判定日（`mql_qualified_at`）が入ったとき。「適合」は MQL の手前（MQL候補） | 初回商談の日時が確定する |
| 商談（見極め） | 初回商談の日時が確定したとき（商談を作る。決定：#444 のコメント 2026-10-24）。代行のアポ・紹介・既存顧客など診断のないリードは、MQL を経ずにここに入ってよい | 初回ヒアリングの後の SQL判定。適格なら課題の確認へ、不適格なら失注（理由付き）で閉じる |
| 商談（課題の確認〜条件の調整） | SQL判定が「適格」（`sql_decision = qualified`）。課題の確認へ進める前に SQL判定を記録する。商談を見極めから先へ動かすとき、未判定なら画面で判定を聞く（API は拒まず、応答の `sqlUndecided` で知らせる。#801、決定 `2026-10-26-sql-before-leaving-qualification`） | 商談が受注か失注で閉じる |
| 受注 | 商談が受注になったとき。AX 移行は段階的に売る（現行調査 → 移行 → AX 化）ので、次の商談が続くことがある。一度受注したリードは、次の商談を進めている間も状態は成約のまま | ― |
| 失注 | すべての商談が失注になったとき、または失注の理由を付けて閉じたとき。「保留」は失注ではない（#445）。時期を理由に失注したリードは、動くべき時期で再接触を追う（#151） | 動くべき時期が来て、再び商談（見極め）になる |
| 再育成 | 商談の前のリードが、時期・予算・保留などで今は進まないとき。次の行動か動くべき時期が必要（#446） | 条件がそろえば MQL か商談（見極め）に戻る |

商談を持つリードはナーチャリングにしない。止まった商談は、失注の理由「時期」で閉じる（`lib/features/deals/types/pipeline.ts` の失注の理由に「保留」はない）。リードは時期の失注になり、動くべき時期（#151）が再接触を追う。時期が来たら新しい商談を作る（決定 `2026-10-25-deals-set-lead-stage`）。

## 2. 軸ごとの対応表

### 2.1 リードの状態（`leads.status`）

定義は `lib/features/leads/types/pipeline.ts` の `LEAD_STATUSES`。

| 値 | 表示 | 段 |
|---|---|---|
| `new` | 新規 | リード・MQL（商談の前） |
| `nurturing` | ナーチャリング | 再育成 |
| `negotiating` | 商談中 | 商談（見極め〜条件の調整） |
| `won` | 成約 | 受注。次の商談（移行・AX 化）を進めている間も `won` のまま。次の商談の進み具合は `deals.stage` と `deal_phase` で見る |
| `lost` | 失注 | 失注 |

`leads.has_negotiated`（商談済み）は、一度でも商談に入ったリードに付く印で、状態が戻っても消えない。

### 2.2 商談フェーズ（`leads.deal_phase`）

定義は同じファイルの `DEAL_PHASES`。初めて入った日を `leads.deal_phase_reached_at` に残す。

| 値 | 表示 | 段 |
|---|---|---|
| `initial_hearing` | 初回ヒアリング | 商談（見極め） |
| `simple_diagnosis` | 簡易診断 | 商談（課題の確認） |
| `proposal` | 提案 | 商談（提案・条件の調整） |
| `survey_won` | 現行調査受注 | 受注（1段目） |
| `migration_won` | 移行受注 | 受注（2段目） |
| `ax` | AX化 | 受注（3段目） |

### 2.3 MQL段階と MQL判定日

診断の回答からの段階は `lib/features/leads/mql-level.ts`（`leadMqlLevel`。回答だけを読む）。MQL判定日のあるリードを関心ありとみなすのは、一覧と分析の `listMqlLevel`（`lib/features/leads/api/list-sql.ts`）。見込みの指標はこれに一本化した（決定 `2026-10-24-mql-level-over-score`）。

| 値 | 表示 | 段 |
|---|---|---|
| `interest`、または MQL判定日あり（`listMqlLevel`） | 関心あり（MQL） | MQL |
| `fit` | 適合 | リード（MQL候補） |
| `none` | 対象外 | リード（育成か失注の候補） |
| なし（診断なし） | 診断なし | リード（手入力などは MQL のチェックで判断する） |

### 2.4 SQL判定（`leads.sql_decision`）

定義は `pipeline.ts` の `SQL_DECISIONS`。

| 値 | 表示 | 意味 |
|---|---|---|
| `qualified` | 適格 | 見極めを抜けた（SQL）。課題の確認〜条件の調整と重なる |
| `not_qualified` | 不適格 | 失注（理由付き）で閉じる |
| なし | 未判定 | 見極めの前・途中 |

### 2.5 商談のステージ（`deals.stage`、#435）

定義は `lib/features/deals/types/pipeline.ts`（#435 のマージ後）。確度はステージに入ったときの初期値で、担当が商談ごとに変えられる（初期値は営業に確認する）。

| 値 | 表示 | 確度 | 段 | リードの商談フェーズ |
|---|---|---|---|---|
| `qualification` | 見極め | 10% | 商談（見極め） | 初回ヒアリング |
| `discovery` | 課題の確認 | 20% | 商談（課題の確認） | 簡易診断 |
| `proposal` | 提案 | 40% | 商談（提案） | 提案 |
| `negotiation` | 条件の調整 | 70% | 商談（条件の調整） | 提案 |
| `won` | 受注 | 100% | 受注 | 商談の種類で決まる（現行調査 → 現行調査受注、移行 → 移行受注、AX 化 → AX化）。保守・運用とその他の受注は変えない |
| `lost` | 失注 | 0% | 失注 | 変えない |

商談からリードへの反映は `lib/features/deals/lead-sync.ts` にだけ書く。商談を持つリードの状態と商談フェーズは、商談の作成・変更・削除のたびに商談から計算し直し、手では変えない（`leads.update`・一括の状態変更・REST API v2 が拒む）。受注を開き直す・消すとリードも戻る。最後の商談を消すと、リードはそのままの値で残り、手で変えられるようになる（#444、決定 `2026-10-25-deals-set-lead-stage`）。

### 2.6 顧客探しの段階（`prospects.stage`、#265）

定義は `lib/features/prospects/types/schemas.ts` の `PROSPECT_STAGES`。顧客探しは、SAS のメンバーが話した相手をリードにする前に書く一覧で、値は表計算の選択肢に合わせてある。リードに引き継いだ（`prospects.lead_id` が入った）後はリードと商談の側が正で、顧客探しの段階は変えられない（画面と API で止めている）。#852 のマージ後は、リード化した行を集計の段階から外し、「リード化済み N 件」として分ける（決定 `2026-10-28-consolidate-input-places`）。

| 値・項目 | 表示 | 当たる段（目安） |
|---|---|---|
| `interest` | 1 関心確認 | リードの前（引き継ぐとリード） |
| 商談日（`meeting_on`）が入った | ― | 商談（見極め）を作る時点 |
| `quick_diagnosis` | 2 簡易診断 | 商談（課題の確認） |
| `spec_survey` | 3 現行仕様調査 | 受注（1段目：現行調査）。営業に確認する |
| `proposal` | 4 移行提案 | 商談（提案。移行の商談） |
| `contract` | 5 契約 | 受注（2段目：移行）。現行調査だけの契約もあり得るので、営業に確認する |
| `nurturing` | 育成 | 再育成 |
| `dropped` | 見送り | 失注 |

顧客探しの段階とリードの状態は自動では連動しない。

## 3. 集計がどの軸を数えているか

| 集計 | 場所 | 数えている軸 |
|---|---|---|
| ダッシュボードのパイプライン（状態ごとの件数） | `lib/features/analytics/dashboard.ts` | `leads.status` |
