### [UI] 開発室（鍵4）を部屋にする。ボードは現行調査の商談、行を開くと準備ファイル（ヒアリングの要約と事前調査カード）。読むだけで、API は足さない（#1194）
- **日付**: 2026-11-14
- **きっかけ**: オーナーの指示「AI社員オフィスに適したエンジニアリング機能をリファクタリングお願いします」。同じ時間に、マーケティング・セールス・バックオフィスのセッションが、それぞれの部屋を受け持っていた
- **決定**（オーナーの判断。2026-11-14、4つの範囲の案から「開発室を部屋にする」を選んでもらった）:
  - 開発室を、扉（`/deals?kind=survey`。決定 `2026-11-14-navigation-one-path` の表の鍵4）から部屋にする。鍵の数字は変えない
  - 部屋の中身は、決定 `2026-11-14-concept-and-flow` の「あとで決めること」の前提（ヒアリングと提案の準備）のとおり
- **形**（実装で決めた）:
  - 壁のボード：進行中の現行調査の商談。`deals.board` を `kinds: ['survey']`・`owner: 'all'`・`closedWithinDays: 0` で1回読み、表示の切り替え（1 進行中の全部・2〜5 開いた段ごと）とページ送りは、その答えから手元で切る。受注・失注は出さない
  - 案内の数字：進行中の件数・提案の段の件数（どちらも列の `count`。ボードの上限を超えても数える）・次の行動が無い件数（並んでいる商談の `hasOpenTask`）。ボードが上限（500件）で切られているときは、並んだ商談から数える件数は言わず、通常の表示へ案内する（営業フロア #1207 と同じ決まり）
  - 行を開くと「準備ファイル」：`leadHandoff.get`（最新のヒアリングと、初回ヒアリングから先へ進んだ日）→ `leadHearings.summary`（要約）と、`leadPrep.get`（事前調査カード）。数字のキー（1・2）は、ファイルの見る場所を切り替えるだけ
  - 部屋もファイルも読むだけ。ヒアリングの記録・カードの編集・段の移動は、ファイルの下のリンクから通常の表示で行う
  - 純粋な関数は `rooms/survey-board.ts`（#1142 の「部屋ごとの純粋な関数は rooms/ に置く」に合わせた）
- **理由**:
  - 現行調査の商談は、もともと開発室の扉が開いていたもの。決定 `2026-11-14-navigation-one-path` が「エンジニアの役目（現行システムの調査）に合う」として選んでいる
  - 「部屋のために API を足さない」（決定 `2026-11-13-office-is-the-base`）。準備の状況（ヒアリング・カードの有無）を一覧の行に出すには、行ごとの問い合わせか新しい API が要るので、行を開いたときにだけ読む
  - 空で保存された事前調査カードは「無い」と同じに扱う（`prepCardFilled`）。用意していないものを、用意したように見せない
- **却下案**:
  - ボードの行に、ヒアリングと事前調査カードの有無を出す：行ごとに3本の問い合わせになる。API を足すなら #1110（AIエンジニアが下書きを用意する）のときに考える
  - 部屋の中でヒアリングや事前調査カードを書く：入力欄が多く、「選択肢で答える」部屋の型に合わない。まず読む場所として作る
  - 営業フロアの商談のファイル（#1171）を待って共用する：営業フロアは商談を動かす場所、開発室は準備を読む場所で、ファイルの中身が違う
- **ほかの決定への影響**:
  - `2026-11-14-navigation-one-path`：表の鍵4は「部屋（現行調査）」になる。`DOOR_PAGES` から `engineering` を外した（同じページは、ボードの下の「通常の表示の商談で開く」から開ける）
  - `2026-11-14-concept-and-flow`：「あとで決めること」の「開発室の部屋の中身」は、これで決まった
- **ルール**:
  - AIエンジニアが仕事を持ったら（#1110）、用意した下書きの報告はこの部屋の案内に足す。していない仕事を、したように書かない（`roomGuide`）
  - 準備ファイルに実行の選択肢を足すときは、決定 `2026-11-13-office-is-the-base` の「選択肢で実行するときの決まり」（数字は実行だけ・取り消しは Z・戻るは Esc）に従い、見る場所の切り替えとキーを分ける
