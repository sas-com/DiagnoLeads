### [Sales] リードの段階を1本のライフサイクルで定義し、各軸の対応表を docs に置く（#444）
- **日付**: 2026-10-25
- **決定**: リードの段階は「リード → MQL → 商談（見極め） → SQL → 商談（課題の確認・提案・条件の調整） → 受注／失注」の1本で表し、閉じる前のどの段からも再育成（ナーチャリング）に移れる。状態・商談フェーズ・MQL段階・SQL判定・商談のステージ・顧客探しの段階の各値がどの段に当たるかと、各集計がどの軸を数えているかは `docs/PIPELINE_LIFECYCLE.md` に書く。営業パイプラインの評価（Epic #430）の推奨案を、オーナーが承認（2026-10-24）
- **理由**: 段階を表す値が5つの軸に分かれ（#435 の商談で6つ目）、互いの関係が書かれていなかった。集計ごとに数える軸が違い、数字が食い違って見えた
- **ルール**:
  - 商談は初回商談の日時が確定したときに作る。商談の「見極め」（10%）が初回ヒアリングに当たり、SQL判定がその出口になる（不適格なら失注の理由を付けて閉じるか、再育成にする）
  - MQL は、MQL段階の「関心あり」か MQL判定日のあるリード。「適合」は MQL候補で、MQL には数えない（決定 `2026-10-24-mql-level-over-score`）
  - 「保留」は失注ではなく再育成（決定 `2026-10-24-on-hold-is-not-lost`）
  - 顧客探しの段階はリードにする前の記録で、リードに引き継いだ後はリードの側が正。両者は自動では連動しない。対応は目安として docs に書く
  - 値を足す・変えるときは、`lib/features/leads/types/pipeline.ts` の冒頭のコメントと `docs/PIPELINE_LIFECYCLE.md` の表も直す
  - 商談を持つリードの状態・商談フェーズを読み取り専用にし、商談から毎回計算するのは #444 の2つ目の PR（#435 のマージ後）。そのときに #435 の「前に進めるだけ」を置き換える決定を足す
- **見直しの条件**: 顧客探しの段階とリードの状態の食い違いが運用で問題になったら、引き継いだ後の顧客探しの段階を読み取り専用にするか、リードから反映するかを決める
- **却下案**: SQL を商談の前に置く（初回ヒアリングの前に SQL判定はできない。見極めを商談の最初のステージにして、SQL判定をその出口にした）
