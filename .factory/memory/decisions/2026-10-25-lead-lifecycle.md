### [Sales] リードの段階を1本のライフサイクルで定義し、各軸の対応表を docs に置く（#444）
- **日付**: 2026-10-25
- **決定**: リードの段階は「リード → MQL → 商談（見極め） →［SQL判定］→ 商談（課題の確認・提案・条件の調整） → 受注／失注」の1本で表す。SQL は段ではなく見極めの出口の判定。商談の前のリードは再育成（ナーチャリング）に移れる。状態・商談フェーズ・MQL段階・SQL判定・商談のステージ・顧客探しの段階の各値がどの段に当たるかと、各集計がどの軸を数えているかは `docs/PIPELINE_LIFECYCLE.md` に書く。営業パイプラインの評価（Epic #430）の推奨案を、オーナーが承認（2026-10-24）
- **理由**: 段階を表す値が5つの軸に分かれ（#435 の商談で6つ目）、互いの関係が書かれていなかった。集計ごとに数える軸が違い、数字が食い違って見えた
- **ルール**:
  - 商談は初回商談の日時が確定したときに作る。商談の「見極め」（10%）が初回ヒアリングに当たり、SQL判定がその出口になる（不適格なら失注の理由を付けて閉じる）。代行のアポ・紹介など診断のないリードは、MQL を経ずに見極めに入ってよい
  - MQL は、MQL段階の「関心あり」か MQL判定日のあるリード。「適合」は MQL候補で、MQL には数えない（決定 `2026-10-24-mql-level-over-score`）
  - 「保留」は失注ではなく再育成（決定 `2026-10-24-on-hold-is-not-lost`）
  - 一度受注したリードは、次の商談（移行・AX 化）を進めている間も状態は成約のまま。次の商談の進み具合は商談のステージと商談フェーズで見る（#435 の反映の規則）
  - 商談を持つリードは再育成（ナーチャリング）にしない。止まった商談は時期を理由に失注にし、動くべき時期で再接触を追う（決定 `2026-10-25-deals-set-lead-stage`）
  - 顧客探しの段階はリードにする前の記録で、リードに引き継いだ後はリードの側が正。引き継いだ後は顧客探しの段階を更新しない~~（仮の運用）~~ → 確定した（リード化した行の段階は画面と API で変えられない）。リード化した行は集計の段階から外し、「リード化済み N 件」として分ける（決定 `2026-10-28-consolidate-input-places`、#852）。両者は自動では連動しない。対応は目安として docs に書き、「3 現行仕様調査」「5 契約」の当てはめは営業に確認する
  - 分析のファネルは、この段（リード → MQL → 商談 → SQL → 受注）で数える。後の段に進んだリードは前の段にも数え、再育成は段にせず、今ナーチャリング中のリードの数として別に出す（#802、2026-10-26 オーナーが推奨案で承認）
  - 値を足す・変えるときは、`lib/features/leads/types/pipeline.ts` の冒頭のコメントと `docs/PIPELINE_LIFECYCLE.md` の表も直す
  - 商談を見極めから先へ動かす前に、画面で SQL判定を聞く。API は拒まず `sqlUndecided` で知らせる（決定 `2026-10-26-sql-before-leaving-qualification`、#801）
  - 商談を持つリードの状態・商談フェーズは読み取り専用で、商談から毎回計算する（決定 `2026-10-25-deals-set-lead-stage`、#444 の2つ目の PR）
- **見直しの条件**: 顧客探しの段階とリードの状態の食い違いが運用で問題になったら、引き継いだ後の顧客探しの段階を読み取り専用にするか、リードから反映するかを決める
- **却下案**: SQL を商談の前に置く（初回ヒアリングの前に SQL判定はできない。見極めを商談の最初のステージにして、SQL判定をその出口にした）
