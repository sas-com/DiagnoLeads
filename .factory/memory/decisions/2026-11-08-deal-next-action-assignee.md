### [Sales] 商談の画面で入れた次の行動は、商談の担当とリードの担当が違うときだけ商談の担当に出す（#853）
- **日付**: 2026-11-08
- **決定**（オーナーの判断「進めてください」、2026-11-08。#853 の計画の案 B-2。決定 `2026-10-28-consolidate-input-places` が #853 に預けた問いへの答え）:
  - 商談の画面（商談の詳細の「次の行動・持ち帰り事項」、ボードと一覧の「次の行動を追加」）で入れた次の行動・持ち帰り事項は、商談の担当とリードの担当が違うときだけ、次の行動の担当（`lead_tasks.assignee_id`）を商談の担当にする。期限の通知と「今日」（「自分」の次の行動）は、その人に出る
  - 同じときは空のままにし、今までどおりリードの担当に従う。リードに担当がいないときは「違う」に数え、商談の担当にする（追加した人に出ると、警告を受ける商談の担当とずれるため）
  - 商談に担当がいないとき、商談の担当が今は担当を持てない（組織のメンバーでない・閲覧だけの役割）ときも空のまま（リードの担当 → 追加した人）
  - あとで商談の担当やリードの担当を変えても、入れた次の行動の担当は移さない（移すのは別の Issue）
- **理由**:
  - 警告（リードに次の行動がない）と「注意が必要な商談」は商談の担当に出る（ボードの「自分」・「今日」の画面は商談の担当で選ぶ）。一方、次の行動の「自分」と期限の通知は、タスクの担当 → リードの担当 → 作成者で決まる。担当が違うと、商談の担当が自分で入れた次の行動の知らせがリードの担当に届き、人の単位で食い違う
  - 既定の運用では担当を引き継ぐ（商談の担当の既定はリードの担当）ので同じ人になり、今の動きを変えない
  - スキーマを変えない。人の id を入力で受けないので、「ほかの人にタスクを割り当てる」新しい権限を作らない
- **ルール**:
  - 入力は `dealId` だけ（`createTaskSchema`。strict のまま `assigneeId` は拒む）。担当はサーバーが商談から決める（`lib/features/lead-follow-up/service.ts` の `dealOwnerAssignee`。担当を持てるかは `findAssignableMember`）
  - `dealId` を送るには商談を読める必要がある（ルーターの `canReadDeals`。読めない役割は FORBIDDEN。連絡の記録の商談と同じ）
  - サービスは、リードを FOR NO KEY UPDATE でロックしてから商談を読む（商談の変更・削除もリードを先にロックするので、読んだ担当は追加が終わるまで変わらない）。商談は id・組織・リードの3つで読み、無ければ BAD_REQUEST。別のリードの商談・別の組織の商談・存在しない id に同じ答えを返し、存在を漏らさない
  - 監査の行は `metadata.dealId` を持ち、担当を入れたときだけ `changes.after.assigneeId` を持つ
  - 担当を入れた次の行動には、リードの画面と商談の詳細のカードに「担当：名前」を出す（辞めた人でも名前を出す）。ダイアログと商談の詳細の追加フォームは、知らせが誰に出るかを書く（商談の担当が担当を持てるメンバーのときはその人、ほかはリードの担当（いなければ追加した人））
  - ボードのカードと一覧の行の「次の行動を追加」は、警告が出る開いた商談にだけ、商談を書ける人（`canEdit`）に出す。追加したらボードを読み直し、フォーカスは商談名のリンクへ移す（ボタンは消えるため）。追加せずに閉じたら、ボタンに戻す
  - 商談の「次の一手」（`deals.next_step`）の API は、送られても受け付けて捨てる（#888 で済み）。列を消すのは別の Issue
- **却下案**:
  - A（今のまま）：変更はいらないが、商談の担当は警告を受けるのに、自分で入れた次の行動の知らせはリードの担当に届く食い違いが残る
  - B-1（いつも商談の担当にする）：担当が同じ既定の運用でも担当が固定される。リードの担当を付け替えても、タスクが前の人に残る（今はリードの担当を変えればタスクも移る）
  - B-3（B-1 に加えて、商談の担当を変えたら前の担当の未完了の次の行動を移す）：決まりは一番すっきりするが、商談のサービスが lead_tasks と監査の行を書き換える。同じ人が持つ開いた商談が1つのリードに2つあると、両方のタスクが動く
  - C（`lead_tasks` に商談を指す列を足す）：スキーマの変更が要り、警告を商談ごとに数え直し、タスクを読むすべての所で deals を結合する。見直しの条件が出てから検討する
- **見直しの条件**:
  - 担当を固定した後で商談の担当を変えても次の行動が移らないことが問題になったら、B-3 にするか、画面でタスクの担当を変えられるようにするかを決める（別の Issue）
  - リードの担当がリードの画面で入れた次の行動は、商談の担当の「今日」には出ない（リード単位の次の行動の性質）。同じリードに開いた商談が並ぶ運用が出たら、案 C を検討する（決定 `2026-10-28-consolidate-input-places` の見直しの条件）
  - メンバーを外しても担当を付け替えないため、辞めた人が担当の次の行動は誰の「自分」にも出ない（前からある性質。リードの担当も同じ）。問題になったら、メンバーを外すときの付け替えを決める
