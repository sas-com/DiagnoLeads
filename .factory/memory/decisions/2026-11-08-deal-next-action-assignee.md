### [Sales] 開いた商談の画面で入れた次の行動は、商談の担当とリードの担当が違うときだけ商談の担当に割り当てる（#853）
- **日付**: 2026-11-08
- **決定**（オーナーの判断「進めてください」、2026-11-08。#853 の計画の案 B-2。決定 `2026-10-28-consolidate-input-places` が #853 に預けた問いへの答え）:
  - 開いた商談の画面（商談の詳細の「次の行動・持ち帰り事項」、ボードと一覧の「次の行動を追加」）で入れた次の行動・持ち帰り事項は、商談の担当とリードの担当が違うときだけ、次の行動を商談の担当に割り当てる（`lead_tasks.assignee_id`）。期限の通知と「今日」（「自分」の次の行動）は、その人に出る
  - 同じときは割り当てず、今までどおりリードの担当に従う。リードに担当がいないときは「違う」に数え、商談の担当に割り当てる（追加した人に出ると、警告を受ける商談の担当とずれるため）
  - 受注・失注の商談の詳細で入れたときは割り当てない（警告は開いた商談だけに出るため。security-specialist のレビュー、2026-11-08）。監査の行には商談を残す
  - 商談に担当がいないとき、商談の担当が今は担当を持てない（組織のメンバーでない・閲覧だけの役割）ときも割り当てない（リードの担当 → 追加した人）
  - あとで商談の担当やリードの担当を変えても、割り当てた次の行動は移さない（移すのは別の Issue）
- **理由**:
  - 警告（リードに次の行動がない）と「注意が必要な商談」は商談の担当に出る（ボードの「自分」・「今日」の画面は商談の担当で選ぶ）。一方、次の行動の「自分」と期限の通知は、タスクの担当 → リードの担当 → 作成者で決まる。担当が違うと、商談の担当が自分で入れた次の行動の知らせがリードの担当に届き、人の単位で食い違う
  - 既定の運用では担当を引き継ぐ（商談の担当の既定はリードの担当）ので同じ人になり、今の動きを変えない
  - スキーマを変えない。人の id を入力で受けないので、「ほかの人にタスクを割り当てる」新しい権限を作らない
- **ルール**:
  - 入力は `dealId` だけ（`createTaskSchema`。strict のまま `assigneeId` は拒む）。割り当てる人はサーバーが商談から決める（`lib/features/lead-follow-up/service.ts` の `dealOwnerAssignee`。商談のステージが受注・失注なら割り当てない。担当を持てるかは `findAssignableMember`）
  - `dealId` を送るには商談を読める必要がある（ルーターの `canReadDeals`。読めない役割は FORBIDDEN。連絡の記録の商談と同じ）
  - サービスは、リードを FOR NO KEY UPDATE でロックしてから商談を読む（商談の変更・削除もリードを先にロックするので、読んだステージと担当は追加が終わるまで変わらない）。商談は id・組織・リードの3つで読み、無ければ BAD_REQUEST。別のリードの商談・別の組織の商談・存在しない id に同じ答えを返し、存在を漏らさない
  - 監査の行は `metadata.dealId` を持ち（受注・失注の商談でも）、割り当てたときだけ `changes.after.assigneeId` を持つ
  - 割り当てた人を組織から外すと（`lib/features/members/api/router.ts` の remove）、同じトランザクションで、その組織の未完了の次の行動・持ち帰り事項のうち、その人に割り当てたものの割り当てを戻す（`releaseTaskAssignments`。#968）。戻したものは、リードの担当 → 追加した人に出る。完了したもの（記録として割り当てを残す）・ほかの組織のもの・ほかの人に割り当てたものは変えない。完了したものを未完了に戻すとき、割り当てた人が担当を持てない（メンバーでない・閲覧だけの役割）なら割り当てを外す（`updateTask`。監査の行の before/after に `assigneeId`。security-specialist のレビュー、2026-11-08）。送った期限の通知は送り直さない。監査の行はタスクごとに1行（`action: 'update'`、`changes` は `assigneeId` の前後、`metadata` は `leadId` と `via: 'member_removed'`、`userId` は外した人）
  - 追加・未完了に戻すと外すが重なっても戻し損ねない：追加と未完了に戻すときは、割り当てる人のメンバーの行を FOR KEY SHARE でロックしてから、担当を持てるかを確かめる（`holdAssignableMember`。役割の変更は待たせない）。外す処理は、メンバーの行を消してから戻す（消すのがそれらの終わりを待ち、そのあとの UPDATE がそれらも戻す。消した後の追加はその人に割り当てず、未完了に戻すと割り当てを外す）
  - 割り当てた次の行動には、リードの画面と商談の詳細のカードに「割り当て：名前」を出す（辞めた人でも名前を出す）。ダイアログと商談の詳細の追加フォームは、送信ボタンの上に、知らせが誰に出るかを言い切る（開いた商談で、商談の担当が担当を持てるメンバーのときはその人。自分なら「あなた」。ほかは「リードの担当（いなければあなた）」）
  - ボードのカードと一覧の行の「次の行動を追加」は、警告が出る開いた商談にだけ、商談を書ける人（`canEdit`）に出す。追加したらボードを読み直し、フォーカスは商談名のリンクへ移す（ボタンは消えるため）。追加せずに閉じたら、ボタンに戻す
  - 商談の「次の一手」（`deals.next_step`）の API は、送られても受け付けて捨てる（#888 で済み）。列を消すのは別の Issue
- **却下案**:
  - A（今のまま）：変更はいらないが、商談の担当は警告を受けるのに、自分で入れた次の行動の知らせはリードの担当に届く食い違いが残る
  - B-1（いつも商談の担当に割り当てる）：担当が同じ既定の運用でも割り当てるので、リードの担当を付け替えても、タスクが前の人に残る（今はリードの担当を変えればタスクも移る）
  - B-3（B-1 に加えて、商談の担当を変えたら前の担当の未完了の次の行動を移す）：決まりは一番すっきりするが、商談のサービスが lead_tasks と監査の行を書き換える。同じ人が持つ開いた商談が1つのリードに2つあると、両方のタスクが動く
  - C（`lead_tasks` に商談を指す列を足す）：スキーマの変更が要り、警告を商談ごとに数え直し、タスクを読むすべての所で deals を結合する。見直しの条件が出てから検討する
- **見直しの条件**:
  - 割り当てた後で商談の担当を変えても次の行動が移らないことが問題になったら、B-3 にするか、画面で割り当てを変えられるようにするかを決める（別の Issue）
  - リードの担当がリードの画面で入れた次の行動は、商談の担当の「今日」には出ない（リード単位の次の行動の性質）。同じリードに開いた商談が並ぶ運用が出たら、案 C を検討する（決定 `2026-10-28-consolidate-input-places` の見直しの条件）
  - 割り当てた次の行動は、リードや商談の担当を付け替えても戻らない。メンバーを外すと戻る（#968）
