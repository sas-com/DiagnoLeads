### [Security] 外のサイトが始めた要求では、出社の画面を自分で開かせない（アドレスの印をプロキシで外す。取り消せない操作の確認は、キーだけでは通さない）（#1175）
- **日付**: 2026-11-14
- **きっかけ**: PR #1174（#1169、ロゴで出社の画面をフロアから開く）の `security-specialist` のレビューの指摘 S1。出社の画面は、アドレスの印（`?source=app`・`login`・`home`）で自分で開き、キーだけで操作に届く（`E` → `1` で採用・休止・復帰、`5` → `1` で次の行動を済みにする）。外のサイトが、ログイン中の人に文字を打たせながら新しいタブでこのアドレスを開くと、続きの打鍵が出社の画面に届く可能性がある（コードから組み立てた筋道。実際の打鍵の届き方は試していない）。今届く操作は元に戻せるものだけだが、#1170 で解雇（取り消せない）が選択肢に入る
- **決定**（オーナーの判断。2026-11-14、こちらの推奨に「進めてください」）:
  - **a**：このサイト自身（`Sec-Fetch-Site: same-origin`）と利用者本人（`none`）が始めた要求のほかは、オフィスのページに印が付いていたら、プロキシで印を外したアドレスへ送り直す（`lib/middleware/office-entry.ts`）。オフィスは通常の表示で開く。`cross-site` に加えて `same-site` も外す（独自ドメインを付けたあと、兄弟のサブドメインから開かせない。印を正しく付ける経路は、同じオリジンのリンクとアプリの起動だけ）
  - **b**：取り消せない操作（解雇）の確認は、数字のキーの続け打ちでは通せない形にする（ボタンのクリックか、名前の入力）。#1170 で実装する
    - **実装した**（#1170、2026-11-14）：会話の「解雇する」（鍵4）は欄を開くだけで、その AI社員の名前を入力するまで実行のボタンを閉じる（`components/features/ai-employees/office-talk-staff.tsx` の `namesTheEmployee`）。欄が開いている間、数字のキーは選択肢に届かない。Esc で閉じると、入力は残らない
    - **これで守れること**：数字・Enter・Space の続け打ちや押しすぎでは、解雇にならない（手元のブラウザで確かめた。`E` → `4` → 数字・Enter・Space・Tab の列で、要求は出なかった）
    - **守れないこと**（`security-specialist` のレビューの指摘 S1・S2。コードから組み立てた筋道で、打鍵は試していない）：名前の入力は「キーだけでは通せない形」ではない。出社の画面に届く打鍵を、名前を知っている・変えられる相手が決められるなら、キーだけで解雇に届く
      - 名前を知らなくても：`2`（名前を変える）→ Tab を3回（フォーカスが一周して入力が全選択になる）→ 1文字 → Enter → Enter → `E` → `4` → 同じ1文字 → Enter
      - 既定の名前のまま：英語の既定の名前は英字と空白だけで、公開リポジトリから分かる。`E` → `4` → 既定の名前 → Enter（日本語の既定の名前はカタカナを含み、変換が要る）
      - 名前が数字だけの AI社員：その数字と Enter
    - **受け入れた理由**：a のあと、外から出社の画面に届くのは「残る経路」だけで、利用者が十数打鍵を、切り替わった画面に指示どおり打ち続ける必要がある。消えるのは AI社員1人の行（名前・状態・見た目と話し方の設定）で、作業記録は残り、採用し直せる。塞ぐなら、最後の実行にポインターの操作を求める（キーによる押下を無視する）。そうすると、キーだけで操作する人は通常の表示で解雇することになる。**オーナーに確かめる**（#1170 の PR の本文に書いた。決まるまでは今の形）
- **却下案**: 印で開いたときは、最初のポインター操作か一定の時間までキーを無視する（打ち続ける相手には効きにくい）
- **ルール**:
  - 出社の画面を自分で開く印を足すときは、同じキー（`source`）に載せる。プロキシは値を見ずにキーごと外すので、新しい印も守られる。別のキーにするなら、`office-entry.ts` も直す
  - 判定は、ルーターが実際に出すパスで行う（言語の接頭辞の有無・エスケープ・重なったスラッシュと `\`・末尾のスラッシュ・大文字小文字をならしてから比べる）。広めに判定しても、印が外れるだけで害は無い。メソッドは見ない（外のサイトのフォームの POST は、Cookie が付かずログインへの誘導に回るので、そこへ印を持ち込ませない）
  - 送り直しは、ログインへの誘導より先に行う（印が `callbackUrl` に入って、ログインのあとに戻ってこないように）。どちらの送り直しも、誰が頼んだかで答えが変わるので `Cache-Control: private, no-store`
  - `Sec-Fetch-Site` が `same-origin`（アプリの中の移動）・`none`（アドレスの入力・ブックマーク・インストールしたアプリの起動）のとき、ヘッダーが無いとき（古いブラウザ）は、今までどおり。古いブラウザでは守りが効かないので、取り消せない操作は b で別に守る
  - このサイトの中から、利用者の操作なしに印付きのアドレスへ自動で移す処理を足さない（その移動は `same-origin` になり、この守りを通る）。診断テンプレートの `redirectUrl`・`ctaUrl`（今は画面から使っていない）を回答後の移動に使い始めるときは、管理画面のパスを行き先にできない検査を入れる
  - 外部のログイン（ソーシャルログイン）を足すと、戻りのリダイレクトの連鎖が `cross-site` になり、到着の印が外れて出社の画面が開かなくなる。足すときに、戻り先をクライアント側の移動にするかを決める
  - 出社の画面に、キーだけで届く取り消せない操作を足さない。足すなら、確認をキーだけで通せない形にする
- **確かめたこと**（2026-11-14、手元の開発サーバー）: 別のホストのページからのリンク（`source=home`・`source=login`）と `window.open` で、307 のあと通常の表示のオフィスが開き、出社の画面は開かない。続けて `e`・`1` を打っても何も起きない。ロゴ（同じオリジン）と、アプリの開始 URL を直接開いた場合は、今までどおり出社の画面が開く
- **確かめていないこと**: Safari・Firefox での `Sec-Fetch-Site` の付き方（Chromium だけで確かめた）。インストールしたアプリを実機で起動したときの値（仕様では `none`）
- **残る経路**（この守りの外。`security-specialist` のレビューの指摘で書き直した）:
  - ログインの画面を経る経路：外のサイトがログインの画面を開かせ、利用者がその場でログインすると、ログインのあとの既定の行き先が印付きの決まったパス（#1153）なので、出社の画面（タイトル）が開く。`callbackUrl` は要らない。タイトルは「出社する」にフォーカスがあり、Enter 1打でフロアに入る。パスワードの自動入力がある環境では、ログインも打鍵だけで通る可能性がある（未確認）
  - インストールしたアプリのウィンドウ：印が無くてもタイトルが開く。外のリンクをアプリのウィンドウで開く設定の環境では、この守りの外（未確認）
  - どちらも、届くのは元に戻せる操作だけ。塞ぐには「ログイン後は出社の画面」（#1153）を変えることになるので、蒸し返さない。**取り消せない操作は、決定 b（確認をキーだけでは通さない）で守る。#1170 の受け入れ基準は b に依存する**
