### [Leads] 動くべき時期の毎朝の再計算は、更新の新しい順にページを読み切る（#374）
- **日付**: 2026-10-24
- **決定**: 毎朝の再計算（`recomputeRecentlyUpdated`）は、直近2日に更新されたすべての組織のリードを、更新の新しい順（同じ時刻は id の順）に100件ずつ読み、残りがなくなるか10秒の時間予算を使い切るまで続ける。打ち切ったときは残りの件数を返し、ログに警告を出す。`2026-10-19-act-timing` の「古い順に100件まで、10秒で打ち切り、残りは翌朝」はこれで置き換える
- **理由**:
  - 古い順に100件で止めると、1日に100件を超える更新があったとき、窓の中で一番古い100件を毎朝処理し直し、新しいリードが窓から外れるまで順番が回ってこないことがあった
  - 新しい順なら、時間切れで残るのは、前の日の実行がまだ新しいうちに処理した古い更新になる。1日の更新が時間予算の中で処理できる件数に収まる限り、取りこぼさない
  - スキーマを変えずに直せる（AX の公開直前で、マイグレーションは本番への適用が要る）
- **却下案**:
  - 処理した時刻の列（例：`act_timing_computed_at`）を足し、「更新が再計算より新しいもの」だけを取る：取りこぼしは最も少ないが、マイグレーションが要る。1日の更新が時間予算を超えるようになったら見直す
  - ワークフローのランナーの定期実行での続き・回収（#299）に載せる：ランナーはまだ着手前（最初の利用先が決まってから）。#299 ができたら、続きをそちらに任せるかを決め直す
  - 続きの位置を JS の Date で持つ：ミリ秒に丸められ、同じミリ秒の中で更新されたリードを飛ばしたり読み直したりする
- **ルール**:
  - 続きの位置は、最後に処理したリードの更新時刻（マイクロ秒まで。文字列で持つ）と id で表す
  - 再計算は `leads.updated_at` を変えない（変えると、再計算したリードが窓を埋める）
  - 各リードは、そのリードの組織の ID と設定で計算する
  - 実 DB のテストで毎朝の実行を確かめるときは、ほかのテストのリードを読まないよう、未来の時刻で窓を作る（`test/unit/integration/act-timing.db.test.ts`）
