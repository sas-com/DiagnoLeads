### [Leads] 動くべき時期の毎朝の再計算は、更新の新しい順にページを読み切る（#374）
- **日付**: 2026-10-24
- **決定**: 毎朝の再計算（`recomputeRecentlyUpdated`）は、直近2日に更新されたすべての組織のリードを、更新の新しい順（同じ時刻は id の順）に100件ずつ読み、残りがなくなるか10秒の時間予算を使い切るまで続ける。打ち切ったときは残りの件数を返し、ログに警告を出す（前の日の実行が読めなかったリードが残れば、運用の通知でも知らせる）。リード1件の失敗では止めない。`2026-10-19-act-timing` の「古い順に100件まで、10秒で打ち切り、残りは翌朝」はこれで置き換える
- **理由**:
  - 古い順に100件で止めると、1日に100件を超える更新があったとき、窓の中で一番古い100件を毎朝処理し直し、新しいリードが窓から外れるまで順番が回ってこないことがあった
  - 新しい順なら、時間切れで残るのは、前の日の実行がまだ新しいうちに処理した古い更新になる。1日の更新が時間予算の中で処理できる件数に収まる限り、取りこぼさない
  - スキーマを変えずに直せる（AX の公開直前で、マイグレーションは本番への適用が要る）
- **却下案**:
  - 処理した時刻の列（例：`act_timing_computed_at`）を足し、「更新が再計算より新しいもの」だけを取る：取りこぼしは最も少ないが、マイグレーションが要る。1日の更新が時間予算を超えるようになったら見直す
  - ワークフローのランナーの定期実行での続き・回収（#299）に載せる：ランナーはまだ着手前（最初の利用先が決まってから）。#299 ができたら、続きをそちらに任せるかを決め直す
  - 続きの位置を JS の Date で持つ：ミリ秒に丸められ、同じミリ秒の中で更新されたリードを飛ばしたり読み直したりする
- **ルール**:
  - 続きの位置は、最後に処理したリードの更新時刻（マイクロ秒まで。文字列で持つ）と id で表す
  - 再計算は `leads.updated_at` を変えない（変えると、再計算したリードが窓を埋める）
  - 各リードは、そのリードの組織の ID と設定で計算する
  - 時間予算は、各リードの前と次のページを読む前に確かめる。ページの読み込みと、打ち切ったあとの残りの数え上げは予算の外（`leads (updated_at, id)` の索引 `leads_updated_at_id_idx` を後ろから読み、表を走査しない。#574 で足した。窓の条件や並びを変えるときは、この索引を使い続けるかを `act-timing.db.test.ts` の EXPLAIN のテストで確かめる）
  - 打ち切ったときは、残り（`pending`）と、そのうち直近1日に更新されたもの（`unseen`：前の日の実行が読めなかったもの）を返す。`pending` には前の日に処理済みの古い更新も入るので、取りこぼしの数ではない。`unseen` が1件でもあれば `reportServerError`（`cron/act-timing-time-limit`）で知らせる。これが却下案の「1日の更新が時間予算を超えるようになったら見直す」のきっかけになる
  - リード1件の再計算が失敗しても止めない。ログに残して次のリードへ進み、最後に1回だけ知らせる（`cron/act-timing-lead`）。止めると、新しい順なので、そのリードより古い窓内のリードが、失敗するリードが窓から外れるまで毎朝処理されない
  - 実 DB のテストで毎朝の実行を確かめるときは、ほかのテストのリードと、強制終了したテストの残りを読まないよう、DB のどのリードよりも後の時刻で窓を作る（`emptyWindow`、`test/unit/integration/act-timing.db.test.ts`）
