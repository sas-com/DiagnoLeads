### [Architecture] AI社員は Claude のエージェントにする方針で、共通の仕組みと業務パックに分ける。役割は一般の営業の仕事で書き、当社固有の仕事は AX 移行パックに置く（#1114・#1115）
- **日付**: 2026-11-13（オーナーの判断。2026-11-12〜13 の会話）
- **決定**（オーナー判断）:
  - 目的：一般の中小企業でも AI エージェントを導入しやすくする存在になる。中小企業の社長が既に知っている「人を採用して、教えて、任せる範囲を広げる」をそのまま操作にする
  - AI社員は、決まったまとめ処理ではなく、Claude のエージェント（指示と道具と記憶を持ち、複数の手順を自分で進めるもの）として作る方向で設計する。採用したらオンボーディングをして、エージェントが記憶を記録し、目的と役割を理解するところから始める。エージェントにはレベルを持たせ、スキルと実績で評価する。なるべく人と同じ節目にそろえる。設計案は #1114
  - 対象の広げ方は、A（このアプリで営業を管理する企業の営業まわり）と B（外部とつなぐ）のハイブリッドにする。形は「共通の仕組み ＋ 業務パック」：仕組み（採用・オンボーディング・記憶・提案と承認・等級・給与・日報）はどの会社でも同じにし、仕事の中身を業務パックとして足す
  - 役割（部門）の中身は一般の営業の仕事で書き、当社の事業に固有の中身は「AX 移行パック」に分ける（#1115）
- **まだ決まっていないこと**（#1114 に残す。ここに書いた方針を理由に、決まったものとして実装しない）:
  - 実行の基盤（Messages API と自前のループか、Claude Managed Agents か）とモデル
  - レベルを任される範囲に結び付けるか、昇格を社長の承認にするか、等級の数と呼び名
  - オンボーディングで読ませる資料の範囲、既存の毎朝の処理との関係
  - 給与（AI社員ごとの費用）を利用組織にどう見せるか、料金に結び付けるか
  - 外部につなぐパックに進む条件
- **理由**:
  - 役割の説明そのものに当社固有の仕事（診断の回答から移行の論点を整理する、動くべき時期を計算し直す）が書かれていると、ほかの会社が自分の会社の部門として受け取れない
  - 仕組みと仕事を分けておけば、A から始めて、作り直さずに B（外部につなぐパック）へ広げられる
- **却下案**:
  - A だけ（このアプリの利用企業の営業まわりに限る）：早く出せるが、対象が広がらない
  - B だけ（独立した製品として外部とつなぐ）：連携・権限・サポートの範囲が一度に広がる
- **ルール**:
  - 仕事はカタログ（`lib/features/ai-employees/types/works.ts`）で決める。仕事ごとに、担当する役割・業務パック・仕事を載せる Issue を持つ。「役割に働ける仕事があるか」（`roleHasWork`）は、その役割の仕事が1つでも動くかで決める
  - 業務パックは2つ：`sales_management`（営業管理。どの会社の営業にもある仕事で、このアプリのリード・商談を扱う）と `ax_migration`（AX 移行。当社の事業に固有の仕事）。当社固有の仕事を `sales_management` に置かない（テストで固定している）
  - 役割の説明（`locales/*/aiOffice.json` の `aiOffice.roles.<role>.description`）は、一般の営業の仕事の言葉で書く。移行・診断・動くべき時期など当社の事業の言葉は、仕事（`aiOffice.works`）と業務パック（`aiOffice.packs`）の側に書く（テストで固定している）
  - 2つ目の外部につなぐパックができるまで、パックを差し替える汎用の仕組みは作らない。境界の決まりだけを守る：AI社員の仕組みの側から `leads` などの機能を直接読まない。道具はパックの側に置く
  - 業務パックを組織ごとに有効・無効にする設定は、仕事を載せるときに決める（今はどの仕事も準備中で動かない）
  - 外部につなぐ道具は「読む・下書き」までを基本にし、外への送信は人の承認を通す。連携先の認証情報はエージェントに見せず、記憶にも書かせない
  - 決定 `2026-11-12-ai-employees-office` の一部を変更：役割の定義の `workIssue` をやめ、仕事のカタログの `issue` に移した。「1回で終わるまとめ処理なので `flow_runs` に載せない」は、エージェントが複数の手順になるときに #1114 で決め直す
