### [DevOps] 公開は Vercel（会社チームに同居）＋Supabase（会社 Organization の Pro）で行い、公開後に DiagnoLeads 全体を AWS へ移す（#1305）
- **日付**: 2026-11-20（2026-11-09 の決定を含む）
- **決定（オーナー）**:
  - **公開まで（A プラン、2026-11-09 の決定）**
    - Vercel：個人チーム（Hobby。商用利用不可）から、会社の既存チーム（Pro・会社払い・社内評価済み）へ移管する。同居の条件は、メンバーを今のオーナー2名に限ること、人を増やす必要が出たら DiagnoLeads を別チームへ移すこと、秘密の値は保存後に読めない形式にすること（Pro ではプロジェクト単位で権限を分けられないため）
    - Supabase：会社名義の Organization を新しく作り、Pro にする。PITR（任意の時点に戻す機能）は付けず、相談の申し込みが月10件を超えたら翌月初めに見直す。移行後も、暗号化した控えを週1回、会社の保管場所に置く
    - 移行と同時に会社のサブドメインを付け、公開は会社のドメインで行う
    - Cloudflare への乗せ換えはしない（費用の目的は Supabase の費用だったが、DB を Postgres のまま移しても Supabase の費用は残り、なくすには DB の作り直しが要るため）
  - **公開後（B プラン、2026-11-20 の決定）**：DiagnoLeads 全体（LP・無料Web診断・管理画面・DB）を AWS へ移す。B への移行は「公開後に判断」ではなく決定事項。時期・AWS のアカウント・構成の書き方・実行の基盤は Epic #1305 で決める
- **理由**:
  - 移行デモ（Java）を AWS で動かすため、会社として AWS の環境を持つことになった。Vercel・Supabase・AWS の3つに分かれる契約・評価・運用を、AWS にそろえる
  - 公開を遅らせないため、移行の準備が整っている A で公開し、そのあと B に移る（A の移行は 2026-11-20 時点で未着手で、どちらでも移行は1回要る）
  - LP とデモサイトのつながりはリンクだけ（`AX_SITE_LINKS.demo`）。クラウドを合わせる理由は連携ではない
- **却下案**:
  - 公開前に AWS へまとめる（実行の基盤・本番反映・定期実行・接続元 IP の判定・監視・DB の移し替えの作り直しで、公開が数週間遅れる）
  - 公開後も Vercel＋Supabase を続け、AWS への集約はそのとき判断する（契約・評価・運用が3つに分かれたままになる）
- **ルール**:
  - DiagnoLeads の AWS の構成とデータは、受託案件のリポジトリ・AWS 環境に置かない（受託案件との分離。Vercel の同居の条件と同じ考え方）
  - B への移行の準備は、公開前の A の作業（Vercel の移管・Supabase の会社 Organization・サブドメイン・#128）を止めない
  - Vercel に依存する作り（`vercel.json` の定期実行とヘッダー、`process.env.VERCEL` で接続元 IP を信用する判定）を変えるときは、AWS でも同じ守りになるかを #1305 で確かめる
  - AWS の月額は、公式の料金ページで確かめた数字で比べる
