### [UI] 営業フロアを出社の画面の部屋にする。部屋は共通の型と登録表を通し、商談ファイルは同じ種類の答えだけを閉じる（#1171・#1142・#1205）
- **日付**: 2026-11-14
- **きっかけ**: オーナーの指示「AI社員オフィスに適したセールス機能をリファクタリングお願いします」。決定 `2026-11-14-concept-and-flow` の4「次に中身を作る場所は営業フロア」に沿って、#1171 として進めた（PR #1207）。レビューの残りは #1205
- **決定**:
  - **営業フロア（鍵3）は部屋**。壁のボードは開いている商談（見極め・課題の確認・提案・条件の調整）。既存の `deals.board` をそのまま読み、API は足さない（決定 `2026-11-13-office-is-the-base`）。見方は4つ：今週中に動かすもの（最初に開く）・次の行動が決まっていないもの・自分の担当・全部
  - **「今週中に動かす」**：次の行動の期限か受注予定日の早いほうが、今週の日曜まで（過ぎたものを含む）。日付の早い順に並べる。受注予定日が理由で出た行には、その日付を出す。範囲を「今日から7日」にするかは、オーナーに確かめている（#1205）
  - **商談ファイルのキー**（`DEAL_KEYS`）：1 次の段へ進める・2 前の段へ戻す・3 次の行動を済みにする・4 次の行動を決める（入力欄が開く）・Z いまのを取り消す・Esc ボードに戻る
  - **受注・失注は部屋の中で扱わない**。日付・金額・理由の入力が要るので、商談のページへのリンクにする。売上予測・顧客探し・商談の作成も、通常の表示へのリンク
- **部屋の型と登録表**（#1142 の「1. 部屋の型」。4部屋とも通している）:
  - 部屋の props は `OfficeRoomProps`（`office-room-contract.ts`）：`organizationId`・`guide`（部屋の AI社員。役割の無い部屋は `null`）・`keysRef`・`onLeaveOffice`・`onFileOpenChange`
  - 入れ物（`office-immersive.tsx`）は、部屋の部品を登録表（`office-room-registry.tsx` の `ROOM_VIEWS`）から取る。入れ物に部屋ごとの出し分けを書かない
  - 型より前に作った部屋（マーケティング室・開発室・総務・受付）は、登録表の中の薄い包みで、今の props の名前に渡し直している。部屋の props を変えたら、その行も直す
  - キーの受け渡しは `useRoomKeys(keysRef, handler)`（`use-room-keys.ts`）
- **商談ファイルで決めたこと**（決定 `2026-11-13-office-is-the-base` の「選択肢で実行するときの決まり」に足す。`ui-ux-specialist` と `architecture-specialist` の読み取り専用のレビュー、2026-11-14）:
  - **答えたあとに閉じるのは、同じ種類の答えだけ**（`dealActionOpen`）。段を動かしたあとは 1・2、済みにしたあとは 3 を閉じる。決めた直後の次の行動も、3 では済みにならない。ほかの答えは続けてできる（済みにする → 次を決める → 段を進める、を1回で済ませる）。顧客ファイルは答えが1種類なので「記録のあとは全部閉じる」のままでよい
    - 理由：はじめは顧客ファイルと同じに「1つ答えたら全部閉じる」にしたが、取り消しの無い答え（決めた次の行動・引き継ぎ書が出た移動）のあとが行き止まりになった
  - **Z は直前の答えだけを取り消す**。次の答えをすると、前の答えの取り消しは無くなる
  - **保存している間は、Esc と「ボードに戻る」を閉じる**。閉じると、結果（引き継ぎ書を送った・失敗した）が読まれないまま実行される。欄が開いていないときも同じにする
  - **段の移動の決まりは、通常の表示（`use-stage-move.tsx`）と同じ**：見極めから進めるときは SQL判定を先に聞く（決定 `2026-10-26-sql-before-leaving-qualification`）。取り消しは段と確度を戻し、SQL判定は戻さない。取り消せるかは `moveIsUndoable`（`lib/features/deals/types/pipeline.ts`）の1か所で決め、両方の画面から呼ぶ（決定 `2026-10-26-deal-move-undo`。戻せない副作用を足すときは、ここに足す）
  - **SQL判定の質問は、選択肢の場所に開く**。数字のキーでは答えにならない（「適格」はボタン、「不適格」は失注の理由が要るので商談のページへのリンク、Esc で選択肢に戻る）。フォーカスは質問の全体に置く。選択肢の文に「（先に SQL判定）」と出して、先に知らせる
  - **「次の行動を決める」は入力して保存するもの**で、Z の取り消しは付けない（会話の「名前の変更」と同じ）。件名と期限は必須で、足りないまま送ろうとしたら、足りないと伝える。期限の「明日」「3日後」「来週の月曜」は欄の中のボタンで、数字のキーは付けない
  - **ボードから消えた商談**（削除された・ほかで閉じられた）のファイルは、開いたときの写しを見せ、実行の選択肢を出さない。理由は「権限がない」ではなく「いまのボードにない」と書く（`gone`）
- **ボードが切られたとき**（`deals.board` は 500 件まで。開発室のボードも同じ決まりにそろえた）:
  - 段ごとの件数と金額は、API が全件を数えているので、そのまま言う
  - 並んだ商談から数える件数（今週中に動かす・次の行動が無い）は、切られているときは言わず、通常の表示へ案内する（`reportTruncated`）。判定は、報告の元のボードの `truncated` で行う
- **却下案**:
  - `useStageMove` をそのまま部屋で使う：結果をトーストで出し、質問を Dialog で出すので、出社の画面の後ろに隠れる。決まりだけを同じにして、部屋の中の文と選択肢で出す
  - 受注・失注も部屋の中の欄で入力する：入力する項目が多く、最初の PR の範囲を超える
  - 切られたときに「少なくとも N 件」と言う：数字が小さく出る理由を毎回説明することになる
- **ルール**:
  - 部屋を足すときは、`office-rooms.ts`（一覧・役割・鍵）と登録表の1行、部屋のファイル、文言だけを触る。入れ物に出し分けを足さない
  - 役割の無い部屋（社長のデスク）を足すときは、`ROOM_ROLES` を役割なしも表せる形にし、席と案内の AI社員を `office-rooms.ts` の純粋な関数に出す（入れ物の3か所が `ROOM_ROLES[room]` を前提にしている。#1205）
  - 部屋のファイルで答えが複数の種類あるときは、「同じ種類だけを閉じる・Z は直前だけ・保存中は Esc を閉じる」にそろえる
  - ブラウザでは確かめていない（クラウドのセッションに DB の接続が無い）。画面の高さ（768px で 8 行が入るか）は #1205 に残している。1ページの行数（`DEAL_BOARD_PAGE_SIZE`）は、確かめてから変える
