### [UI] 営業フロアを出社の画面の部屋にする。部屋は共通の型と登録表を通し、商談ファイルは答えた種類を閉じる（#1171・#1142・#1205）
- **日付**: 2026-11-14
- **きっかけ**: オーナーの指示「AI社員オフィスに適したセールス機能をリファクタリングお願いします」。決定 `2026-11-14-concept-and-flow` の4「次に中身を作る場所は営業フロア」に沿って、#1171 として進めた（PR #1207）。レビューの残りは #1205
- **決定**:
  - **営業フロア（鍵3）は部屋**。壁のボードは開いている商談（見極め・課題の確認・提案・条件の調整）。既存の `deals.board` をそのまま読み、API は足さない（決定 `2026-11-13-office-is-the-base`）。見方は4つ：今週中に動かすもの（最初に開く）・次の行動が決まっていないもの・自分の担当・全部
  - **「1週間以内に動かす」**（最初の見方）：次の行動の期限か受注予定日の早いほうが、今日から7日後まで（過ぎたものを含む。`moveHorizon`）。日付の早い順で、同じ日は金額の大きい順。受注予定日が近い行には、その日付を出す
    - はじめは「今週の日曜まで」だった。2026-11-15 に変えた（`sales-strategy-specialist` の読み取り専用のレビューの推奨。オーナーには3回尋ねて返事が無く、推奨に沿った。2026-11-17 にオーナーに尋ね、今の形のまま進めることになった）。理由：月曜は7日先まで見えるのに日曜は当日だけになり、週の後半に来週の頭の準備を見落とす。「来週の月曜」のボタンで決めた次の行動が、最初の見方からすぐ消える
    - 報告は、期限を過ぎたもの（`isOverdue`）と、まだ先のもの（1週間以内）を分けて数える。範囲に下限が無いので、分けないと、期限切れが溜まるほど「動かすもの」の件数がふくらみ、最初に手を打つものが分からなくなる
  - **商談ファイルのキー**（`DEAL_KEYS`）：1 次の段へ進める・2 前の段へ戻す・3 次の行動を済みにする・4 次の行動を決める（入力欄が開く）・5 連絡を記録する（場所が開く）・Z いまのを取り消す・Esc ボードに戻る
  - **受注・失注は部屋の中で扱わない**。日付・金額・理由の入力が要るので、商談のページへのリンクにする。売上予測・顧客探し・商談の作成も、通常の表示へのリンク
- **部屋の型と登録表**（#1142 の「1. 部屋の型」。4部屋とも通している）:
  - 部屋の props は `OfficeRoomProps`（`office-room-contract.ts`）：`organizationId`・`guide`（部屋の AI社員。役割の無い部屋は `null`）・`keysRef`・`onLeaveOffice`・`onFileOpenChange`・`onBusyChange`
  - 入れ物（`office-immersive.tsx`）は、部屋の部品を登録表（`office-room-registry.tsx` の `ROOM_VIEWS`）から取る。入れ物に部屋ごとの出し分けを書かない
  - 型より前に作った部屋（マーケティング室・開発室・総務・受付）は、登録表の中の薄い包みで、今の props の名前に渡し直している。部屋の props を変えたら、その行も直す
  - キーの受け渡しは `useRoomKeys(keysRef, handler)`（`use-room-keys.ts`）
- **商談ファイルで決めたこと**（決定 `2026-11-13-office-is-the-base` の「選択肢で実行するときの決まり」に足す。`ui-ux-specialist` と `architecture-specialist` の読み取り専用のレビュー、2026-11-14）:
  - **答えた種類は、ファイルを開いている間、閉じる**（`dealActionOpen` の `closed`）。段を動かしたら 1・2、済みにしたら 3（次の行動を決めたあとも 3）を閉じる。ほかの種類の答えは続けてできる（済みにする → 次を決める → 段を進める、を1回で済ませる）。取り消すと、その種類がまた開く。顧客ファイルは答えが1種類なので「記録のあとは全部閉じる」のままでよい
    - 経緯：はじめは「1つ答えたら全部閉じる」（取り消しの無い答えのあとが行き止まりになった）→「直前の答えの種類だけ閉じる」（1→3→1 と押すと2段進み、3→1→3 と押すと見ていない次の行動が済みになった。`ui-ux-specialist` の2回目のレビュー、2026-11-15）→ 今の形
    - 3 の選択肢には、済みにする次の行動の件名を出す（どの件かが分かるように）
    - 新しい答えが失敗しても、前の答えはそのまま残す（取り消しも、閉じた種類も）。失敗で前の答えを捨てると、閉じたはずの種類がまた開く
    - 理由：はじめは顧客ファイルと同じに「1つ答えたら全部閉じる」にしたが、取り消しの無い答え（決めた次の行動・引き継ぎ書が出た移動）のあとが行き止まりになった
  - **Z は直前の答えだけを取り消す**。次の答えをすると、前の答えの取り消しは無くなる。閉じられた商談（受注・失注）には、取り消しも効かせない（取り消しが、受注を開いた段に戻してしまう）
  - **保存している間は、Esc と「ボードに戻る」を閉じる**。閉じると、結果（引き継ぎ書を送った・失敗した）が読まれないまま実行される。欄が開いていないときも同じにする。通常の表示へのリンクも閉じ、報告の文で「保存しています」と伝える。次の行動の保存は、ボードの読み直しが終わるまでを保存中とする（読み直しの前に 3 が開くと、見ていない次の行動が済みになる）
    - 出社の画面の右上の「フロアへ戻る」も、保存中は閉じる。部屋が `onBusyChange` で保存中を入れ物に知らせ、入れ物がボタンを `aria-disabled` にする（Esc は部屋のキーが先に受けるので、マウスで押せるこのボタンだけが抜けていた）。知らせない部屋は、止められない：ファイルで保存する部屋は、`onBusyChange` を呼ぶ
  - **段の移動の決まりは、通常の表示（`use-stage-move.tsx`）と同じ**：見極めから進めるときは SQL判定を先に聞く（決定 `2026-10-26-sql-before-leaving-qualification`）。取り消しは段と確度を戻し、SQL判定は戻さない。取り消せるかは `moveIsUndoable`（`lib/features/deals/types/pipeline.ts`）の1か所で決め、両方の画面から呼ぶ（決定 `2026-10-26-deal-move-undo`。戻せない副作用を足すときは、ここに足す）
  - **見極めから進めるときは、必ず先に確かめる**。見込み客を見極めから初めて進めると、技術担当に引き継ぎ書が送られ、取り消せない。取り消せないものは押す前に伝える（会話の解雇と同じ考え方）。SQL判定がまだなら SQL判定の質問に、済んでいるなら「進める前の確認」に、その文を出す。初めてかどうかはボードの答えからは分からないので、見極めから進めるときはいつも出す
  - **通信が切れているときは、待たずに失敗させる**（オーナーの判断、2026-11-17。#1251 の案 (a)）：商談ファイルの保存（段の移動・済み・次の行動・連絡の記録と取り消し）と、ボードの読み込みに `networkMode: 'always'` を付ける。既定のままだと、通信が切れている間、保存は送られずに待ち続け、保存中は出口を閉じているので、部屋から出られなくなる。失敗の文に「通信が切れていないかを確かめて」と書く。通信が戻っても自動では送り直さない（もう一度答える）。ボードの読み込みにも付けるのは、答えの保存がボードの読み直しまでを待つため。却下案：(b) 待っていると伝えて出口を開ける（出たあとに保存が実行されても結果を見られない。開発室と形が分かれる）
    - 商談の更新は `useDealMutations({ failOffline: true })` で渡す。通常の表示は、今までどおり（通信が戻るまで待つ）
    - 送った要求に応答が来ないまま固まる場合は別の話で、#1254（要求に時間の上限を付ける）が扱う
  - **見極めから進める前の確認に、引き継ぎ書の未入力の項目を並べる**（オーナーの判断、2026-11-17：知らせるだけで、止めない）：対象システム・金額・受注予定日（`missingHandoffFacts`）。通常の表示は止めていないので、部屋だけ止めると決まりが2つになる。並べる項目は、技術部門に確かめて直す（#1237）
  - **SQL判定の質問は、選択肢の場所に開く**。数字のキーでは答えにならない（「適格」はボタン、「不適格」は失注の理由が要るので商談のページへのリンク、Esc で選択肢に戻る）。フォーカスは質問の全体に置く。選択肢の文に「（先に SQL判定）」と出して、先に知らせる
  - **「連絡を記録する」（5）**：何をしたか（電話した・メールした・訪問した・オンラインで商談した・つながらなかった）を、その商談の連絡として残す（`leadFollowUp.recordContact` に `dealId` を付ける。API は足さない。2026-11-15、`sales-strategy-specialist` の指摘：次の行動を済みにするだけでは、何をして相手がどう答えたかが残らない）。5 は場所を開くだけで、記録は種類のボタンで行う（数字のキーでは記録にならない。フォーカスは場所の全体に置く）。メモは任意で、種類を押す前に入れる。記録は Z で取り消せる。済みにすることとは別の答えにした（済みにするたびに聞くと、記録しない人の手が増える）。日時・所要時間・結果を付ける記録は、通常の表示に残す
  - **「次の行動を決める」は入力して保存するもの**で、Z の取り消しは付けない（会話の「名前の変更」と同じ）。件名と期限は必須で、足りないまま送ろうとしたら、足りないと伝える。期限の「明日」「3日後」「来週の月曜」は欄の中のボタンで、数字のキーは付けない。決めても、いまの次の行動は済みにするまで残る（画面に出るのは期限のいちばん早い1件）ので、欄の頭にそう書く
  - **ボードから消えた商談**（削除された・ほかで閉じられた）のファイルは、開いたときの写しを見せ、実行の選択肢を出さない。今日ほかで受注・失注になった商談も同じに扱う（ボードの閉じた段の列には載っているが、開いた段からだけ探す）。理由は「権限がない」ではなく「いまのボードにない」と書く（`gone`）
- **ボードが切られたとき**（`deals.board` は 500 件まで。開発室のボードも同じ決まりにそろえた）:
  - 段ごとの件数と金額は、API が全件を数えているので、そのまま言う
  - 報告の金額は、合計と、確度を掛けた見込みの両方を言う（オーナーの判断、2026-11-17）。合計だけだと、見極め（確度 10%）の商談も満額で入り、見込みを大きく読む。どちらも API が全件を数えた段ごとの値（`amount`・`weightedAmount`）なので、切られていても言える
  - 並んだ商談から数える件数（期限を過ぎたもの・1週間以内に動かす・次の行動が無い）は、切られているときは言わず、通常の表示へ案内する（`reportTruncated`）。判定は、報告の元のボードの `truncated` で行う
- **却下案**:
  - `useStageMove` をそのまま部屋で使う：結果をトーストで出し、質問を Dialog で出すので、出社の画面の後ろに隠れる。決まりだけを同じにして、部屋の中の文と選択肢で出す
  - 受注・失注も部屋の中の欄で入力する：入力する項目が多く、最初の PR の範囲を超える
  - 切られたときに「少なくとも N 件」と言う：数字が小さく出る理由を毎回説明することになる
- **ルール**:
  - 部屋を足すときは、`office-rooms.ts`（一覧・役割・鍵）と登録表の1行、部屋のファイル、文言だけを触る。入れ物に出し分けを足さない
  - 役割の無い部屋（社長のデスク）を足すときは、`ROOM_ROLES` を役割なしも表せる形にし、席と案内の AI社員を `office-rooms.ts` の純粋な関数に出す（入れ物の3か所が `ROOM_ROLES[room]` を前提にしている。#1205）
  - 部屋のファイルで答えが複数の種類あるときは、「答えた種類を開いている間閉じる・Z は直前だけ・保存中は外へ出る道をすべて閉じて、そう伝える」にそろえる
  - ボードの1ページは6行（`DEAL_BOARD_PAGE_SIZE`）。ブラウザで測って決めた（2026-11-14、#1205）：高さ 768px の画面で、次の行動と受注予定日の両方を持つ行は3行になり、8行は入らなかった（7行目が切れた）。6行は収まる。高さ 720px では、頭と足が折れて入りきらず、ボードの中でスクロールになる。行の中身を足す・頭や足に段を足すときは、768px で測り直す
  - 測り方：DB の接続が無い環境でも、部品だけを仮のデータで描画すれば測れる（`learnings.md` の「[UI] DB の接続が無い環境でも、出社の画面の部屋は仮のデータで描画して確かめられる」）
