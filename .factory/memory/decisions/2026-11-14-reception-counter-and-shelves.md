### [UX] 総務・受付を、バックオフィスの仕事の部屋にする。窓口で数字を報告し、棚（期限・メンバーと招待・設定の扉）を選ぶ（Epic #1195）
- **日付**: 2026-11-14
- **きっかけ**: オーナーの指示「AI社員オフィスに適したバックオフィス機能をリファクタリングお願いします」。範囲を4つの選択肢で確かめ、オーナーが「部屋の中身を広げる」を選んだ（ほかは：コードの整理だけ／AIバックオフィスの仕事を作る／通常の表示も含めて全体）
- **決定**（オーナーの判断）:
  - 総務・受付（鍵 5）は、期限を渡すだけの部屋から、バックオフィスの仕事の部屋にする。期限を1件ずつ渡す形（#1133）は、棚の1つとして残す
  - 決定 `2026-11-14-concept-and-flow` の1「総務・受付は…今の形のまま」は、これで一部変わる（期限の渡し方は同じ。入ってすぐは窓口になり、棚が増える）。社長のデスクとの分け方（デスクは「今日」の全体）は変えない
- **形**（#1196）:
  - **窓口**：AIバックオフィスが、自分の期限が今日までの次の行動の件数（うち過ぎた件数）・メンバーの人数・招待中の件数を、記録されている値で伝える。選択肢は 1 期限・2 メンバーと招待・3 設定（`SHELF_KEYS`）
  - **棚**：期限（今までの部屋をそのまま）／メンバーと招待（読むだけ）／設定（通常の表示のページへの扉。`SETTINGS_DOORS` の決まったパスだけ。並びはサイドメニューの総務・受付と同じ）
  - Esc は1段ずつ：棚 → 窓口 → フロア
- **ルール**:
  - 窓口の数字のキーは棚を「開く」だけで、何も実行しない。だから同じ数字を、開いた棚の実行（期限の棚の 1 済みにする・2 次の件へ）に使える。棚の中でのキーの意味は、今までどおり場面の状態で変えない
  - 読めなかった数字と、見る権限が無い数字は言わない（招待は管理者とオーナーだけ。API の答えが FORBIDDEN なら、件数も一覧も出さない）。上限（200件）を超えて全部を読めていないときは、過ぎた件数を言わない
  - 窓口と棚は同じ問い合わせを使う（窓口で伝えた数字と、棚で見える中身が合う）。部屋のために API を足さない
  - 棚が開いている間は、見出しの「Esc フロアへ戻る」の Esc の印を出さない（顧客ファイルと同じ `onFileOpenChange`）
  - 棚を開いた・閉じたあとのフォーカスは報告の文に置く
- **棚の中の操作**（#1197。オーナーの判断、2026-11-14。4つの選択肢から選んでもらった）:
  - 棚でできる操作は、**招待中の取り消しだけ**。招待を送る・役割の変更・メンバーの削除は、通常の表示のメンバーの画面に残す（棚の扉から開く）
  - 理由：出社の画面は、キーだけで操作に届く（決定 `2026-11-14-office-entry-same-site-only`）。解雇は「相手が知らない名前」を打たせるので守りになるが、招待は打つメールアドレスそのものを相手が選べるので、同じ守りが効かない。外の人が組織に入ると、リードの個人情報を読める。解雇より重いので、出社の画面には入れない
  - 却下：最後の送信をクリックだけにする（キーだけで操作する人は通常の表示で招待することになる）／棚からは「メンバー」の役割だけ招待できる（外の人が入る筋道は残る）／解雇と同じ扱いで受け入れる
  - 取り消しの形：メンバーと招待の棚の 1（`REVOKE_KEY`）は欄を開くだけ。招待中の相手のメールアドレスを入力するまで、実行のボタンを閉じる（`invitationNamed`。全角と半角・大文字と小文字・前後の空白は問わない。アドレスの全体が合うこと）。権限が無い人（招待が見えない人）には選択肢を出さず、招待中が無いときは閉じる
  - 欄が開いている間、棚のキーは Esc のほかを使わない（打った文字になる）。Esc は欄を閉じて棚へ戻る。保存している間は、Esc と「棚に戻る」を閉じる（要求はもう出ている。会話の人事と同じ）
  - 失敗は、サーバーの文ではなくコードで言い分ける（NOT_FOUND は「もう取り消されているか、承認されています」）。終わったら招待の一覧を読み直す（窓口の数字も同じ問い合わせ）
  - 入力欄は標準の検証を止める（`noValidate`）。標準の検証は、何も読み上げずに送信だけを止める。種類は `type="text"` と `inputMode="email"` にする（メールの欄にすると、ブラウザが覚えているアドレスを候補に出すことがあり、矢印と Enter で入力できてしまう）
  - **守れないこと**（`security-specialist` のレビュー。コードから組み立てた筋道で、打鍵は試していない）：招待中のアドレスを知っていて、出社の画面に届く打鍵を決められる相手は、5 → 2 → 1 → アドレス → Enter で取り消しに届く。解雇の「守れないこと」と同じ型。消えるのは招待1件で、送り直せる（解雇より軽い）ので、今の形のままにする
  - 出社の画面に、招待の送信・役割の変更・メンバーの削除を足したくなったら、この決定と `2026-11-14-office-entry-same-site-only` に照らして、先にオーナーに確かめる
- **UI/UX のレビューで直したこと**（#1226、2026-11-14。`ui-ux-specialist` の読み取り専用のレビューと、手元の DB での目視）:
  - 窓口の 1（期限の棚を開く）と、期限の棚の 1（済みにする）が同じキーなので、5 → 1 → 1 と続けて押すと、1件目が見ないまま済みになった。期限の棚は、開いてから `DUE_ARM_MS`（0.4秒）の間「済みにする」を閉じる。窓口の鍵は変えない（却下：窓口の鍵を文字にする。フロアの数字と並びがそろわなくなる）
  - 開いている棚の名前を、左の案内の先頭に出す（`ShelfName`）。数字の意味がフロア・窓口・棚の3段で変わるため
  - 設定の扉は1列に並べる（2列だと、下キーが右隣へ動く）
  - 窓口の報告は、3つの問い合わせが決まってから1回で言う（決まった順に文が伸びると、そのたびに読み直される）
  - 「招待中」の件数は有効期限が切れたものを除く。棚の一覧は切れたものも並べ、見出しを「送った招待（有効期限切れを含む）」にする。招待の「期限切れ」は「有効期限切れ」と書く（次の行動の「期限を過ぎています」と別のものなので）
  - 手元の DB での確かめ方：この環境には PostgreSQL 16 が入っている。`pg_ctlcluster 16 main start` で起動し、`apt-get update` のあと `postgresql-16-pgvector` を入れ、空の DB に `db:migrate` と `test:e2e:seed` を流すと、E2E の利用者で出社の画面を開ける（`DATABASE_URL` は必ず手元の DB に上書きする）
- **レビューの残りを直したこと**（#1236、2026-11-15）:
  - 「済みにする」を閉じる 0.4 秒は、1件目が出たときから数える（読み込みが遅いと、棚が開いたときから数えた 0.4 秒は、見る前に過ぎる）。コードは PR #1231 で直し、#1236 では読み込みが遅いときのテストを足した
  - 開いている棚の名前は、フォーカスの移る報告の文の中に置く（外に置くと読み上げられない）
  - 窓口と棚の報告は、メンバーや招待を読めなかったとき、黙って省かずに「読めませんでした」と言う。数字が1つも無いときだけ言う（読み直しに失敗しても前の数字は残るので、数字と「読めませんでした」を同時に言わない）。メンバーを読めないときは、招待については言わない（棚もメンバーを読めないと招待を出さない）
  - 手元の DB で表示して確かめた（2D と 3D・幅 1440px と 800px・高さ 900px と 680px）：窓口、期限の棚（5 → 1 → 1 で済みにならず、待ってから 1 で済み、Z で取り消し）、メンバーと招待の棚と取り消しの欄、設定の棚。昼の表示と読み上げは確かめていない
  - 保存している間（期限を済みにする・招待の取り消し）は、棚から窓口へも、部屋からフロアへも戻れない（Esc・「窓口へ戻る」・右上の「フロアへ戻る」を閉じる）。部屋の型の `onBusyChange`（決定 `2026-11-14-sales-floor-room`）で入れ物に知らせる。保存中かどうかは窓口（`OfficeRoomReception`）が棚から受け取って1か所で持つ
  - 操作（済みにする・取り消す・欄を閉じる）のあとのフォーカスは、結果の文だけに置く（報告の領域の全体に置くと、そのたびに棚の名前から読み直される）。棚を開いたときは、棚の名前を含む領域に置く
  - 「今日までの期限」で言葉をそろえた：窓口のボードの見出し・窓口の選択肢（今日までの期限を受け取る）・期限の棚の見出し（過ぎた件も入るので「今日の期限」とは書かない）
  - 昼の表示（時計を 12:00 にして確かめた）：フロアは昼の明るさになり、部屋の案内とボードは暗い面のままで読める
- **通信が切れたときの保存**（#1251、2026-11-17。オーナーの判断は案 (a)「すぐ失敗させる」。営業フロア・開発室と同じ）:
  - 期限を済みにする・取り消す（`leadFollowUp.updateTask`）と、招待の取り消し（`members.revokeInvitation`）の mutation に `networkMode: 'always'` を付ける。既定（`online`）では、通信が切れている間は送らずに待ち続け、保存中は戻る道を閉じているので、部屋から出られなくなる
  - 総務・受付の保存は、成功のあとの読み直し（`invalidate`）を待たない（`void` で投げるだけ）ので、読み込みの `useQuery` には付けない。読み込みが通信待ちで止まっても「読んでいます」が続くだけで、戻る道は閉じない
  - 失敗の文に「通信が切れていないかを確かめて」を足す（営業フロアと同じ言い方）
  - 通信はつながっているが応答が返らない場合は、この直しでは防げない（#1254 で、tRPC の要求に時間の上限を付ける）
  - 本物のライブラリ（`@tanstack/query-core`）で確かめた：通信が切れているとき、既定では保存が `isPending`・`isPaused` のまま待ち、`always` では再試行1回（`app/providers.tsx`、1秒）のあとに失敗する。再試行を待つ間にタブを離れると、戻るまで保存中が続く（ライブラリがフォーカスも見るため。戻れば失敗する）
- **読み込みと保存中の文**（#1300、2026-11-17〜19）:
  - 窓口と棚の読み込み（`leadFollowUp.dueTasks`・`members.list`・`members.listInvitations`）にも `networkMode: 'always'` を付ける（`READ_OFFLINE_FAILS`）。通信が切れて棚を開くと、既定では「読んでいます」のまま理由が出なかった。いまは再試行（2回）のあとに「読めませんでした。通信が切れていないかを確かめて…」と言う
  - 読み直しが通信の失敗で終わっても、前に読めた中身は残して見せ、報告に「最新の内容を読めなかったので、前に読んだ内容をお伝えしています。」と添える（`queryFailure`・`queryStale`）。済みにしたあとの読み直しが失敗して、手に持っている期限の一覧が消えないように
  - サーバーが断った読み直し（FORBIDDEN・UNAUTHORIZED）は、中身があっても失敗として扱い、中身を消す。権限を下げられた人に、前に読んだ招待の一覧を見せ続けない（`ui-ux-specialist` のレビューの指摘）
  - 保存している間は、報告に「保存しています。」（期限の棚）・「取り消しています。」（招待の取り消し）と言う。フォーカスは結果の文に移るので、結果が返るまでの間もそれと分かる
- **却下案**:
  - 窓口を置かず、期限の画面に棚の切り替えを足す：期限の棚は数字を実行に使っている（1 済みにする）。同じ場面で数字を切り替えにも使うと、キーの意味が状態で変わる
  - 期限があるときは窓口を飛ばして期限の棚から始める：入るたびに始まる場所が変わる
- **あとで決めること**:
  - AIバックオフィスの仕事（期限の見張り）を動かす（#1198。今は仕事が動いておらず、採用しても「研修中」）
