### [Process] 学びの評価は PR テンプレートの1行ずつの記録から数え、毎月1日に Actions が見直しの Issue を開く（#1111、2026-11-12-memory-ace-grow-and-refine の一部を変更）
- **日付**: 2026-11-12
- **決定**（オーナー判断。architecture-specialist の読み取り専用のレビューで出た案 B・C と、記述の整合を進める）:
  - 記録：PR テンプレートに「役立った学び／外れた学び」の節を置き、`- 役立った：[分類] 題名` か `- 外れた：[分類] 題名（理由）` を1行ずつ書く。無ければ「なし」のまま
  - 見直しの起動：毎月1日 09:23 JST に `.github/workflows/memory-review.yml` が `memory-review` ラベルの Issue を開く。前の月にマージされた PR の本文から上の行を集め、`learnings.md` の行数・項目数・いちばん長い項目と一緒に書く。前の月の Issue が open のままなら、新しい Issue を作らずにコメントを足す。PR の本文は作者があとから書き換えられるので、集めた行はインラインコードに入れ（メンション・HTML・リンクを効かせない）、300字で切る
  - 数え方：見出しが一致しない行は人が確かめてから数える。「評価」の行にすでにある PR 番号は数えない。評価の数の更新は承認なしで整理の PR に入れてよい（整理そのものはオーナーの承認が要る）
  - フックかテストに移す候補の基準を、「役立った」が3以上から「機械で判定でき、同じ学びへの追記か再発が2回以上」に替える
  - 整理の候補に「有効な決定・CLAUDE.md と合わない」「公開に適さない記述」を加える。まとめる・消す前に参照元を探し、まとめた後に元の項目と1行ずつ突き合わせる。整理の PR の前に、`learnings.md` を変えている open な PR を確かめる
  - 用語を「役立った・外れた」、見出しを `[分類] 題名` にそろえる。原則違反は `violations.md` に書き、`learnings.md` に重ねない。長くなった経緯は PR へのリンクに置き換えてよい（教訓は具体的なまま）
  - 決定 `2026-11-12-memory-ace-grow-and-refine` の `paths` から `.factory/memory/` の2つを外す（フック `post-tool-decisions.ts` は `.factory/memory/` を対象外にしていて、通知されない）
- **理由**:
  - 学びの記録は本人の申告だけで、きっかけは `ship` スキルの中にしかなかった。テンプレートに節があれば、人が書いた PR にも付き、行の形がそろって機械で集められる
  - 月1回の見直しを起こす仕組みがなく、前回の日付を残す場所もなかった（「最終更新」の行は書かない決まり）。Issue にすれば起動が確実になり、前回の見直しも Issue でたどれる
  - フックに移すべきかは「同じ失敗が何回起きたか」で決まる。文章の学びがよく役立っているなら、フックの必要はむしろ低い。決定 `2026-10-24-claude-harness-guards` とも合わせる
  - 整理で学びをまとめたり消したりすると、決定と `violations.md` からの題名での参照が切れる
- **却下案**:
  - 学びに `paths` を付けてフックで通知する（案 E）：分割と索引・テストが要り、1件1ファイルに近づく。2か月回して記録の件数を見てから判断する
  - 集計を専用のスクリプトにする（案 D）：テストを含めて保守が要る。ワークフローの中の `gh api` と `jq` で足りるうちは作らない
- **ルール**:
  - 見直しの手順は `.factory/memory/README.md` の「メンテナンス（月1回）」。Issue のやることを進め、結果（数えた件数・適用した整理・行数）をコメントに書いて閉じる
  - 2か月（2026年12月・2027年1月の見直し）で記録の件数を見て、評価の数の仕組みを続けるか、外すか、案 E を足すかをオーナーが決める
