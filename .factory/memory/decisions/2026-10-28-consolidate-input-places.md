### [Sales] 顧客探し・リード・商談は分けたまま、同じことを入力する場所を1か所に集約する（Epic #856）
- **日付**: 2026-10-28
- **決定**: 運用を難しくしないことを第一にする。3つの機能（顧客探し・リード・商談）は統合せず、同じことを入力・確認する場所を1か所にする。リード・商談・顧客探しの重複の評価（architecture-specialist の読み取り専用のレビュー、2026-10-28）の推奨案を、オーナーが4点とも承認（2026-10-28）
  - **次の行動**：リードのタスク（`lead_tasks`）に一本化する。商談の「次の一手」（`deals.next_step`）の入力欄はやめ、既存の文はメモとして読めるように残す（#853。列を消すのは別の PR）
  - **リード化した顧客探しの行**：経営層向けの集計の段階から外し、「リード化済み N 件」として分けて出す。リード化の後の進み具合はリードと商談で見る（#852）
  - **商談の作成**：初回の打ち合わせが確定したら（打ち合わせの確定・顧客探しの商談日・代行のアポ）、商談（見極め）を自動で作る（#854）
  - **見込みの度合い**：商談の見込みは、商談の確度に一本化する。ヒアリングの A/B/C は確度の初期値に使う（A/B/C と確度の対応は営業に確認する。#855）。商談の前の見込みは、MQL段階のまま（決定 `2026-10-24-mql-level-over-score`）
- **理由**: 評価の結論
  - リードと商談は決定どおり分かれている（決定 `2026-10-24-deals-beside-leads`）。重なる列のうち状態と商談フェーズは、商談から毎回計算する写し（`lib/features/deals/lead-sync.ts`、決定 `2026-10-25-deals-set-lead-stage`）で、統合は要らない
  - 運用の手間になっているのは、同じことを入力・確認する場所が複数あること：次の行動（4か所）、段階（顧客探しはリード化で止まる）、見込みの度合い（A/B/C と確度）、初回商談日（5か所。商談を手で作り忘れると、予測とボードから漏れる）
- **却下案**（統合しないもの。運用がかえって難しくなるため）
  - 顧客探しをリードに統合する：顧客探しは社員全員が話した相手を書く簡単な一覧で、社員が書く行は氏名・連絡先を持たない（会社名・部署・役職・苗字まで。代行のコールの行だけは連絡先を持ち、営業と書いた人にだけ見せる）。リードはメールアドレスが必須（`leads.email`）なので、リードに寄せると、メールアドレスを知らない相手を書けなくなる
  - リードの状態を廃止して商談だけにする：商談は初回の打ち合わせが確定してから作る（決定 `2026-10-25-lead-lifecycle`）ので、その前の新規・再育成を表す場所がなくなる（MQL は MQL段階で表す）。商談を持つリードの状態は商談から計算する写しで、二重に入力する場所ではない
  - 担当を1列にまとめる：顧客探しの営業担当（`prospects.sales_user_id`）・リードの担当（`leads.assignee_user_id`）・商談の担当（`deals.owner_user_id`）は別の列で、1つのリードに商談が複数つく。担当は既定で引き継ぐので、分けたままでも入力は1回で済む（顧客探しからリードにすると営業担当がリードの担当になり、商談の担当の既定はリードの担当）
- **ルール**:
  - 3つの機能の役割と、入力する場所の正本は `docs/PIPELINE_LIFECYCLE.md` の「0. 3つの機能の役割と、入力する場所」に書く。子 Issue（#852〜#855）で順に合わせ、合わせるまでは今の動きが正
  - 新しく次の行動・段階・見込みの度合いを入力する場所を足すときは、正本に入力させ、ほかの場所は正本を読むだけにする
  - 商談を作る入口（打ち合わせの確定・顧客探しの商談日・代行のアポ）は3つとも残し、どの入口から入っても商談は1件にする。入口を足すときは #854 の作成の処理を通す
  - 商談の担当とリードの担当が違うときに、商談の次の行動を誰に出すかは #853 で決める
  - 決定 `2026-10-25-lead-lifecycle` の「顧客探しの段階は、リードに引き継いだ後は更新しない（仮の運用）」から「仮の運用」を外して確定する（リード化した行の段階は、画面と API で変えられない）。加えて、リード化した行は集計の段階から外す（#852）。リードの側から顧客探しの段階へ反映するかは決めない
  - 決定 `2026-10-24-mql-level-over-score` の「ヒアリングの後は商談評価 A/B/C で優先を付ける」を、商談の確度で付けるに変える（A/B/C は確度の初期値。#855）
- **見直しの条件**: 同じリードに開いた商談が並ぶ運用が出たら、次の行動を商談ごとに持つか（`lead_tasks` に商談を指す列を足す）を決める
