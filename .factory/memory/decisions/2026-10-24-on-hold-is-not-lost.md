### [Sales] 「保留」は失注ではない。保留のリードはナーチャリングにする（#445）
- **日付**: 2026-10-24
- **決定**: 失注・保留理由の「保留」（`on_hold`）は、状態が失注のリードには付けられない。保留のリードは状態をナーチャリングにし、理由に「保留」を入れる。営業パイプラインの評価（Epic #430）の推奨案 A を、オーナーが承認
- **理由**: 失注＋保留のリードは、動くべき時期（#151）が追わず（失注は理由が「時期」のときだけ追う）、失注の件数にも入っていた。ナーチャリングなら動くべき時期が追い、時期が来ると担当に次の行動が出る
- **ルール**:
  - 判定は `lib/features/leads/types/pipeline.ts` の1か所（`makesLostOnHold`・`dropsOnHoldReason`・`hasLostReason`）。tRPC の作成・更新・一括の状態変更と REST API v2 の更新が使う
  - 失注に「保留」を明示して書くとき（作成・更新）は拒む。保留のリードを理由なしで失注にしたとき（状態のバッジ・一括・REST API v2）は、理由の「保留」を消して保存し、監査ログに残す。失注理由の入力を促すトーストは「保留」を理由なしとみなすので、続けて本当の理由を聞く（2026-10-24 のレビューで、拒むと保留から失注へ移れなくなるため変更）
  - リードのフォームは理由の欄が見えているので、失注＋保留なら保存前にその欄でエラーを出す（消さない）
  - パイプラインのカードは、ナーチャリングのときも失注・保留理由の欄を出す（保留を記録できるように）。失注のリードでは選択肢から「保留」を外す
  - #445 より前に失注＋保留になったリードは、状態も理由も変えない保存なら通す（名前の修正などで止めない）。ナーチャリングへ移すデータの移行はしない（2026-10-25、本番の件数が 0 件だったため）
  - 商談（#435）の失注理由にも「保留」を使わない。商談でリードが失注になるとき、リードの理由が「保留」なら消すか置き換える（SFA のセッションに共有済み）
- **却下案**: 状態に「保留」を足して6段にする（漏斗・ダッシュボード・代行のファネル・REST API v2・Webhook の値がすべて変わる）
