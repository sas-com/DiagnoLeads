### [Sales] 「保留」は失注ではない。保留のリードはナーチャリングにする（#445）
- **日付**: 2026-10-24
- **決定**: 失注・保留理由の「保留」（`on_hold`）は、状態が失注のリードには付けられない。保留のリードは状態をナーチャリングにし、理由に「保留」を入れる。営業パイプラインの評価（Epic #430）の推奨案 A を、オーナーが承認
- **理由**: 失注＋保留のリードは、動くべき時期（#151）が追わず（失注は理由が「時期」のときだけ追う）、失注の件数にも入っていた。ナーチャリングなら動くべき時期が追い、時期が来ると担当に次の行動が出る
- **ルール**:
  - 判定は `makesLostOnHold`（`lib/features/leads/types/pipeline.ts`）の1か所。tRPC の作成・更新・一括の状態変更と REST API v2 の更新が使う。画面（リードのフォーム・パイプラインのカード）は同じ関数か選択肢の絞り込みで先に止める
  - #445 より前に失注＋保留になったリードは、状態も理由も変えない保存なら通す（名前の修正などで止めない）。ナーチャリングへ移すかは件数を見てから決める
  - 商談（#435）の失注理由にも「保留」を使わない。使うと `lib/features/deals/lead-sync.ts` がその理由をリードへ写し、失注＋保留が生まれる（SFA のセッションに共有済み）
- **却下案**: 状態に「保留」を足して6段にする（漏斗・ダッシュボード・代行のファネル・REST API v2・Webhook の値がすべて変わる）
