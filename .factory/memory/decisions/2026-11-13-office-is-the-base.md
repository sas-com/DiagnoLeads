### [UI] 業務システムの土台は AI社員バーチャルオフィスにする。従来の管理画面（メニュー・ヘッダー・カード）に色を当てる形は求められていない（#1100・#1120）
- **日付**: 2026-11-13
- **決定**（オーナーの訂正。2026-11-13「違いますね。AI社員バーチャルオフィスがベースであり、今まで通りの Web システムチックなものを求めているわけではありません。斬新的かつ画期的な業務システムといいましたよね」）:
  - 土台は AI社員バーチャルオフィス（全画面の出社の画面）。オフィスを「機能の1つ」として管理画面の中に置くのではなく、業務の画面のほうをオフィスの中に置く
  - 従来の管理画面の形（サイドメニュー・ヘッダー・カードの並び）のまま色と飾りを変えることは、求められている方向ではない
  - オフィスの描画は大きくする（同日「もう少しオフィスの描画サイズを大きくするべきではないですか？」）。フロア全体が入る大きさの 1.2 倍からカメラを始める（決定 `2026-11-12-ai-employees-office` に書いた）
- **経緯**: 「全て AI社員オフィスの世界観に統一してください。没入感を上げるための改善お願いします」を、管理画面の色と飾りをオフィスに合わせる作業として進めた（PR #1124）。オーナーが求めていたのは、画面の枠組みそのものをオフィスにすること。「世界観に統一」と言われたら、色ではなく、画面の枠組み（どこに立ち、どう移動し、誰と話して仕事が進むか）から考える
- **進め方の案**（Claude Design のキャンバス「AI社員バーチャルオフィス」の「オフィスが土台 1〜4」。オーナーの確認の前）:
  - ログインするとフロアに立つ。メニューとダッシュボードのページは無い。部屋の札に、その部屋の今の数字が出る
  - 部屋に入ると、その部屋の AI社員の報告（言葉）と、壁のボード（一覧）が出る。マーケティング室＝リード管理・分析、営業フロア＝商談・売上予測・顧客探し、開発室＝ヒアリング・移行の提案、研修室＝営業の手引き・使い方、総務・受付＝設定・メンバー・通知、社長のデスク＝今日
  - リードの詳細は「顧客ファイル」として、部屋の中で開く
  - 仕事は、AI社員への返事（選択肢）と決裁で進む。AI社員は用意するところまでで、送る・変えるは人が決める
  - 移動は、部屋の札・フロア案内・数字のキー・1行の指示（「[会社名] のファイルを開いて」）
- **オーナーの判断**（2026-11-13「この方向で進めてください」）: 上の案の形で進める。1部屋目はマーケティング室（#1127）
- **部屋の作り方**（#1127 で決めた。次の部屋も同じ型にする）:
  - 部屋は出社の画面の場面の1つ（`stage: 'room'`）。カメラはその部屋の AI社員の席に寄り、左に案内、右に壁のボードを置く。部屋の一覧と鍵は `components/features/ai-employees/office-rooms.ts`（鍵の数字は部屋ごとに固定：1 社長のデスク、2 マーケティング室、3 営業フロア、4 開発室、5 総務・受付）
  - ボードは既存の API をそのまま読む（マーケティング室は `leads.list`。絞り込みはリードの一覧のプリセットと同じ `presetFilters`）。部屋のために API を足さない。組織の絞り込みと権限は API が確かめる
  - 案内の文は実際の数字だけから作る。AI社員が研修中・休止中・空席のとき、作業が止まっているとき（`attention`）は、そう書いて数字だけを読み上げる（`roomGuide`）。AI社員がしていない仕事を、したように書かない
  - 「社長（あなた）」の選択肢が、ボードの切り替えを兼ねる（数字のキー）。同じ切り替えを2か所に置かない
  - キー：上下で行、Enter で開く、左右でページ、Esc でフロアへ。ページの端のボタンは `aria-disabled` にする（`disabled` にするとフォーカスが落ち、部屋のキーが効かなくなる）
  - 行を開くと、部屋の中で顧客ファイルが開く（#1128。`office-lead-file.tsx`）。ファイルの中のものが開いている間、Esc はそれを閉じる（部屋の鍵のハンドラが true を返すと、出社の画面は場面を戻さない）
- **計画「探さない業務システム」**（オーナーの指示 2026-11-13「画期的なプランで進めてください」。全体は #1120 のコメント）: 仕事のほうが社長のところへ来る。人が一覧を探して入力するのではなく、AI社員が「決めること」を持ってきて、社長が選択肢で答えると記録と更新がその場で済む。段：1 顧客ファイル（#1128）→ 2 朝の報告（決めることを1件ずつ）→ 3 営業フロア → 4 1行の指示 → 5 AI社員が用意する（#1114）→ 6 入口をオフィスにする
- **1件ずつ渡す部屋の作り方**（#1133。総務・受付の「今日の期限」。朝の報告もこの型にする）:
  - 渡す順番（キュー）は、部屋を開いたときの一覧で固定する。済みにするとサーバーの一覧からは消えるが、手元の順番は動かさない（選択肢の対象が指の下で入れ替わらないように）
  - 済みにした直後は「済みにする」（1）を閉じ、「次の件へ」（2）で進む（`dueActionOpen`）。同じキーを続けて押しても、次の件が見ないまま済みにならない
  - 「あとで」は何も変えずに次へ進む。最後に、済みにした件数と残りの件数を伝える
  - 読むのは自分の分だけ（`leadFollowUp.dueTasks` の `scope: 'mine'`）。上限（200件）を超える分は、件数を伝えて通常の表示へ案内する
  - 部屋ごとの共通の部品は `office-room-parts.tsx`（案内の見出し・枠・選択肢の見た目）
- **選択肢で実行するときの決まり**（#1128 で決めた。朝の報告と営業フロアでも同じにする）:
  - 選択肢は1回の押下で実行する（確認のダイアログを挟まない）。その代わり、必ず取り消しを付ける
  - キーの意味は場面の状態で変えない（2026-11-13、`ui-ux-specialist` のレビューで変更。前は「実行のあとは最初の選択肢を『戻る』にする」で、同じ数字が記録・戻る・取り消しに変わり、読み込みの前後や押しすぎで意図しない操作になった）：
    - 数字は実行だけに使い、同じ数字はいつも同じ実行（顧客ファイル：1 電話した・2 メールした・3 つながらなかった。総務・受付：1 済みにする・2 次の件へ）。一覧は `FILE_KEYS`・`DUE_KEYS`
    - 取り消しは Z、戻るは Esc だけ。数字で戻らない・取り消さない
    - 今は実行できない選択肢は、場所とキーを変えずに `aria-disabled` で閉じる（実行の直後・読み込み中・保存中）。閉じているキーは何もしない（`fileActionOpen`・`dueActionOpen`）。権限が無い人には、実行の選択肢を出さない
    - 取り消しに失敗したら、記録（済み）は手元に残し、もう一度取り消せるようにする
    - 選択肢のボタンは `RoomChoiceButton`（`office-room-parts.tsx`）
  - **会話の人事は別の形**（#1170、2026-11-14）：名前の変更・作業記録・解雇の選択肢は、数字で「開く」だけで、何も実行しない。実行は、選択肢の場所に開いた欄で行う（`office-talk-staff.tsx`）
    - 開いている間、数字のキーは選択肢に届かない（入力する文字になる）。戻るのは Esc だけで、会話ではなく選択肢に戻る
    - 保存している間は、Esc と「選択肢に戻る」を閉じる（`onBusyChange`）。要求はもう出ているので、戻れると「取りやめた」ように見えて実行される（`ui-ux-specialist`・`security-specialist` のレビューの指摘）
    - 欄で実行したあと（Enter で実行する）は、フォーカスを報告の文に置く。「オフィスに戻る」に置くと、Enter をもう1回押しただけで、結果を読む前にフロアへ戻る（`outcome.typed`）。作業記録は、見出しにフォーカスを置く（読み上げが記録の頭から始まり、Enter は何もしない）
    - 開いている欄は1つの値（`matter`）で見る。相手の AI社員がいなくなったら（ほかの管理者が解雇）、欄は閉じ、数字のキーは選択肢に戻る
    - 入力欄は、出社の画面の色に固定する（`office-talk-staff.tsx` の `FIELD`）。共通の `Input` の既定はテーマで色が変わり、出社の画面の「昼夜は時計で決める」と食い違う
    - 名前の変更は入力して保存するもので、Z の取り消しは付けない（もう一度変える）
    - 解雇は取り消せないので、「1回の押下で実行して取り消しを付ける」の例外にする。その AI社員の名前を入力するまで実行のボタンを閉じる（`namesTheEmployee`。全角と半角・空白の数は問わない。大文字と小文字は区別する。決定 `2026-11-14-office-entry-same-site-only` の b）。合わない名前で実行しようとしたら、合っていないと伝える
    - 名前を変えた返事には、前の名前も入れる（打ち間違いで変わっても、戻せる）
    - 作業記録は、記録されたものだけを出す。無いときは無いと出す（していない仕事を見せない）。権限が無い人にも出す（通常の表示と同じ）
    - 選択肢の並びは `talkChoices`：その日の指示（休止・再開）→ 名前を変える → 作業記録 → 解雇 → またあとで。解雇は最初の鍵（1）に置かない
  - 場面が開いたときと、実行のあとのフォーカスは報告の文に置く（Enter の押しすぎで実行されない）
  - Esc は `onEscapeKeyDown` から1回だけ部屋に渡す（`onKeyDown` からも渡すと2回届く）
  - 日本語入力（IME）の変換中のキーは、出社の画面の入口（`onKeyDown`・`onEscapeKeyDown`）でも、部屋のキーの処理の先頭でも除く（`components/ui/ime.ts` の `isImeKey`・`ignoreImeEscape`）。部屋には、変換中かどうかが分かるブラウザのイベントを渡す（`RoomKeyEvent`）。#1129 の検査が、Enter・Esc を見る行の上10行以内にこの確認があることを求める（#1140）
  - 記録は既存の API（`leadFollowUp.recordContact`・`deleteContact`）で行い、その記録を出すほかの画面（リードの詳細・今日・ダッシュボード）のキャッシュを捨てる。結果は部屋の中の文で伝える（トーストは出社の画面の後ろに隠れる）
  - 変える権限は API の答え（`canEdit`）で見て、無い人には実行の選択肢を出さない
- **まだ決まっていないこと**（オーナーに確かめる）:
  - 従来の一覧の画面を残すか（スマホ・読み上げ・狭い画面のための「通常の表示」）。残すなら、どちらを最初に出すか。#1127 の時点では残していて、登録・取り込み・一括の操作は通常の表示で行う
  - 既存の画面の中身（表・フォーム・ダイアログ）を、部屋のボードの中にそのまま入れるか、ボード用に作り直すか
  - PR #1124（管理画面の色を昼と夜にする）の扱い：取り下げるか、「通常の表示」の色として残すか
- **ほかの決定への影響**:
  - `2026-11-13-admin-office-world`（PR #1124 のブランチにある）：「管理画面の見た目をオフィスの世界観にする」は、この決定で前提が変わった。色の決まり（昼と夜・コントラストの数字）は、オフィスの中のボードと「通常の表示」で使える
  - `2026-11-12-ai-employees-office`：オフィスは `/office` の1画面、という前提が変わる。出社の画面が入口になる
