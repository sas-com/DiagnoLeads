### [Architecture] ワークフローの基盤は自前のランナー（A案）にし、PoC はしない（#289）
- **日付**: 2026-10-24
- **決定**（オーナー判断）: 時間をまたぐ自動化（`docs/WORKFLOW_ENGINE_EVALUATION.md` 0章の「システム間の処理連携」）の基盤は、外部のワークフローエンジンを使わず、評価文書7章の A案にする。既存の Postgres に実行の状態を保存し、最初のステップは応答の後（`after()`）にすぐ、続きは既存の日次の定期実行で1ステップずつ進める自前のランナーである（7.1）。6章で提案した Inngest と Vercel Workflows の PoC は行わない。実装は 7.4 の段階1の4つの Issue で進める
  - #298：実行テーブル `flow_runs` とフロー定義の型（F1・F2）
  - #299：開始（`startFlow`）と定期実行での続き・回収（`runDueFlows`）（F4・F9）
  - #300：送信の保証とリトライ（F6・F7）
  - #301：滞留の検知（F13）
- **理由**:
  - 新しい契約先とサーバーが増えない（7.2、7.6）。外部サービスが呼ぶ公開の受け口と、その署名鍵などの秘密も増えない（6章の想定リスク）
  - リードの個人情報を新しい外部サービスに保存しないので、外部のワークフローサービスを採るときの海外保存の判断（6章の想定リスク、9.2 の法務部門）が要らない。情報システム部門への確認も、範囲を既存の契約先（Vercel・Supabase・Resend）に限れる見込み（7.6。確認そのものは要る。#547）
  - 必要なのは「リードの状態変化や診断の回答を起点に、待機を挟んで数個の処理を順に実行する」ことだけで、作る範囲が限られる（7.1。段階1は目安で20ポイント）。4章の54点は、機能をすべて自分で作る前提の点数
  - Webhook の新規配信と再送（`processWebhookRetries`）がすでに同じ型で動いていて、それをなぞれる（7.3、7.6）
  - 子 Issue #298〜#301 は、すでに A案を前提に書かれている
- **却下案**:
  - 4章の上位案を PoC で比べてから選ぶ（4章・6章）。今の利用先は #154 の段階メールが主で（#48 は AI 分析の失敗率を測ってから載せるかを決める。7.4 段階3）、日数単位の待機なら A案で足りる（7.5 ②）
    - Inngest（87点）：起動イベント・ステップの入出力・エラーを外部サービスに保存する（保存先が海外なら、外国にある第三者への提供に当たるかの判断が要る）。外部から呼ばれる公開の受け口（`/api/inngest`）と、イベントキー・署名鍵などの秘密が増える（6章の想定リスク）。月額は従量（5章、7.7）
    - Vercel Workflows（84点）：既存の契約先の中で完結するが、有料プランが前提（7.7）。実行の状態とステップの入出力の保存先が契約先の中に増えるので、保存先の地域・保存期間の確認は同じく要る（6章の想定リスク）
    - Trigger.dev（81点）のクラウド版：タスクが Trigger.dev 側の実行環境で動き、Vercel とは別のデプロイが要る（5章）。ステップの入出力を外部に保存する（6章の想定リスク）
    - Temporal（71点）：常駐のワーカーが要り、Vercel のサーバーレス関数では動かせない。Temporal Cloud でもワーカーの置き場所が別に要る（5章）
    - Upstash Workflow（70点）：運用画面と待ち受けの機能が上位3案より少なく（5章）、ステップの入出力を外部に保存する（6章の想定リスク）
  - Postgres 上のジョブキュー（pg-boss、graphile-worker）や、Inngest・Trigger.dev・Temporal の自前運用（7.2 の B〜E）。常時動き続けるプロセスが要り、Vercel のサーバーレス関数（1回30秒まで）の上では動かせない
- **ルール**:
  - ランナー専用の `flow_runs` を作り、`workflow_executions` には相乗りさせない。`workflow_executions` は段階5まで触らない（7.3）
  - 最初のステップは `after()` で動かし、続きと取りこぼしの回収は既存の `cleanup-webhook-deliveries` の定期実行に相乗りさせる。`notify-due-tasks` には載せず、新しい定期実行も足さない（7.3、7.5 ②）
    - この定期実行では、Webhook の再送（時間予算20秒）・古い配信の削除・サイト訪問の集計（`maintainSiteVisits`、#412、決定 `2026-10-23-site-visit-measurement`）が `Promise.allSettled` で並列に動いている。7.3（10/22）の後にサイト訪問の集計が載ったので、ランナーはこれらと、30秒の `maxDuration`（`vercel.json` の `functions`）と DB の接続を分け合う。ランナーの時間予算は、並列に動くほかの処理と同じ30秒の中に収まるように決める（#299）
  - 置き場所：ランナー本体は `lib/workflow/`（機能モジュールを import せず、フローの定義は引数で受け取る）。フローの定義は各機能に置き、利用者が設定するワークフローは `lib/features/workflows/` に置く（7.8）
    - `lib/workflow/` は古いエンジンを #306 で消したあと、まだファイルがない（`paths` は実在するファイルに当たる必要がある）。#298 で作るときに、この決定の `paths` に `lib/workflow/**` を足す
  - Webhook の再送、`notify-due-tasks`、`after()` だけで足りる処理は、ランナーに載せ替えない（7.8）
    - 例外：`notify-due-tasks` の中で動く「動くべき時期」の再計算（`recomputeRecentlyUpdated`）の続きをランナーに任せるかは、決定 `2026-10-24-act-timing-morning-run` の却下案のとおり、#299 ができた後に決め直す（7.8 は 10/22 に書かれ、その決定が 10/24 に問いを開け直したため）
  - ランナーは最初の利用先（#154 の段階メールが主。#48 は AI 分析の失敗率を測ってから載せるかを決める）と同じ時期に作り、利用先がないまま先に作らない。着手は公開（2026-10-29）の後（7.4、7.5 ⑥、8.1）
  - 利用者が設定するワークフロー（段階5）を動かすときも、別の実行の仕組みを足さず、`flow_key='workflow'` として `flow_runs` に載せる（7.4 段階5 の F5）
  - 分岐の合流・並列実行・ループ・外部イベントの待機は作らない（7.4「対象外」）
- **この決定で決めていないこと**:
  - 「費用ゼロ」を条件にするかと、許容する金額（7.5 ⑦。経理部門・経営企画）。#547 で追う
  - Vercel・Supabase の無料プランのまま本番を運用してよいか（7.5 ①、9.2。法務部門・情報システム部門）と、既存の契約先（Vercel・Supabase・Resend）でのリード情報の扱い（7.6、9.2。情報システム部門）。#547 で追う。Supabase のバックアップは、10/24 のオーナー決定で Free のまま毎日 pg_dump にした（#51）
  - 送信の保証の方針（7.5 ⑤。#300 で決める）と、開始条件・停止条件の初期値（7.5 ④。#154 の段階メールで決める）
- **見直す条件**: 次のどれかに当たったら、4章の上位案（Inngest・Vercel Workflows）を PoC で比べ直す
  - 数分単位の待機が要る利用先が出た（7.5 ②）
  - 処理件数が増えて1回の時間予算に収まらず、#301 の滞留の検知が続けて出る（7.6）。`cleanup-webhook-deliveries` に相乗りするほかの処理が重くなり、ランナーの時間予算を削る必要が出たときも同じ
  - 有料プランにして「費用ゼロ」の前提が変わった（7.5 ①。#547）
  - 分岐・並列実行・外部イベントの待機が要るようになった（7.4「対象外」）
