### [Testing] テストカバレッジ方針
- **日付**: 2026-02-06
- **決定**: 層別カバレッジ目標 + E2E補完
  - Core (lib/features, lib/db, lib/auth): 80%
  - API (server/, app/api/): 70%
  - UI (components/, app/[locale]/): 30-40% (E2Eで補完)
  - E2E: 主要フロー100%
  - 全体目標: 40%+ (E2E含めた実質70%+)
- **理由**: 
  - 品質の一貫性を保つため、カバレッジ対象を恣意的に除外しない
  - UIコンポーネントはE2Eで効果的にカバー可能
  - ビジネスロジック層は高カバレッジを維持
- **却下案**: 
  - 全体70%一律目標（UIテストのコストが高すぎる）
  - カバレッジ対象からUIを除外（品質の一貫性が損なわれる）

### [Naming] テストファイル命名規則（種別別）
- **日付**: 2026-02-07
- **決定**: 
  - `*.test.ts` → Unit tests（外部依存なし、高速）
  - `*.integration.ts` → Integration tests（モック使用、中程度）
  - `*.spec.ts` → E2E tests（実環境、長時間）
- **理由**: 
  - テスト種別による明確な分類
  - CI並列化の容易さ（種別ごとに分離実行可能）
  - 外部依存の有無が明確になる
- **却下案**: 
  - レイヤー別のみの分類（Unit/Integration/E2Eが混在）
  - ディレクトリ分離のみ（ファイル名で判別不可）

### [Architecture] 診断はコードで定義し、点数はサーバー側でだけ計算する
- **日付**: 2026-10-09
- **決定**: AX マイグレーション診断は `lib/features/diagnostics/` に TypeScript で定義する（設問・選択肢・配点・判定ルール）。回答は `diagnostic_submissions` に保存し、作成・更新したリードと紐づける（#55、#46 の方針の具体化）
- **理由**:
  - MQL / SQL 判定や難易度の計算は、配点の合計だけでは表せないルールを含む
  - 判定ロジックを単体テストで固定でき、設問の版（`version`）と結果を一緒に保存できる
  - v1 は点数をクライアントから受け取っていて改ざんできた。その弱点を引き継がない
- **ルール**:
  - お客様に返すのは難易度・緊急度・主な課題・推奨ステップだけ。リードスコア・MQL/SQL 判定は返さない
  - 業務側で「要確認」の基準は `ax-migration/config.ts` に集める
  - 公開フォームは本人確認ができないため、同じメールアドレス（大文字小文字は区別しない）の既存リードは**書き換えない**。回答は既存リードに紐づけて保存し、営業には「本人未確認」として既存の登録名で通知する（2026-10-09 レビュー指摘: 第三者が他人のメールで回答するとリードを改ざんできた）
  - 同じメールの同時送信は (組織, メール) の advisory lock で直列化し、リードの重複を防ぐ
  - Web診断の完了を MQL の「行動」に数える（2026-10-09 オーナー判断）。config で「MQL候補」止まりにも切り替えられる → 2026-10-16 廃止（#139「適合」と「関心あり」）
  - 移行対象は基幹システムに加えて、VB のクライアントサーバー型、Access（部署単位のツールを含む）、WebPerformer（ローコードはまず WebPerformer のみ）。それぞれ別の選択肢・対象システムとして扱う。その他のローコード製品は当面対象外（2026-10-09 オーナー判断）
- **却下案**: Payload の DiagnosticForms に配点を持たせる（判定ルールを表現できず、テストもしにくい）。Payload は今後もブログ・LP など文章コンテンツに使う

### [Domain] AX 診断 v2: 移行元ごとの設問と LP（#62）
- **日付**: 2026-10-11
- **決定**: 最初に移行元（AS/400・NEC ACOS・Access・その他）を選び、移行元ごとに設問を変える。LP `/[locale]/ax-migration` に診断を埋め込む。デザインは同社の maru2-dx.com に合わせる
- **理由**: オーナー指示（移行元ごとに必要な診断内容を聞き、回答者の負担を極力減らす）。専門家レビュー（フォーム UX、Access・AS/400・ACOS 移行、コード、セキュリティ、アクセシビリティ）を反映
- **ルール**:
  - 必須は1経路あたり約10問。数値は範囲で聞き、技術的な設問にはすべて「わからない」を置く。詳しい設問は結果のあとの任意の追加質問（`detail`）にする
  - 刷新の緊急度は「使い続けるリスク」（直せる人・保守期限・サポート終了）で測り、回答者の検討時期は入れない（検討時期はリードスコアにだけ使う）
  - ACOS は NEC が継続を表明しているため、機器契約の区切りの重みを他より小さくする。「ACOS の終了」を理由にした文言は使わない
  - Access（Office）のサポート状況は終了日から計算する。終了日の当日はサポート中とみなす
  - 選択肢を足すときは、点数表（`AX_POINT_TABLES`）に重みを書く（加点しない選択肢も 0 と明記）。テストで漏れを検出する
  - 追加質問は1回だけ、送信から24時間以内。営業が変えたリードスコアは上書きしない
- **却下案**: 検討時期を緊急度に入れる（「1年以内」と答えるほど緊急度が上がる循環になる）。追加質問を必須にする（回答者の負担が増える）

### [Security] 公開フォームの送信対策（#67）
- **日付**: 2026-10-11
- **決定**: 永続的なレート制限（DB の `public_rate_limits`、固定ウィンドウ）と Cloudflare Turnstile（鍵を2つとも設定したときだけ有効。社内検証の間は無効のまま＝オーナー判断）。組織ごとの上限は受付ではなく通知に掛ける
- **理由**: middleware のレート制限はインスタンスごとのメモリで、Vercel では共有されない。通知を `after()` で確実に送るようにした（#65）ので、大量の送信で営業の受信箱とメールの送信枠をあふれさせられる。送信枠はパスワード再設定のメールと共用
- **ルール**:
  - 上限は `lib/features/diagnostics/ax-migration/limits.ts` にまとめる。送信は IP（30件/時）→メールアドレス（6件/時）の順に数え、断った規則より後は数えない。回答の検証は数える前に行う
  - 組織ごとの上限（通知100件/時、営業メール10通/時・30通/日）を超えても送信は保存する。通知だけを止め、超えた最初の1回だけメンバー（アプリ内）と営業（メール1通）に知らせ、相談申込はリード一覧で確認するよう書く（全員を締め出す使い方をさせない）
  - IP ごとの上限は1時間30件と1日100件（両方を数える）
  - IP のヘッダーは Vercel 上でだけ信じる（`process.env.VERCEL`）。それ以外では IP ごとの上限を掛けない。IPv6 は /64 で数える。キーは鍵付きハッシュで、生の値は保存しない
  - Turnstile は action と hostname を照合する。Cloudflare のテスト用の鍵は本番（`VERCEL_ENV=production`）では通さない。失敗は 403、Cloudflare が答えないときは 503（通さない）
  - Turnstile を有効にする前に、プライバシーポリシーに Cloudflare の利用（IP と端末の情報を送ること）を書く
  - **外部に公開する前に Turnstile を必須にする**（専門レビュー）。鍵がないと、多数の IP からの送信で通知の枠（1時間100件）を使い切り、本物の相談申込の通知を止められる。上限は備えであって、主な防御は Turnstile
  - CSP の要点は `test/unit/lib/middleware/csp.test.ts` で固定する。`style` 属性にユーザーの文字列を入れない
- **既知の限界**: 新規リードの作成と既存リードへの紐づけで DB の処理が数ミリ秒違う（応答の中身は同じ。悪用には送信ごとの上限があり、未登録のアドレスはその1回でリードになる）
- **却下案**: Upstash Redis（アカウントと鍵が要る。DB で足りる量）。組織ごとの上限で受付を止める（1つの IP から全員を締め出せる）。Turnstile を必須にする（社内検証の段階では鍵の準備を待たない）

### [Domain] 「別のシステムも診断する」の2件目（#67）
- **日付**: 2026-10-11
- **決定**: 同じ画面から続けて送った2件目以降は、1件目と同じ回答者として扱い、リードの `responses.axMigration.otherSystems` に記録する。「本人未確認」にしない
- **理由**: 2件目も同じメールアドレスなので、既存リードと一致して「本人未確認」で通知されていた（オーナーが「すべて実施」と判断）
- **ルール**:
  - 画面は1件目の送信 ID（`continuedFrom`）を覚えておき、2件目以降に付ける（メモリだけ。保存しない）
  - サーバーは、その送信がこのリードを作ったこと・同じ組織・24時間以内を確かめる。満たさなければ今までどおり「本人未確認」
  - 確かめているのは「リードを作ったブラウザと同じか」で、メールの持ち主かではない。営業向けの文言も「同じ画面から続けて診断された」と書く。送信 ID は相談申込・追加質問の鍵と同じく、通知や Webhook の受け手にも見える（受け手は社内か連携先なので許容）
  - 応答の形は変えない（メールアドレスがリードとして登録済みかを、外から推測させない）
  - 2件目はリードの名前・会社名・スコアを変えない。相談申込は `conversion_point` を相談にし、MQL は未判定のときだけ付ける。2件目の追加質問は、その系の記録だけを更新する
- **却下案**: HMAC の継続トークン（発行の有無で登録済みかが分かってしまう。送信 ID を確かめれば足りる）

### [Security] 新規登録は招待制、招待リンクは48時間（#51・#78）
- **日付**: 2026-10-16
- **決定**: 管理画面の利用者は当面は社内（SAS）だけ。新規登録は、有効な招待のトークンと、その招待先アドレスがそろったときだけ受け付ける。トップページ・LP・ログイン画面から新規登録への導線を外す。招待の有効期限は7日から48時間に縮める。組織作成は今のまま（登録した人は作れる）

  - better-auth の organization プラグインは使わない（組織と招待はアプリ側で持つ。プラグインの API を公開しない）
  - 登録した後に招待が期限切れ・取り消しになると、アカウントだけが残る（組織には入れない）。48時間の窓なので許容する
- **既知の限界**: メール確認がないので、招待リンクを持っている人なら招待先アドレスで登録して参加できる。自社ドメインの送信元ができたら、招待の承認にメール確認を必須にする
- **見直す条件**: 社外提供を決めたとき。登録を開ける前に、新規登録のメール確認と組織作成の上限を入れる
- **却下案**: アドレスだけで判定（推測で先に登録される）。組織作成を閉じる（招待制なら登録者は社内に限られ、リンク漏れの本当の対策はメール確認なので、オーナー判断で今のまま）

### [Domain] リードの活動履歴と、営業による更新の監査ログ（#101）
- **日付**: 2026-10-16
- **決定**: 公開フォームはリードの項目を書き換えない（#67 のまま）が、リードの行動は本人確認の有無にかかわらずすべて履歴に残して見せる（オーナー判断）。営業による更新は監査ログに変更点だけを残す
- **理由**: 既存のリードと同じメールアドレスからの診断・やり直し・相談の申込み・追加の回答が、通知でしか分からなかった。営業による状態やフェーズの変更はどこにも記録していなかった
- **ルール**:
  - 新しいテーブルは作らない。履歴は既にある記録（leads・diagnostic_submissions・lead_hearings・lead_comments・audit_logs）を時系列に並べて作る（`lib/features/lead-activity/service.ts`）
  - 営業の更新（leads の create / update / delete と一括の更新・削除・インポート）は、`audit_logs` に1操作1行（一括はリードごとに1行）を、更新と同じトランザクションで書く。update は値が変わった項目だけを `changes.before/after` に入れ、何も変わらなければ書かない。create は営業の項目だけ（連絡先は入れない）、delete は名前と会社名だけ
  - 本人確認済み＝その送信がリードを作った、または同じ画面から続けて診断した（#67）。それ以外は「本人未確認」の印を付けて出す
  - 相談の申込みは、診断と同時でも結果画面からでも、いつも別の行（`consultation_requested`）にする。追加の回答は、回答した時刻が残っているとき（本人確認済みの送信）だけ別の行にし、それ以外は診断の行に「回答済み」とだけ出す
  - MQL・SQL・商談フェーズは、リードの日付の列から出す。ただし同じ変更を記録した監査ログがあるとき（MQL・SQL は同じ時刻、フェーズは同じ日（日本時間））は、監査ログの「リードを更新」の行だけにする（二重に出さない）
  - 読めるのはリードを閲覧できる人（`read Lead`、parent_viewer を含む）。すべての読み出しを organizationId と leadId で絞り、別の組織のリードは NOT_FOUND
  - 回答者へのメール（#154）も履歴に出す: 結果メールの依頼（`result_email_requested`、確認待ち／確認済み／辞退／リンク期限切れ）、送付（`result_email_sent`、依頼ごとに1行。Resend が重複として断った再送は数えるが別の行にしない）、配信停止（`email_unsubscribed`、リードの今のアドレスか依頼・送付のアドレスに当たる組織の停止リスト、理由と経路）。確認メールは個別に出さない。アドレス・トークン・Resend のメッセージ ID・エラーコードは履歴に含めない
  - 配信停止の理由・経路・停止した担当者と、辞退した依頼の「依頼していない」は、設定を更新できる人（`update Settings`。owner / admin / group_owner / group_admin）にだけ返す。ほかの人（member / parent_viewer）には「配信停止」と「このアドレスにはメールを送らないでください」という注意だけを出す。隠すのはサーバー側（応答に入れない）で、画面で隠すだけにはしない（2026-10-23 オーナー判断、#365。迷惑メールの報告や「依頼していない」は回答者とのトラブルに当たる情報で、親組織の閲覧者まで見せる理由がない）
    - 確認画面で辞退された依頼の「辞退」は全員に見せる。辞退すると必ず「依頼していない」で停止するので、辞退の行と同時刻の停止から理由は推し量れるが、営業がもう連絡しないと判断するのに要る情報として受け入れる（2026-10-23 オーナー判断、#368 のレビュー）。隠す主な対象は、時刻からは割り出せない迷惑メールの報告や宛先不明などの理由の表示
- **既知の限界**: ヒアリングの更新は最後の1回しか分からない。各記録はリードごとに新しい順に1000件までを読む。外部 API（`/api/v2/leads`）からの更新はまだ監査ログに残らない
- **却下案**: 活動履歴のテーブルを新しく作る（本番 DB の変更が要る。マイグレーションより先にマージすると本番が壊れる）

### [Architecture] 診断ビルダーの土台（#122）
- **日付**: 2026-10-16
- **決定**: マーケターが作る診断は、新しいテーブル `diagnoses`（下書き）と `diagnosis_versions`（公開版。変更不可の写し）で持つ。定義の形は AX 診断の型（sections / showWhen / exclusiveOptions）を広げたもので、回答の検査は `lib/features/diagnostics/engine.ts` を共有する。AX 診断はコード定義のまま残す。下書きの編集と公開は owner / admin だけ（オーナー判断）

  - シードやテストは架空の診断だけ。営業の内容はリポジトリに置かない
- **却下案**: `diagnostic_templates` の拡張（意味の衝突と1本の採点を抱え続ける）、Payload の DiagnosticForms（組織の分離がない）、AX 診断のビルダー移行（過去回答の再計算が全件一致することを条件に後で再検討）

  - 手元では差分が出ないのに失敗するときは、Bun の版の違いを疑う。ビルドログの Bun の版で `bunx bun@<その版> install --frozen-lockfile` を流して再現する。すぐ直せなければ、`installCommand` を戻す PR で逃がす
  - ビルドキャッシュが疑わしいときは、Vercel の Redeploy で「Use existing Build Cache」を外す
  - Bun の版を上げて `bun.lock` の形式が変わる場合は、Vercel の Bun が読めるかを先に確かめる

### [Email] [Security] 回答者への結果メール（ダブルオプトイン）（#154）
- **日付**: 2026-10-23
- **決定**: AX 診断の結果画面に「診断結果をメールで受け取る」を置く。押すと固定の文面の確認メールを送り、確認のページのボタン（POST）を押した人にだけ結果を送る。#67 で却下した「結果をメールで送る」をこの形で置き換える（[UX] 診断結果の保存（#67）の却下案の理由は、下のルールで解消する）
- **理由**: 公開フォームには他人のアドレスも入れられる。宛先をサーバーが決め、本人が確認したときだけ結果を送れば、任意の宛先に送る経路にならない
- **ルール**:
  - 宛先は「送信 → リード → メールアドレス」でサーバーが決める。リクエストは送信 ID と言語だけ（送信 ID は送ったブラウザだけが知る。受付は結果画面と同じ24時間）。画面に出すアドレスは表示だけ
  - 確認メールは同じアドレス（組織ごと）に24時間に1通まで（`respondent_email_sends` の confirmation の sent/pending と `idempotent_replay` で判定）。本文に回答者の入力も結果も入れない。確認のリンクは72時間、トークンはフラグメント（`#t=`）に置き、DB にはハッシュだけ
  - 送信済み・配信停止中・24時間以内に送り済み・テストモードで対象外・同じ診断から申込済みは、API ではどれも同じ `accepted` を返し、画面も同じ文面を出す（アドレスの状態を推測させない。内部の結果 `already_requested` はテストとログ用）。組織の上限（30通/時・100通/日、`AX_RATE_LIMITS`）は `sendRespondentEmail` の前に数え、超えたら 503（何も記録しない。上限は組織のもので、アドレスについては何も分からない）
  - 確認メールが送れなかったときも同意の行は消さない（申込の記録として残す）。同じ診断からもう一度押されたら、その同意の確認メールがどれも失敗（`idempotent_replay` と `recipient_not_allowed` を除く）のときだけ、新しいトークンを発行して送り直す（24時間の規則と組織の上限はそのまま効く）。idempotencyKey は `ax-confirm:<同意 ID>:<トークンのハッシュの先頭16文字>`。送り直しは本文（トークン）が変わるので、同意 ID だけのキーだと Resend が 409 `invalid_idempotent_request` を返し、届いていない確認メールを送信済みと誤認するため
  - Resend の 409 `invalid_idempotent_request`（同じキーで本文の違う依頼が24時間以内にあった）は、前の依頼が届いたものとして扱う。この試行の行は `failed`＋`idempotent_replay`（配信停止のトークンは届いていない）で記録し、`already_sent` を返す。「送信済みがあるか」の判定はどこもこの行も数える。409 `concurrent_idempotent_requests`（同じキーの依頼が処理中）は送信済みにせず、普通の失敗（もう一度押せる）
  - Resend の呼び出しは10秒で打ち切る（`EMAIL_SEND_TIMEOUT_MS`。SDK が AbortSignal を受けないので Promise.race）。打ち切りは失敗として扱い、ロックと接続を maxDuration（30秒）まで持たない
  - 確認のページは GET では何も変えない。確定は同じリンクの同時押しを advisory lock で1つにし（2つ目は `busy`）、この依頼の結果の送信（sent/pending/`idempotent_replay`）があれば `already_sent`。Resend の idempotencyKey は `ax-result:<同意 ID>`（試行をまたいで同じ）。送れたらトークンを消す（使い切り）。送れなかったときはトークンを残し、もう一度押せる
  - 結果は保存した診断（`diagnostic_submissions.result`）から作り直す（ブラウザの値は使わない）。リードか診断が消えていれば送らない
  - 確認のページの「心当たりがない・受け取らない」で、依頼を取り消し（`withdrawn_at`、トークンを消す）、アドレスを組織の停止リストに入れる（`not_requested`／`confirm_page`）。期限切れの後も使える
  - 配信停止のリストは組織ごと。送る直前に毎回確かめる
  - 結果画面のボタンは `AX_RESULT_EMAIL_ENABLED=true` のときだけ出し、申込の API もそれ以外は 404。確認のページと API はフラグに関係なく動く（届いた確認メールは使え、断ることはいつでもできる）。本番で有効にするのは、法務の OK と #128（送信元の切り替え）の後、オーナーの承認を得てから
  - ロックを持つ処理（申込・確定・断る）は、ロック用とその中の処理用に DB の接続を2本使う。接続の取り合いで止まらないよう、1つのサーバーで同時に4件まで（超えたら申込は 503、確定は `busy`。どちらももう一度押せる）。この上限が守るのはそのサーバーの接続プール（10本、`lib/db/client`）で、Supabase 全体の接続数ではない
  - 確定の API は組織の上限を数えない。結果メールは、上限を数えて送った確認メール1通につき最大1通なので、上限は申込の側で効いている
- **未決**: 同意・送信・停止の記録を残す期間と、本人からの消去の求めへの対応は法務の回答を待つ（#154 の確認事項）
- **却下案**: 結果画面に入力欄を置いて任意の宛先に送る（#67 の理由のまま）。確認なしで結果を送る（他人のアドレスに自社ドメインから届く）。確定の処理全体を1つのトランザクションにする（送れた後にコミットに失敗すると、届いたメールの配信停止のトークンが DB に残らない）

### [Security] 管理画面 API の役割の確認と、埋め込み設定・QR キャンペーンの権限（#356）
- **日付**: 2026-10-23
- **決定**: 役割の確認がなかった管理画面の手続きに、各ルーターで使っている判定を足す。埋め込み設定と QR キャンペーンの作成・変更・削除（API キーの再発行を含む）は、設定を更新できる人（`update Settings`。owner / admin / group_owner / group_admin）だけにする。閲覧はリードを読める人（parent_viewer を含む）。画面では、変更できない人にボタンを出さない（`embed.canManage` / `distribution.canManage`）（オーナー判断）
- **理由**: 10/23 の監査で、閲覧専用の役割でも API キーの再発行や削除ができることが分かった。閲覧で見えるのは、伏せ字の API キー、ハッシュにした IP、集計だけ。parent_viewer はリード本体を読めるので、見える範囲は広がらない
- **ルール**:
  - 閲覧の手続きはリードの閲覧（`read Lead`）。A/B テストと診断テンプレートのカウンターはリードの更新（`update Lead`、同じルーターのほかの変更と同じ）
  - 書き込みは、直前の読み込みで組織を絞っていても、`organizationId` の条件を付ける（同じトランザクションの中で組織を絞って `FOR UPDATE` で読んだ行を書く場合と、書く行の id をサーバーの中で決める場合は除く）。A/B テストの variant のテンプレートは、作成でも更新でも同じ組織のものか確かめる
  - 管理画面を社外の利用者に開くときは、parent_viewer に埋め込み設定と QR キャンペーンを見せるかを見直す
  - 組織の切り分けの DB テスト（約120）をすべて足し終えるまで、AX 診断を公開しない（2026-10-23 オーナー判断。#51 の公開の条件）
- **対象外**: feature-flags と audit-logs のルーターは `server/routers/_app.ts` に組み込まれておらず、外から呼べない（触っていない）

### [Architecture] 商談（deals）を leads の横に足す（#435, Epic #430）
- **日付**: 2026-10-24
- **決定**: 商談を新しい表 `deals`（種類・ステージ・金額・確度・受注予定日・担当・前の商談）と `deal_history`（変更のたびに変更後の値をすべて1行）で持つ。`leads` は「担当者（人）＋入口」のまま残す。商談の作成・変更は、同じトランザクションでリードを前に進める（状態・商談フェーズ・到達日・商談済み）。オーナーは Epic #430 の計画で「Issue を作成して進めて」と指示
- **理由**: 金額・受注予定日・確度・ステージの履歴がなく、予測・目標・担当者別の成績が出せなかった。1つのリードに調査 → 移行の複数の商談がある。既存の集計（ダッシュボード・代行のファネル・納品レポート・REST API v2・Webhook）は leads を読むので、leads を前に進めれば変えずに動く
- **ルール**:
  - 種類・ステージ・既定の確度・予測の区分は `lib/features/deals/types/pipeline.ts` の1か所に置く（DB は text、検証は zod）。初期値（見極め 10%・課題の確認 20%・提案 40%・条件の調整 70%、確度 70% 以上はコミット・40% 以上はベストケース）は、営業部門の確認で変える
  - リードへの反映の規則は `lib/features/deals/lead-sync.ts` の1か所に置く。前に進む向きだけにする（成約のリードは成約のまま、フェーズは戻さない）。商談を削除してもリードは変えない
  - ステージを変えると、確度はそのステージの既定値に戻る（確度が送られたときはそれを使う）。受注・失注で閉じた日を入れ、開き直すと消す。失注には失注理由が必須。開き直すと失注理由と詳細を消す
  - 予測が読む値（種類・ステージ・金額・確度・区分・受注予定日・担当）が変わったときだけ `deal_history` に1行足す。変更はすべて `audit_logs`（resource 'deal'、metadata.leadId）に1行残す。リードが変わったときは、リードの監査行（metadata.dealId）・Webhook・引き継ぎの通知（#86）を今の部品で出す
  - 権限は既存の ability を使う（読む＝read Lead、作る・変える＝update Lead、消す＝delete Lead）。金額は読める人全員に見せる（初期値。営業代行のアカウント #276 には見せない）
  - ロックは商談 → リードの順に取る（同じリードの2つの商談の変更は、リードの行で待ち合わせる）
  - 取引先（companies）は後の段で足す。`accounts` は認証の表の名前なので使わない
- **マイグレーション**: drizzle の migrator は、記録済みの最新より `when` が古いマイグレーションを飛ばす。そのため、開いている #416（0031）・#422（0032）・#433 の後に番号を付け直してから本番に適用する
- **却下案**: Salesforce 型に leads を分ける（追加だけで済まず、公開フォームのメール照合・集計・Webhook がすべて変わる）。leads に金額などの列を足すだけにする（調査 → 移行の2件目の商談を表せない）
