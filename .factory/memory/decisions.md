### [Testing] テストカバレッジ方針
- **日付**: 2026-02-06
- **決定**: 層別カバレッジ目標 + E2E補完
  - Core (lib/features, lib/db, lib/auth): 80%
  - API (server/, app/api/): 70%
  - UI (components/, app/[locale]/): 30-40% (E2Eで補完)
  - E2E: 主要フロー100%
  - 全体目標: 40%+ (E2E含めた実質70%+)
- **理由**: 
  - 品質の一貫性を保つため、カバレッジ対象を恣意的に除外しない
  - UIコンポーネントはE2Eで効果的にカバー可能
  - ビジネスロジック層は高カバレッジを維持
- **却下案**: 
  - 全体70%一律目標（UIテストのコストが高すぎる）
  - カバレッジ対象からUIを除外（品質の一貫性が損なわれる）

### [Naming] テストファイル命名規則（種別別）
- **日付**: 2026-02-07
- **決定**: 
  - `*.test.ts` → Unit tests（外部依存なし、高速）
  - `*.integration.ts` → Integration tests（モック使用、中程度）
  - `*.spec.ts` → E2E tests（実環境、長時間）
- **理由**: 
  - テスト種別による明確な分類
  - CI並列化の容易さ（種別ごとに分離実行可能）
  - 外部依存の有無が明確になる
- **却下案**: 
  - レイヤー別のみの分類（Unit/Integration/E2Eが混在）
  - ディレクトリ分離のみ（ファイル名で判別不可）

### [Architecture] 診断はコードで定義し、点数はサーバー側でだけ計算する
- **日付**: 2026-10-09
- **決定**: AX マイグレーション診断は `lib/features/diagnostics/` に TypeScript で定義する（設問・選択肢・配点・判定ルール）。回答は `diagnostic_submissions` に保存し、作成・更新したリードと紐づける（#55、#46 の方針の具体化）
- **理由**:
  - MQL / SQL 判定や難易度の計算は、配点の合計だけでは表せないルールを含む
  - 判定ロジックを単体テストで固定でき、設問の版（`version`）と結果を一緒に保存できる
  - v1 は点数をクライアントから受け取っていて改ざんできた。その弱点を引き継がない
- **ルール**:
  - お客様に返すのは難易度・緊急度・主な課題・推奨ステップだけ。リードスコア・MQL/SQL 判定は返さない
  - 業務側で「要確認」の基準は `ax-migration/config.ts` に集める
  - 公開フォームは本人確認ができないため、同じメールアドレス（大文字小文字は区別しない）の既存リードは**書き換えない**。回答は既存リードに紐づけて保存し、営業には「本人未確認」として既存の登録名で通知する（2026-10-09 レビュー指摘: 第三者が他人のメールで回答するとリードを改ざんできた）
  - 同じメールの同時送信は (組織, メール) の advisory lock で直列化し、リードの重複を防ぐ
  - Web診断の完了を MQL の「行動」に数える（2026-10-09 オーナー判断）。config で「MQL候補」止まりにも切り替えられる → 2026-10-16 廃止（#139「適合」と「関心あり」）
  - 移行対象は基幹システムに加えて、VB のクライアントサーバー型、Access（部署単位のツールを含む）、WebPerformer（ローコードはまず WebPerformer のみ）。それぞれ別の選択肢・対象システムとして扱う。その他のローコード製品は当面対象外（2026-10-09 オーナー判断）
- **却下案**: Payload の DiagnosticForms に配点を持たせる（判定ルールを表現できず、テストもしにくい）。Payload は今後もブログ・LP など文章コンテンツに使う

### [Domain] AX 診断 v2: 移行元ごとの設問と LP（#62）
- **日付**: 2026-10-11
- **決定**: 最初に移行元（AS/400・NEC ACOS・Access・その他）を選び、移行元ごとに設問を変える。LP `/[locale]/ax-migration` に診断を埋め込む。デザインは同社の maru2-dx.com に合わせる
- **理由**: オーナー指示（移行元ごとに必要な診断内容を聞き、回答者の負担を極力減らす）。専門家レビュー（フォーム UX、Access・AS/400・ACOS 移行、コード、セキュリティ、アクセシビリティ）を反映
- **ルール**:
  - 必須は1経路あたり約10問。数値は範囲で聞き、技術的な設問にはすべて「わからない」を置く。詳しい設問は結果のあとの任意の追加質問（`detail`）にする
  - 刷新の緊急度は「使い続けるリスク」（直せる人・保守期限・サポート終了）で測り、回答者の検討時期は入れない（検討時期はリードスコアにだけ使う）
  - ACOS は NEC が継続を表明しているため、機器契約の区切りの重みを他より小さくする。「ACOS の終了」を理由にした文言は使わない
  - Access（Office）のサポート状況は終了日から計算する。終了日の当日はサポート中とみなす
  - 選択肢を足すときは、点数表（`AX_POINT_TABLES`）に重みを書く（加点しない選択肢も 0 と明記）。テストで漏れを検出する
  - 追加質問は1回だけ、送信から24時間以内。営業が変えたリードスコアは上書きしない
- **却下案**: 検討時期を緊急度に入れる（「1年以内」と答えるほど緊急度が上がる循環になる）。追加質問を必須にする（回答者の負担が増える）

### [Security] 公開フォームの送信対策（#67）
- **日付**: 2026-10-11
- **決定**: 永続的なレート制限（DB の `public_rate_limits`、固定ウィンドウ）と Cloudflare Turnstile（鍵を2つとも設定したときだけ有効。社内検証の間は無効のまま＝オーナー判断）。組織ごとの上限は受付ではなく通知に掛ける
- **理由**: middleware のレート制限はインスタンスごとのメモリで、Vercel では共有されない。通知を `after()` で確実に送るようにした（#65）ので、大量の送信で営業の受信箱とメールの送信枠をあふれさせられる。送信枠はパスワード再設定のメールと共用
- **ルール**:
  - 上限は `lib/features/diagnostics/ax-migration/limits.ts` にまとめる。送信は IP（30件/時）→メールアドレス（6件/時）の順に数え、断った規則より後は数えない。回答の検証は数える前に行う
  - 組織ごとの上限（通知100件/時、営業メール10通/時・30通/日）を超えても送信は保存する。通知だけを止め、超えた最初の1回だけメンバー（アプリ内）と営業（メール1通）に知らせ、相談申込はリード一覧で確認するよう書く（全員を締め出す使い方をさせない）
  - IP ごとの上限は1時間30件と1日100件（両方を数える）
  - IP のヘッダーは Vercel 上でだけ信じる（`process.env.VERCEL`）。それ以外では IP ごとの上限を掛けない。IPv6 は /64 で数える。キーは鍵付きハッシュで、生の値は保存しない
  - Turnstile は action と hostname を照合する。Cloudflare のテスト用の鍵は本番（`VERCEL_ENV=production`）では通さない。失敗は 403、Cloudflare が答えないときは 503（通さない）
  - Turnstile を有効にする前に、プライバシーポリシーに Cloudflare の利用（IP と端末の情報を送ること）を書く
  - **外部に公開する前に Turnstile を必須にする**（専門レビュー）。鍵がないと、多数の IP からの送信で通知の枠（1時間100件）を使い切り、本物の相談申込の通知を止められる。上限は備えであって、主な防御は Turnstile
  - CSP の要点は `test/unit/lib/middleware/csp.test.ts` で固定する。`style` 属性にユーザーの文字列を入れない
- **既知の限界**: 新規リードの作成と既存リードへの紐づけで DB の処理が数ミリ秒違う（応答の中身は同じ。悪用には送信ごとの上限があり、未登録のアドレスはその1回でリードになる）
- **却下案**: Upstash Redis（アカウントと鍵が要る。DB で足りる量）。組織ごとの上限で受付を止める（1つの IP から全員を締め出せる）。Turnstile を必須にする（社内検証の段階では鍵の準備を待たない）

### [Domain] 「別のシステムも診断する」の2件目（#67）
- **日付**: 2026-10-11
- **決定**: 同じ画面から続けて送った2件目以降は、1件目と同じ回答者として扱い、リードの `responses.axMigration.otherSystems` に記録する。「本人未確認」にしない
- **理由**: 2件目も同じメールアドレスなので、既存リードと一致して「本人未確認」で通知されていた（オーナーが「すべて実施」と判断）
- **ルール**:
  - 画面は1件目の送信 ID（`continuedFrom`）を覚えておき、2件目以降に付ける（メモリだけ。保存しない）
  - サーバーは、その送信がこのリードを作ったこと・同じ組織・24時間以内を確かめる。満たさなければ今までどおり「本人未確認」
  - 確かめているのは「リードを作ったブラウザと同じか」で、メールの持ち主かではない。営業向けの文言も「同じ画面から続けて診断された」と書く。送信 ID は相談申込・追加質問の鍵と同じく、通知や Webhook の受け手にも見える（受け手は社内か連携先なので許容）
  - 応答の形は変えない（メールアドレスがリードとして登録済みかを、外から推測させない）
  - 2件目はリードの名前・会社名・スコアを変えない。相談申込は `conversion_point` を相談にし、MQL は未判定のときだけ付ける。2件目の追加質問は、その系の記録だけを更新する
- **却下案**: HMAC の継続トークン（発行の有無で登録済みかが分かってしまう。送信 ID を確かめれば足りる）

### [Security] 新規登録は招待制、招待リンクは48時間（#51・#78）
- **日付**: 2026-10-16
- **決定**: 管理画面の利用者は当面は社内（SAS）だけ。新規登録は、有効な招待のトークンと、その招待先アドレスがそろったときだけ受け付ける。トップページ・LP・ログイン画面から新規登録への導線を外す。招待の有効期限は7日から48時間に縮める。組織作成は今のまま（登録した人は作れる）

  - better-auth の organization プラグインは使わない（組織と招待はアプリ側で持つ。プラグインの API を公開しない）
  - 登録した後に招待が期限切れ・取り消しになると、アカウントだけが残る（組織には入れない）。48時間の窓なので許容する
- **既知の限界**: メール確認がないので、招待リンクを持っている人なら招待先アドレスで登録して参加できる。自社ドメインの送信元ができたら、招待の承認にメール確認を必須にする
- **見直す条件**: 社外提供を決めたとき。登録を開ける前に、新規登録のメール確認と組織作成の上限を入れる
- **却下案**: アドレスだけで判定（推測で先に登録される）。組織作成を閉じる（招待制なら登録者は社内に限られ、リンク漏れの本当の対策はメール確認なので、オーナー判断で今のまま）

- **決定**: 公開フォームはリードの項目を書き換えない（#67 のまま）が、リードの行動は本人確認の有無にかかわらずすべて履歴に残して見せる（オーナー判断）。営業による更新は監査ログに変更点だけを残す

### [Process] Vercel のインストールでロックファイルを厳密に守る（#257）
- **日付**: 2026-10-21
- **決定**: `vercel.json` の `installCommand` を `bun install --frozen-lockfile` にする。CI と同じく、`bun.lock` どおりの版で本番をビルドする（解決し直しで別の版が入り、型チェックやビルドが壊れたことがあるため。#236）

  - `package.json` と `bun.lock` がずれていると、本番デプロイのインストールが `lockfile had changes, but lockfile is frozen` で失敗する（本番は前のデプロイのまま）。そのときは `bun install` でロックファイルを更新した PR を出し、マージし直す

  - 手元では差分が出ないのに失敗するときは、Bun の版の違いを疑う。ビルドログの Bun の版で `bunx bun@<その版> install --frozen-lockfile` を流して再現する。すぐ直せなければ、`installCommand` を戻す PR で逃がす
  - ビルドキャッシュが疑わしいときは、Vercel の Redeploy で「Use existing Build Cache」を外す
  - Bun の版を上げて `bun.lock` の形式が変わる場合は、Vercel の Bun が読めるかを先に確かめる

  - 本人確認なしの回答：希望がまだない → 保存する。既存が本人確認なしで未確定 → 置き換える。既存が本人確認あり → 変えない（フォームには #270 の案内文）。確定済み → 変えない
  - 本人確認ありの回答は今までどおり（本人確認なしの希望も置き換える）。本人確認なしの希望を置き換えたときは、通常の通知をもう一度送る
  - 確定では、営業が見た候補（日付と時刻）も送る。その間に希望が置き換わっていたら確定せず、カードに最新の候補を確認するよう出す
  - リード詳細のカードに注意を出し、確認メールのチェックは初期値を外す。アプリ内通知のタイトルに「（本人確認なし）」を付け、確定前にご本人へ確認するよう本文に書く
