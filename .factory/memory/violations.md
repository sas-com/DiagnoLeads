### [CRITICAL] 秘密情報のコミット - 本番 DB の接続情報
- **日付**: 2026-10-15（発見）。コミットは 2026-02-08
- **違反原則**: Continuous Quality（秘密情報をリポジトリに置かない）
- **状況**: `.factory/memory/preferences.md` に本番 Supabase の DB パスワードとアクセストークンを書き、公開リポジトリにコミットしていた
- **影響**: 約8か月、第三者が本番 DB とアカウントを操作できる状態だった
- **対応**: 2026-10-18 にアクセストークンを無効化し、DB パスワードを変更して Vercel の `DATABASE_URL` を更新・再デプロイ（古いパスワードで接続できないこと、新しい接続で本番が動くことを確認）。直属の上長と情報セキュリティ担当へ報告済み（本人申告）。履歴に残る値は無効化済み
- **反省**: 発見から対応まで約3日、機能開発を優先して後回しにした。秘密情報の流出は、見つけた時点で他の作業より先に対応する
- **原因**: メモリのファイルを「手元のメモ」と考え、公開リポジトリに入ることを確認しなかった。secret scanning も無効だった
- **再発防止**:
  - 接続情報は Vercel と `.env.local` にだけ置く（`preferences.md` に明記）
  - `.factory/memory/` に書く前に、公開されてよい内容かを確かめる
  - GitHub の secret scanning と push protection を有効にする

### [MEDIUM] node_modules の直接編集 - Bun の共有キャッシュを書き換えた（#213）
- **日付**: 2026-10-22
- **違反原則**: Continuous Quality（依存の変更は `bun patch` だけで行う）
- **状況**: `bun patch sonner` がバージョンの曖昧さ（1.7.0 と 1.7.4）でエラーになったのに、そのまま worktree の `node_modules/sonner/dist` を直接書き換えた。ファイルは Bun の共有キャッシュ（`~/.bun/install/cache`）とハードリンクでつながっており、キャッシュと本体のチェックアウトを含む10か所が書き換わった
- **影響**: 数分間、ほかのワークツリーと本体のチェックアウトの sonner が改変版になっていた（テスト・ビルドの実行は無し）
- **対応**: npm の配布物（sonner@1.7.0）の内容で同じファイルをその場で上書きし、ハッシュの一致と本体の一致を確認。そのあと `bun patch sonner@1.7.0` で取り出した（リンク数1の）コピーを編集し、`bun patch --commit` で確定。前後でキャッシュのハッシュが変わらないことを確認
- **原因**: コマンドのエラーを確かめずに次の手順へ進んだ。既知の注意（メモリ「Bun patch, not node_modules」）を作業前に読み返さなかった
- **再発防止**:
  - 依存を変えるときは、編集の前に `stat -c %h` でリンク数が1であることを確かめる（1でなければ止まる）
  - `bun patch` は必ず `name@version` で指定し、エラーが出たら次の手順に進まない

## 違反パターンと対策

> Issue-First の運用は 2026-10-24 に変わった（`decisions/2026-10-24-issue-first-claude-creates.md`）。上の記録の「ユーザーに確認」は当時の再発防止策。

### パターン1: ユーザー指示への即時対応
**状況**: ユーザーが「〜してください」と指示
**誤った対応**: すぐに実装開始
**正しい対応**:
1. 対応する Issue を検索する
2. あればその番号で、なければ Claude が Issue を作り、番号を報告してから作業開始（2026-10-24 から。以前は作成してよいかを毎回確認していた）

### パターン2: 会話の流れでの機能追加
**状況**: 議論の結果、新機能の追加が決定
**誤った対応**: そのまま実装開始
**正しい対応**:
1. 決定事項をIssueとして記録
2. 受け入れ基準を明確化
3. ラベル付与後に作業開始

### パターン3: 軽微な変更の連続
**状況**: 「ついでにこれも」的な追加作業
**誤った対応**: 既存のコミットに含める
**正しい対応**:
1. 別のIssueとして切り出す
2. または既存Issueのスコープを明示的に拡大

### パターン4: レビュー無しのIssueクローズ
**状況**: 作業完了後、すぐにIssueをクローズ
**誤った対応**: エビデンス報告なし、レビュー依頼なしでクローズ
**正しい対応**:
1. エビデンス（テスト結果、変更内容）をIssueにコメント
2. レビュー担当者にレビュー依頼
3. レビュー承認後にクローズ

```
  - レビュー観点を記載

□ レビュー承認を得てからクローズしたか？
```
