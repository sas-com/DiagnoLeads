## 記録フォーマット

```
### [分類] 題名
- **日付**: YYYY-MM-DD
- **状況**: 何が起きたか
- **原因**: なぜ起きたか
- **解決策**: どう解決したか
- **教訓**: 今後どうすべきか
- **評価**: 役立った N / 外れた N（PR #番号, …）
```

- 新しい学びは項目を1つ足すか、同じ学びの項目に追記する。ファイル全体や節をまとめて書き直さない。教訓は短く言い直さない（具体的な手順や数字が落ちる）。長くなった経緯は PR へのリンクに置き換えてよい
- 「評価」の行は、新しい項目には書かない。月1回の見直しで初めて数えたときに足す
- 学びに従って作業したら、PR の本文の「役立った学び／外れた学び」の節に、`- 役立った：[分類] 題名` か `- 外れた：[分類] 題名（理由）` を1行ずつ書く。見出しは「### 」より後ろをそのまま写す。作業の PR では「評価」の数を変えない（決定 `2026-11-12-memory-ace-grow-and-refine`）

### [Test] ほかのセッションと CPU を取り合うと、関係のない画面のテストが時間切れで落ちる
- **日付**: 2026-10-24
- **状況**: 複数のセッションが同じ4コアのマシンで動き、load average が 14〜21 のときに全体のテストを流すと、変更と関係のない画面のテストが時間切れやデバウンスの判定で落ちた（PR #542 で5ファイル、全体は約23分。型チェックと並べた PR #528 でも同じ）
- **原因**: #573 で調べた4ファイルでは、テストの書き方だった。初めは「画面のテストは描画とタイマーに時間がかかり、CPU が足りないと `testTimeout`（20秒、`vitest.config.ts`）に届く。コードの問題ではない」と書いたが、違った。4ファイルは、#542 の5ファイルのうちの3つ（`hearing-settings-card`・`lead-hearing-editor-inputs`・`webhooks-settings-page`）と、#573 を立てたときの実行で落ちた `lead-filter-toolbar`。負荷の下では画面のテストが単独のときの5〜7倍遅くなり、次の書き方のテストが落ちた
  - 時間で動く処理を本物の時計で待っていた。`lead-filter-toolbar` は入力の後の待ち（30ミリ秒）を本物の時計で測り、キーの間に待ちが過ぎて検索が早く送られた。`lead-hearing-editor-inputs` は自動保存（本物の時計で3秒）が遅い手順の途中で走り、書きかけの入力を送った
  - 要素の多い画面で、`getByLabelText` と `getByRole` を画面全体にかけていた。`hearing-settings-card` はボタンが約130あり、1回に0.1〜0.8秒かかって20秒を超えた
  - 長い値を1文字ずつ打っていた。`webhooks-settings-page` は1キーごとにページ全体を描き直し、時間切れになったテストが止まらずに、次のテストの入力欄に文字を打ち込んだ
- **解決策**: 当時（#542・#528）は流し直して通ることを確かめただけだった。Issue #573 で負荷の下で再現させ、PR #588（3ファイル）と PR #627（`lead-filter-toolbar`）で直した。残りの2ファイル（`lead-hearing-editor`・`lead-card-list`）は Issue #711・PR #749 で直した（1コアの負荷では落ちなかった `lead-hearing-editor` を、3.1秒の待ちを入れて確かめた一時ファイルの差分は https://github.com/sas-com/DiagnoLeads/issues/711#issuecomment-6396788489 ）。`testTimeout` は上げていない。書き方は `docs/TESTING.md` の「1.5 画面のテストは、CPU の混み具合で結果が変わらないように書く」
- **教訓**:
  - 負荷の下でだけ落ちるテストを「コードの問題ではない」と決めない。単独で流し直して通っても、それで済ませない。本物の時計か重い処理（画面全体への問い合わせ・1文字ずつの入力）に頼っているしるしなので、`docs/TESTING.md` の 1.5 に沿って書き方を確かめる
  - 直す前に、同じ節の1コアの負荷のかけ方（CPU を回すプロセスと vitest を `taskset -c 0` で1つのコアにまとめる）で落ちるのを再現させ、直した後に同じ形で通ることを確かめる。1回で落ちなければ、`-t` で対象のテストだけを何回か流す（#627 では、1コアの負荷の下でもファイル全体は 11/12 回通り、検索のテストだけを20回流して 18/20 回落ちた）。1コアの負荷（3〜6倍）でも落ちないときは、待ちの長さ（例：自動保存の3秒）を超える待ちを手順の間に入れた一時的なファイルで、仕組みを確かめる。その差分は Issue か PR に貼り、ほかの人が流し直せるようにする（#711）。全部のコアに負荷をかける形は、ほかのセッションのテストを落とすので使わない
  - 自分の変更の範囲外のファイルで、その場で直せないときは、落ちたファイルと流し直した結果を PR に書き（黙って流し直さない）、書き方を直す Issue を切り出す。`testTimeout` を上げて済ませない
  - 重い処理（全体のテスト・型チェック・ビルド・E2E）は並べずに1つずつ流す。ほかのセッションも重い処理をしているときは、`bun run test:run --maxWorkers=2` のように並列数を抑える
  - テストのファイルの `afterEach` は、`test/setup.ts` の `cleanup()` より先に動く（vitest は後片付けのフックを、登録の逆の順に流す）。画面がまだ描かれている間に `resize` などのイベントを送ると、act の外で描き直しが走り、時間と大量の警告になる。画面の外の状態を戻す `afterEach` では、先に `cleanup()` を呼ぶ（#711）

### [Test] 手元の E2E とスクリプトは同じアドレスから来るので、アドレスごとの回数制限に互いに当たる
- **日付**: 2026-10-24
- **状況**:
  - #23 で認証の E2E を `@smoke` にして本番ビルド（`next start`）で流すと、ログインしたのに画面が未ログインの表示になる（get-session が 429）ことがあり、テストがまれに落ちた
  - E2E の直後にスクリーンショット用のスクリプトで AX 診断を送ったら、結果画面が出ずにタイムアウトした。時間を空けて流し直すと通った（どの制限に当たったかは確かめていない）
- **原因**: `proxy.ts` の回数制限（`lib/middleware/rate-limit.ts`）は、クライアントのアドレス（X-Forwarded-For の先頭。無ければ X-Real-IP）とパスの組ごとに、サーバーのメモリで1分の窓で数える。AX 診断の送信は1分10回、sign-in は5回、sign-up は3回。get-session は #23 の当時1分5回で、#519 で一般の API と同じ1分100回にした。better-auth の回数制限（本番ビルドだけ有効。sign-in と sign-up は10秒に3回）も同じアドレスで数える。手元の E2E とスクリプトはどれも同じマシンから来るので、ほかのテストや直前の実行の分まで合わせて数えられる
- **解決策**: テストごと（招待された人のブラウザも）に、`uniqueClientAddress()`（`test/e2e/helpers/auth.ts`）で X-Forwarded-For を変えた。本番で人ごとにアドレスが違うのと同じ形になる
- **前提**: `lib/middleware/rate-limit.ts` の `getIdentifier` は X-Forwarded-For の先頭をそのまま信用する。本番で安全なのは、Vercel が X-Forwarded-For を書き換え、クライアントが送った値を渡さないから（https://vercel.com/docs/headers/request-headers の `x-forwarded-for`）。Enterprise の Trusted Proxy を有効にするか、Vercel の前に別のプロキシを置くと、この前提が崩れる。E2E でアドレスを変えられるのは、`next start` の前にプロキシがないから。手元で効くのは、Next.js のサーバーが X-Forwarded-For を、無いときだけ足すから（`node_modules/next/dist/server/base-server.js`）
- **教訓**:
  - 本番ビルドに対する E2E で、ログイン・画面の読み込み・診断の送信を足すときは、アドレスごとの回数制限を考える。待ち時間（`waitForTimeout`）で避けない
  - 手元のスクリプト（スクリーンショットなど）で診断やログインを続けて送るときも、実行ごとに X-Forwarded-For を変える（Playwright なら `newContext({ extraHTTPHeaders: { 'x-forwarded-for': uniqueClientAddress() } })`）。診断で送るメールも毎回変える。AX 診断のメールごとの DB の制限（1時間6回、`AX_RATE_LIMITS.submitPerEmail`）は手元でも効き、X-Forwarded-For では避けられない（アドレスごとの DB の制限は、Vercel の外では数えない。`lib/request-guard.ts` の `clientIp`）
  - ヘッダーを変えられない（手で開いたブラウザなど）ときだけ、429 の `Retry-After` の秒数だけ待つ
  - X-Forwarded-For を変えて送るのは、手元のサーバーに対してだけにする。Vercel の上では書き換えられて効かず、本番やプレビューに診断を送ると、本物のリードと通知になる

### [Test] 本物の auth client を購読するテストは、セッションの store を止めてから終える
- **日付**: 2026-10-25
- **状況**: #706。`bun run test:run --maxWorkers=2` で全部のテストが通ったのに、未処理の例外 `ReferenceError: window is not defined`（better-auth の `client/broadcast-channel.mjs`）1件で終了コードが1になった。本物の `lib/auth/client.ts` をスタブしたネットワークで動かす `sign-out-other-devices.test.tsx` と `password-change.test.tsx` で起きる。1ファイルだけ流すと出ない
- **原因**: better-auth のセッションの store（nanostores の atom）は、最後の購読が外れてから1秒後（nanostores の `STORE_UNMOUNT_DELAY`）に止まり、止まるときに `window` から自分のリスナーを外す。画面の unmount の後と、購読のないときの `sessionStore.get()` の後に、このタイマーが残る。CPU が混んでワーカーの終了が1秒より遅れると、jsdom が片付いた後にタイマーが動く
- **解決策**: `beforeAll` で空のリスナーを付けて store をファイルの間ずっと動かし（開いたままのタブと同じ）、`afterAll` で偽のタイマー（`setTimeout`・`clearTimeout`）の下でリスナーを外し、`vi.runOnlyPendingTimers()` で jsdom があるうちに止めた。この形は `test/mocks/auth-session-store.ts` の `keepAuthSessionStoreMounted()` にまとめ、止めるときにタイマーが1つ積まれたことも確かめる（ほかの購読が残っていると、黙って何も止まらないため）。nanostores の `cleanStores` は、nanostores が直接の依存でないので使わない。直ったことは、組み込みの jsdom を包み、片付けの後に1.5秒待つ環境のファイル（コミットしていない）を `--environment <そのファイルの絶対パス>` で渡し、対象のファイルともう1つ時間のかかるファイルを `--maxWorkers=2` で流して確かめた。main では毎回出て、直した後は出ない（ほかのファイルが流れている間は、終わりかけのワーカーの例外も拾われる）。vitest 4.1 では `vitest/environments` は非推奨（読み込むと警告が出る）なので、`vitest/runtime` の `builtinEnvironments.jsdom` を包む
- **教訓**: 本物の auth client（nanostores の store）を購読するテストを足すときは、describe の外（ファイルの最上位）で `keepAuthSessionStoreMounted(authClient.$store.atoms.session)` を呼ぶ。`@/lib/auth/client` をモックするテストには要らない。全体の実行だけで出る未処理の例外は、報告されたファイルの片付けの後に残るタイマーを疑い、上の片付けの後に待つ環境で再現させてから直す

### [Test] 固定の日付のデータを、「今」を受け取らない関数で確かめるテストは、日付が進むと必ず落ちる
- **日付**: 2026-11-07
- **状況**: #924。CI の必須の検査「DB Integration Tests」が、2026-11-06 を過ぎてから、どのブランチでも落ちるようになった。落ちたのは `test/unit/integration/site-analytics.db.test.ts` の権限のテストで、`expected 0 to be greater than 0` だった。PR #922（変更はフックのテストだけ）の CI で見つかり、その PR は直るまでマージできなかった
- **原因**:
  - テストは、訪問のデータを「日本の今日 = 2026-10-30」（`NOW`）の日付で入れていた
  - ほかのテストは `getSiteOverview(..., { now: NOW })` で今日を渡していた
  - 権限のテストだけが、tRPC のルーター `siteAnalytics.overview` を呼んでいた。このルーターは「今」を受け取らず、実際の今日から7日分を数える
  - そのため、実際の日付が 10/30 から7日を過ぎると、期間にデータが無くなった
- **解決策**:
  - そのテストの間だけ、`vi.useFakeTimers({ toFake: ['Date'] })` と `vi.setSystemTime(NOW)` で Date を固定し、`finally` で `vi.useRealTimers()` に戻した（PR #926）
  - 偽物にするのは `Date` だけにした。postgres.js は待ち時間を `setTimeout` と `performance.now()` で測るので、接続には影響しない
  - 同じ書き方は `lead-meetings-export.db.test.ts` と `today-org-isolation.db.test.ts` にもある
  - 直す前の失敗は、手元の実 DB で再現させてから直した。クラウドのセッションでは Docker が使えないので、PostgreSQL 16 に `postgresql-16-pgvector` を入れて、127.0.0.1:55432 に立てた
- **教訓**:
  - 固定の日付でデータを入れるテストでは、「今」を引数で渡すか、Date を固定する。ルーターのように「今」を受け取らない入口を呼ぶなら、Date を固定する
  - 必須の検査が、変更と関係のないテストで落ちたら、まず main でも落ちるか（日付・外部の状態に依存していないか）を確かめる。直す作業は別の Issue に切り出し、それをマージしてから main を取り込む

### [Test] 守りを外すテストで、まだコミットしていない変更を `git checkout` で戻さない
- **日付**: 2026-11-10
- **状況**: #998 で、守りを外したときにテストが落ちるかを確かめるため、ファイルを書き換えてテストを流し、`git checkout -- <file>` で戻した。まだコミットしていない2つのファイルの変更が消え、未追跡の新しいファイルは戻らずに書き換えたまま残った。続く確かめの件数も、そのせいで誤っていた
- **原因**: `git checkout -- <file>` は、作業中の版ではなく HEAD の版に戻す。未追跡のファイルは git が知らないので戻せない（エラーになっても、ループは先へ進んだ）
- **解決策**: 書き換える前に、変更したファイルと未追跡のファイルを控えた（`{ git diff --name-only; git ls-files --others --exclude-standard; } | tar -cf <控え> -T -`）。1つ書き換えるたびに控えから戻し、最後に控えと同じかを `cmp` で確かめた。消えた変更は打ち直した
- **教訓**: 守りを外す確かめは、コミットしたあと（`git checkout` で戻せる）か、控えから戻す形で行う。戻したあとは、控えかコミットと同じことを確かめてから先へ進む

### [DB] 本番の接続先を持たないクラウドのセッションから、Supabase のコネクタでマイグレーションを適用する
- **日付**: 2026-10-25
- **状況**: #574（PR #662）の 0035（索引1つ）を本番に適用するとき、クラウドのセッションには本番の接続先がなく、`bun run db:migrate` を流せなかった。オーナーの承認を得て、Supabase のコネクタ（`execute_sql`、プロジェクト `diagnoleads-v2`）で適用した
- **原因**: 本番の接続文字列は手元の `.env.local` と Vercel にだけ置く（秘密情報を書かない）。コネクタはそれを使わずに本番の SQL を流せる
- **解決策**: 次の順で行った
  1. オーナーの承認を、その回ごとに得る（`.claude/rules/db-schema.md`。コネクタで流すことも含めて頼む）
  2. 流すマイグレーションのハッシュと `when` を、drizzle と同じ方法で出す：`readMigrationFiles({ migrationsFolder: './drizzle' })` の最後の要素の `hash`・`folderMillis`・`sql`（scratchpad の小さなスクリプトを `bun` で流す）
  3. 流す前に読み取りで確かめる（1つのクエリで）：`drizzle.__drizzle_migrations` の `max(created_at)` が、流すものの `when` より小さい／そのハッシュが未記録／作るもの（索引など）がまだ無い／変える表の大きさ／`pg_stat_activity` で長いトランザクションが無い
  4. 1つのトランザクションで流す：`begin; set local lock_timeout = '5s'; <マイグレーションの SQL>; insert into drizzle.__drizzle_migrations ("hash", "created_at") values ('<hash>', <when>); commit;`。台帳に記録しないと、あとで `db:migrate` が同じ SQL をもう一度流して失敗する
  5. 流したあとに読み取りで確かめる：`pg_indexes`（など）にできたこと、台帳の最新がそのマイグレーションになったこと
- **教訓**:
  - コネクタの経路は `db:migrate` を通らないので、#620 の台帳の検査と #723 の lock_timeout が効かない。上の 3 と 4 の `set local lock_timeout` で代わりをする
  - 本番に流すのは、PR の CI が緑で、main を取り込んだ後のマイグレーションだけ。ほかの PR と番号が重なるときは、先に作り直してから流す（今回は 0032 を 0035 に作り直した）
  - 複数のマイグレーションや、データを書き換えるマイグレーションは、この経路でなく `db:migrate`（Session pooler か直接の接続）で流す。この経路は、短い DDL を1本流すときに限る
  - Supabase の `apply_migration` は Supabase 自身の台帳に記録するもので、drizzle の台帳には書かないので使わない

### [DB] join のない select で選ぶ SQL の値は、その一番上の列が表名なしで書かれ、相関サブクエリの中で別の表の列になる
- **日付**: 2026-10-28
- **状況**: #556（「今日」の画面）の `getMyMeetings` で、`leads` だけの select に list-sql.ts のサブクエリ（`(select mr.confirmed_time from meeting_requests mr where mr.lead_id = ${leads.id} ...)`）を値として選ぶと、時刻と評価が空になった。実 DB のテストで見つかった
- **原因**: drizzle は、join のない select の選ぶ値（`select({ x: <sql のテンプレート> })`）の一番上にある列を、表名なしで書く（`mr.lead_id = "id"`）。相関サブクエリの中では、`"id"` はサブクエリ自身の表の列（`meeting_requests.id`）を指すので、エラーにならずに条件が別のものになる。値を1段入れ子にする（sql のテンプレートで `${sub}` を包み直す）か、select に join があるか、WHERE の中なら `"leads"."id"` と書かれる（2026-10-28 に `QueryBuilder` の `toSQL()` で確かめた）
- **解決策**: 選ぶ値を1段入れ子にする `nested()`（sql のテンプレートで包み直すだけの関数）を `lib/features/leads/api/list-sql.ts` に置き、join のない select で list-sql.ts の値を選ぶときはこれを通すとコメントに書いた。`getMyMeetings`（`lib/features/leads/meetings.ts`）は、選ぶ値をすべてこれで包む
- **教訓**:
  - 相関サブクエリを持つ SQL の値を、join のない select で選ぶときは、1段入れ子にするか、`toSQL()` で表名が付いているかを確かめる。サブクエリの中で外の列を、表名なしで指す書き方をしない
  - list-sql.ts の値（`leadDealRating`・`leadNextMeetingDate` など）は、リード一覧（join あり）と WHERE では正しく書かれるので、一覧のテストでは気づかない。新しい場所で選ぶときは、実 DB のテストで値まで確かめる

### [CI] `timeout` で `playwright install --with-deps` を止めても、sudo の下の apt は裏で動き続ける
- **日付**: 2026-11-12
- **状況**: #1098 で、E2E の `timeout 180 bunx playwright install --with-deps chromium` を `timeout 60` に縮めた。上限で切ると apt・dpkg が途中で止まり、壊れた状態が残るのではないかを確かめた
- **原因**: Playwright は apt を `sudo -- sh -c "apt-get update&& apt-get install -y ..."` で起動する。GNU `timeout` はプロセスグループ全体に SIGTERM を送る。（推測）sudo は同じプロセスグループから来たシグナルを中継せず、Ubuntu 24.04 の既定の `use_pty` では apt が別のセッションで動くため、止まらない。止まらないこと自体は次の行のログで確かめた
- **解決策**: apt の障害時の3つの run のログで、`::warning` の行のあとにも apt の出力（`Err:4 ... noble-backports` など）が続いていることを確かめた。後続の `bunx playwright install chromium` は apt・dpkg を使わず、ワークフローのほかの場所にも apt は無いので、裏の apt は害にならない
- **教訓**:
  - `timeout` で切れるのは bun・node の Playwright 側だけで、apt はジョブが終わるまで動く（ジョブの終わりにランナーが残ったプロセスを片付ける）。dpkg のロックは fcntl なので、プロセスが終われば外れる
  - 上限で切ったあとに apt を使う手順を足すときは、裏の apt と dpkg のロックを取り合う。足す前に、裏の apt の終わりを待つ形にする
  - 上限の長さは、2026-11-10〜12 の成功した run のうち、apt の障害時を除く29件の実績から決めた。27件は17〜37秒、ミラーが遅かった2件は132秒・189秒。遅い2件のような日は回避に進むことを受け入れた

### [API] organizationProcedure の input には、手続きのスキーマにない項目も残る
- **日付**: 2026-10-25
- **状況**: #743（#740 のレビューで見つかった）。`notifications.updatePreferences` が `const { organizationId, ...updates } = input` を `.set({ ...updates })` に渡していた。組織のメンバーが `userId`（同じ組織のほかのメンバーの id）や `id` を足して送ると、自分の通知の設定の行の `user_id`・`id` が書き換わり、ほかのメンバーの (user, org) の行が2つになった。`createdAt` に文字を送ると INTERNAL_SERVER_ERROR になった（実 DB のテストで再現した）
- **原因**: `organizationInputSchema` が `.passthrough()` で、tRPC 11 は `.input()` ごとに生の入力を検査し、結果を `{ ...前の結果, ...次の結果 }` でつなぐ。手続きの `z.object` が落とした項目も、最初の結果から resolver の `input` に残る。drizzle の `.set()`・`.values()` は、テーブル定義のプロパティ名（camelCase。例：`userId`）と同じキーをすべて書く（DB の列名の `user_id` では書かれない）
- **解決策**: スイッチを名前（`NOTIFICATION_PREFERENCE_KEYS`）で1つずつ取り出す `pickPreferenceUpdates` を足し、ルーターと service の両方で使った。ほかの手続きを見回し、`...input` や残りの項目を受け取る service は、どれも項目を名前で読むか、`.strict()` のスキーマが知らない項目を断ることを確かめた（表は #743）
- **教訓**: resolver の `input`（と `...rest`）は、検査を通った項目だけとは限らない。DB の書き込み・監査・外への送信・ログには、項目を名前で取り出して渡し、`input` やその残りを広げない。型チェックはこれを守らない。passthrough の出力の型に `[k: string]: unknown` が付くので、resolver で宣言していない `input.<名前>` を直接読んでも型エラーにならない（打ち間違いも通る）。スキーマにない optional の項目を引数の型に持つ関数に `input`・`...input`・`...rest` を渡しても、TS はエラーにせず、呼び出し先ではその項目が型付きで読める（#773 のレビュー）。今ある32か所の受け渡しも、実行時には宣言していない項目が呼び出し先まで届く。安全なのは、呼び出し先の引数の型にある項目がどれもスキーマで宣言されていて、ほかの項目を読まないからにすぎない（2026-10-26 の再レビューで確かめた）。passthrough は外さず、項目を名前で取り出して守ることにした（オーナー判断の経緯は決定 `2026-11-08-keep-organization-input-passthrough`、ルールは `.claude/rules/api-routers.md`）

### [Performance] 空だった表に書き込みを足すときは、その表の外部キーの索引を確かめる
- **日付**: 2026-10-25

### [UI] 日本語入力の確定・取り消しの Enter と Esc を、送信や閉じる操作に取られないようにする
- **日付**: 2026-10-26
- **状況**: リード詳細のメモ（#722、PR #807）と連絡の記録（#554、PR #769）で、Ctrl/⌘＋Enter で送り、Esc で編集を閉じるようにした。読み取り専用の UI/UX のレビューで、変換を確定する Enter や、変換を取り消す Esc が、送信や閉じる操作に取られるおそれを指摘された
- **原因**: Chrome は変換中の keydown に `isComposing: true` を付ける。Safari は、変換を確定・取り消す keydown を compositionend の後に送り、そのとき `isComposing` は false で、`keyCode` は 229 になる。`isComposing` だけを見ると、Safari では確定の Enter で送信され、取り消しの Esc で書いた文が消える
- **解決策**: `components/common/form-controls.ts` の `isComposing`（`isComposing || keyCode === 229`）を変換中とみなし、`isSendShortcut`・`isCloseShortcut` で使う。テストは `fireEvent.keyDown` に `isComposing: true` と `keyCode: 229` の両方を渡して確かめる
- **教訓**: キーで送る・閉じる欄を作るときは、`components/common/form-controls.ts` の判定を使う。自分で `event.key === 'Enter'` を見ない。Radix の部品の Esc とブラウザのイベントは `components/ui/ime.ts`（`isImeKey`・`ignoreImeEscape`）を使う。Dialog・Sheet・AlertDialog・Popover は既定で対応済み（PR #1010・#1062）。この学びのあとも、#969・#1012・#1063 で同じ不具合が出た
