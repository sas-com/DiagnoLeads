### [Test] ほかのセッションと CPU を取り合うと、関係のない画面のテストが時間切れで落ちる
- **日付**: 2026-10-24
- **状況**: 複数のセッションが同じマシン（4コア）で動き、load average が 14〜21 のときに全体のテスト（`bun run test:run`）を流すと、変更と関係のない画面のテスト5ファイル（`hearing-settings-card`・`lead-hearing-editor-inputs`・`lead-hearing-editor`・`lead-card-list`・`webhooks-settings-page`）が上限の20秒を超えたり、デバウンスの判定で落ちたりした。全体は約23分かかった（#542）。型チェックと並べて流したときも同じことが起きた（#528）
- **原因**: #573 で調べた4ファイルでは、テストの書き方だった。初めは「画面のテストは描画とタイマーに時間がかかり、CPU が足りないと `testTimeout`（20秒、`vitest.config.ts`）に届く。コードの問題ではない」と書いたが、違った。4ファイルは、#542 の5ファイルのうちの3つ（`hearing-settings-card`・`lead-hearing-editor-inputs`・`webhooks-settings-page`）と、#573 を立てたときの実行で落ちた `lead-filter-toolbar`。負荷の下では画面のテストが単独のときの5〜7倍遅くなり、次の書き方のテストが落ちた
  - 時間で動く処理を本物の時計で待っていた。`lead-filter-toolbar` は入力の後の待ち（30ミリ秒）を本物の時計で測り、キーの間に待ちが過ぎて検索が早く送られた。`lead-hearing-editor-inputs` は自動保存（本物の時計で3秒）が遅い手順の途中で走り、書きかけの入力を送った
  - 要素の多い画面で、`getByLabelText` と `getByRole` を画面全体にかけていた。`hearing-settings-card` はボタンが約130あり、1回に0.1〜0.8秒かかって20秒を超えた
  - 長い値を1文字ずつ打っていた。`webhooks-settings-page` は1キーごとにページ全体を描き直し、時間切れになったテストが止まらずに、次のテストの入力欄に文字を打ち込んだ
- **解決策**: 当時（#542・#528）は、落ちたファイルを流し直して通ることを確かめ、PR に書いただけだった（#542 では落ちた5ファイルを新しいテストと一緒に流し直し、6ファイル82件が通った。#528 では単独で15秒で通った）。#573 で負荷の下で落ちるのを再現し、4ファイルのテストを直した（#588 で3ファイル、#627 で `lead-filter-toolbar`）。待ちを確かめるテストは偽のタイマーで進め、待ちが対象でないテストでは止め（`lead-hearing-editor-inputs` は自動保存を `vi.mock` で止めた）、問い合わせは `within()` で絞り、長い値は `clear` と `paste` で入れる。`testTimeout` は上げていない。書き方は `docs/TESTING.md` の「1.5 画面のテストは、CPU の混み具合で結果が変わらないように書く」にまとめた。#542 で落ちた残りの2ファイル（`lead-hearing-editor`・`lead-card-list`）は、#573 では調べず、#711 で同じ1コアの負荷の下で調べて直した。ただし `lead-hearing-editor` は、1コアの負荷では落ちなかった（直す前も2ファイル3回が 44/44 で通り、`-t "meeting mode"` の10回もすべて通った）。2つの変更の間が最大1.8秒あき、自動保存の3秒に近づいていたので、手順の間に本物の時計で3.1秒の待ちを入れた一時的なファイルで、自動保存が書きかけの入力を先に送ることを確かめた（直す前は落ち、直した後は通る。差分は #711 のコメント）。`lead-hearing-editor` は、自動保存を describe ごとに切り替える mock で止め、自動保存のテスト（偽のタイマー）でだけ動かした。保存ボタンは保存バー、項目の「次回」「対象外」はその項目のカードの中で探す（商談モードはボタンが100を超え、画面全体の `getByRole` は1回に2〜3.5秒かかった）。`lead-card-list` は、表の列のテストが `getByRole('cell', { name })` を画面全体に8回かけて14秒かかっていた（単独では4秒）のを、文字で行を探す形にした（2秒）。また、ファイルの `afterEach` が一覧を外す前に画面の幅を戻し、テストごとに一覧を表として act の外で描き直していた（1テストに最大1,249件の act の警告）ので、先に `cleanup()` で外すようにした
- **教訓**:
  - 負荷の下でだけ落ちるテストを「コードの問題ではない」と決めない。単独で流し直して通っても、それで済ませない。本物の時計か重い処理（画面全体への問い合わせ・1文字ずつの入力）に頼っているしるしなので、`docs/TESTING.md` の 1.5 に沿って書き方を確かめる
  - 直す前に、同じ節の1コアの負荷のかけ方（CPU を回すプロセスと vitest を `taskset -c 0` で1つのコアにまとめる）で落ちるのを再現させ、直した後に同じ形で通ることを確かめる。1回で落ちなければ、`-t` で対象のテストだけを何回か流す（#627 では、1コアの負荷の下でもファイル全体は 11/12 回通り、検索のテストだけを20回流して 18/20 回落ちた）。1コアの負荷（3〜6倍）でも落ちないときは、待ちの長さ（例：自動保存の3秒）を超える待ちを手順の間に入れた一時的なファイルで、仕組みを確かめる。その差分は Issue か PR に貼り、ほかの人が流し直せるようにする（#711）。全部のコアに負荷をかける形は、ほかのセッションのテストを落とすので使わない
  - 自分の変更の範囲外のファイルで、その場で直せないときは、落ちたファイルと流し直した結果を PR に書き（黙って流し直さない）、書き方を直す Issue を切り出す。`testTimeout` を上げて済ませない
  - 重い処理（全体のテスト・型チェック・ビルド・E2E）は並べずに1つずつ流す。ほかのセッションも重い処理をしているときは、`bun run test:run --maxWorkers=2` のように並列数を抑える
  - テストのファイルの `afterEach` は、`test/setup.ts` の `cleanup()` より先に動く（vitest は後片付けのフックを、登録の逆の順に流す）。画面がまだ描かれている間に `resize` などのイベントを送ると、act の外で描き直しが走り、時間と大量の警告になる。画面の外の状態を戻す `afterEach` では、先に `cleanup()` を呼ぶ（#711）

### [Test] E2E のテストは同じアドレスから来るので、アドレスごとの回数制限に互いに当たる
- **日付**: 2026-10-24
- **状況**: #23 で認証の E2E を `@smoke` にして本番ビルド（`next start`）で流すと、ログインしたのに画面が未ログインの表示になる（get-session が 429）ことがあり、テストがまれに落ちた
- **原因**: `proxy.ts` の回数制限（`lib/middleware/rate-limit.ts`。get-session は1分5回、#519）と better-auth の回数制限（本番だけ有効。sign-in と sign-up は10秒に3回）は、どちらもクライアントのアドレス（X-Forwarded-For）ごとに数える。E2E のテストはどれも同じマシンから来るので、ほかのテストの分まで合わせて数えられる
- **解決策**: テストごと（招待された人のブラウザも）に、`uniqueClientAddress()`（`test/e2e/helpers/auth.ts`）で X-Forwarded-For を変えた。本番で人ごとにアドレスが違うのと同じ形になる
- **前提**: `lib/middleware/rate-limit.ts` の `getIdentifier` は X-Forwarded-For の先頭をそのまま信用する。本番で安全なのは、Vercel が X-Forwarded-For を書き換え、クライアントが送った値を渡さないから（https://vercel.com/docs/headers/request-headers の `x-forwarded-for`）。Enterprise の Trusted Proxy を有効にするか、Vercel の前に別のプロキシを置くと、この前提が崩れる。E2E でアドレスを変えられるのは、`next start` の前にプロキシがないから
- **教訓**: 本番ビルドに対する E2E でログインや画面の読み込みを足すときは、アドレスごとの回数制限を考える。待ち時間（`waitForTimeout`）で避けない

### [Test] 実 DB のテストだけで確かめているモジュールは、カバレッジが低く出る
- **日付**: 2026-10-24
- **状況**: #28 で `lib/features/members/invitations.ts` のカバレッジが 11% だった。本物の PostgreSQL での振る舞い（ロック・一意制約・同時の承認）は `test/unit/integration/member-invitations.db.test.ts` で確かめていた
- **原因**: `*.db.test.ts` は `TEST_DATABASE_URL` がないと飛ばされる。CI の Test Coverage Report（`bun run test:coverage`）には DB がないので、数に入らない
- **解決策**: 偽の DB（受けたクエリを記録し、用意した結果を返すもの）でユニットテストを足し、100% にした（#528）。実 DB のテストはそのまま残した
- **教訓**: カバレッジが低いモジュールを見たら、先に `*.db.test.ts` で確かめていないかを探す。数字だけで「テストがない」と決めない。ユニットテストを足すときは、確かめる内容を実 DB のテストと分ける（ユニットはクエリの組み立てと分岐、実 DB はロック・制約・同時の操作）

### [Test] `describe.skipIf` の中身は、スキップされても収集のときに流れる
- **日付**: 2026-10-25
- **状況**: #673 で足した `test/unit/integration/migration-ledger.db.test.ts` が、`TEST_DATABASE_URL` のない環境（ユニットのシャードと手元）で、スキップされずにファイルごと落ちた
- **原因**: `describe.skipIf(!url)` でも、vitest はテストを集めるために describe の中身を流す。中身で `drizzle(client!)`（client は null）と `fs.mkdtempSync` を呼んでいた
- **解決策**: ほかの `*.db.test.ts` と同じく `(client ? drizzle(client) : null)!` にし、一時ディレクトリは `beforeAll` で作った
- **教訓**: 新しい `*.db.test.ts` は、コミットの前に `TEST_DATABASE_URL` なしでも1回流し、「skipped」になるのを確かめる。describe の中身では、接続や副作用のある処理を呼ばない（`beforeAll` に置く）

### [Test] 本物の auth client を購読するテストは、セッションの store を止めてから終える
- **日付**: 2026-10-25
- **状況**: #706。`bun run test:run --maxWorkers=2` で全部のテストが通ったのに、未処理の例外 `ReferenceError: window is not defined`（better-auth の `client/broadcast-channel.mjs`）1件で終了コードが1になった。本物の `lib/auth/client.ts` をスタブしたネットワークで動かす `sign-out-other-devices.test.tsx` と `password-change.test.tsx` で起きる。1ファイルだけ流すと出ない
- **原因**: better-auth のセッションの store（nanostores の atom）は、最後の購読が外れてから1秒後（nanostores の `STORE_UNMOUNT_DELAY`）に止まり、止まるときに `window` から自分のリスナーを外す。画面の unmount の後と、購読のないときの `sessionStore.get()` の後に、このタイマーが残る。CPU が混んでワーカーの終了が1秒より遅れると、jsdom が片付いた後にタイマーが動く
- **解決策**: `beforeAll` で空のリスナーを付けて store をファイルの間ずっと動かし（開いたままのタブと同じ）、`afterAll` で偽のタイマー（`setTimeout`・`clearTimeout`）の下でリスナーを外し、`vi.runOnlyPendingTimers()` で jsdom があるうちに止めた。この形は `test/mocks/auth-session-store.ts` の `keepAuthSessionStoreMounted()` にまとめ、止めるときにタイマーが1つ積まれたことも確かめる（ほかの購読が残っていると、黙って何も止まらないため）。nanostores の `cleanStores` は、nanostores が直接の依存でないので使わない。直ったことは、組み込みの jsdom を包み、片付けの後に1.5秒待つ環境のファイル（コミットしていない）を `--environment <そのファイルの絶対パス>` で渡し、対象のファイルともう1つ時間のかかるファイルを `--maxWorkers=2` で流して確かめた。main では毎回出て、直した後は出ない（ほかのファイルが流れている間は、終わりかけのワーカーの例外も拾われる）。vitest 4.1 では `vitest/environments` は非推奨（読み込むと警告が出る）なので、`vitest/runtime` の `builtinEnvironments.jsdom` を包む
- **教訓**: 本物の auth client（nanostores の store）を購読するテストを足すときは、describe の外（ファイルの最上位）で `keepAuthSessionStoreMounted(authClient.$store.atoms.session)` を呼ぶ。`@/lib/auth/client` をモックするテストには要らない。全体の実行だけで出る未処理の例外は、報告されたファイルの片付けの後に残るタイマーを疑い、上の片付けの後に待つ環境で再現させてから直す

### [Harness] フックは置いた直後から効き、チェックアウト中のコードが動く

- **教訓**:
  - ガードを変えたら、ふだんの作業（コミット・PR・検索）で実際に使って誤検知を探す
  - 外部からの PR はチェックアウトせず、`gh pr diff` で読む（そのブランチのフックが動くため。運用はオーナーの判断待ち）

### [Harness] 専門エージェントの「読み取り専用」はフックで守る
- **日付**: 2026-10-24
- **状況**: 認証・セキュリティの PR はマージ前に読み取り専用のレビューを通す決定（`2026-10-19-security-review-gate`）があるのに、専門エージェントの tools に Bash があり、本文の指示だけに頼っていた。公式も「Bash を含む許可リストは厳密には読み取り専用でない」と言う
- **原因**: 「変更しない」を仕組みでなく文章で頼んでいた
- **解決策**: PreToolUse のガードが、入力の `agent_type` が `-specialist` のとき読み取り専用のルールを掛ける（#461）。書き込みは `/dev/null` だけ、依存の変更・インラインのスクリプト・外部への送信・書き込み系の MCP を止める
- **教訓**: 文字列の解析で作るガードは抜け道が多い。許可したコマンドのオプション（`sort -o`・`sed` の e/w・`git --upload-pack`・`vitest --outputFile`）、変数（`GIT_EXTERNAL_DIFF`・`NODE_OPTIONS`・`PATH`）、ループや条件のキーワードに付けたリダイレクト、`>&`・`<<<` まで見る。読み取り専用のレビューを2回通し、各抜け道を実際のフックの入口（`agent_type` を付けた入力）に流して塞いだ。意図した回避までは防げない前提で、既知の限界を決定に書く

### [DB] 本番の接続先を持たないクラウドのセッションから、Supabase のコネクタでマイグレーションを適用する
- **日付**: 2026-10-25
- **状況**: #574（PR #662）の 0035（索引1つ）を本番に適用するとき、クラウドのセッションには本番の接続先がなく、`bun run db:migrate` を流せなかった。オーナーの承認を得て、Supabase のコネクタ（`execute_sql`、プロジェクト `diagnoleads-v2`）で適用した
- **原因**: 本番の接続文字列は手元の `.env.local` と Vercel にだけ置く（秘密情報を書かない）。コネクタはそれを使わずに本番の SQL を流せる
- **解決策**: 次の順で行った
  1. オーナーの承認を、その回ごとに得る（`.claude/rules/db-schema.md`。コネクタで流すことも含めて頼む）
  2. 流すマイグレーションのハッシュと `when` を、drizzle と同じ方法で出す：`readMigrationFiles({ migrationsFolder: './drizzle' })` の最後の要素の `hash`・`folderMillis`・`sql`（scratchpad の小さなスクリプトを `bun` で流す）
  3. 流す前に読み取りで確かめる（1つのクエリで）：`drizzle.__drizzle_migrations` の `max(created_at)` が、流すものの `when` より小さい／そのハッシュが未記録／作るもの（索引など）がまだ無い／変える表の大きさ／`pg_stat_activity` で長いトランザクションが無い
  4. 1つのトランザクションで流す：`begin; set local lock_timeout = '5s'; <マイグレーションの SQL>; insert into drizzle.__drizzle_migrations ("hash", "created_at") values ('<hash>', <when>); commit;`。台帳に記録しないと、あとで `db:migrate` が同じ SQL をもう一度流して失敗する
  5. 流したあとに読み取りで確かめる：`pg_indexes`（など）にできたこと、台帳の最新がそのマイグレーションになったこと
- **教訓**:
  - コネクタの経路は `db:migrate` を通らないので、#620 の台帳の検査と #723 の lock_timeout が効かない。上の 3 と 4 の `set local lock_timeout` で代わりをする
  - 本番に流すのは、PR の CI が緑で、main を取り込んだ後のマイグレーションだけ。ほかの PR と番号が重なるときは、先に作り直してから流す（今回は 0032 を 0035 に作り直した）
  - 複数のマイグレーションや、データを書き換えるマイグレーションは、この経路でなく `db:migrate`（Session pooler か直接の接続）で流す。この経路は、短い DDL を1本流すときに限る
  - Supabase の `apply_migration` は Supabase 自身の台帳に記録するもので、drizzle の台帳には書かないので使わない

### [API] Route Handler の GET は、HEAD の要求でも呼ばれる
- **日付**: 2026-10-25
- **状況**: #41 で QR の入口（`app/q/[code]/route.ts`、GET だけを定義）にスキャンの記録を足すとき、リンクの確認ツールなどの HEAD の要求も記録に入るかを確かめた
- **原因**: Next.js は、HEAD を定義していない Route Handler の HEAD を GET の関数で答える（`node_modules/next/dist/server/route-modules/app-route/helpers/auto-implement-methods.js`）。`req.method` は `HEAD` になる
- **解決策**: 記録の前に `req.method !== 'GET'` なら記録しないようにし、ユニットテストで HEAD を流して確かめた
- **教訓**: GET の Route Handler で書き込む（数える・記録する）ときは、HEAD でも同じ関数が動くことを前提にし、書き込みを `req.method` で分ける

### [API] organizationProcedure の input には、手続きのスキーマにない項目も残る
- **日付**: 2026-10-25
- **状況**: #743（#740 のレビューで見つかった）。`notifications.updatePreferences` が `const { organizationId, ...updates } = input` を `.set({ ...updates })` に渡していた。組織のメンバーが `userId`（同じ組織のほかのメンバーの id）や `id` を足して送ると、自分の通知の設定の行の `user_id`・`id` が書き換わり、ほかのメンバーの (user, org) の行が2つになった。`createdAt` に文字を送ると INTERNAL_SERVER_ERROR になった（実 DB のテストで再現した）
- **原因**: `organizationInputSchema` が `.passthrough()` で、tRPC 11 は `.input()` ごとに生の入力を検査し、結果を `{ ...前の結果, ...次の結果 }` でつなぐ。手続きの `z.object` が落とした項目も、最初の結果から resolver の `input` に残る。drizzle の `.set()`・`.values()` は、テーブル定義のプロパティ名（camelCase。例：`userId`）と同じキーをすべて書く（DB の列名の `user_id` では書かれない）
- **解決策**: スイッチを名前（`NOTIFICATION_PREFERENCE_KEYS`）で1つずつ取り出す `pickPreferenceUpdates` を足し、ルーターと service の両方で使った。ほかの手続きを見回し、`...input` や残りの項目を受け取る service は、どれも項目を名前で読むか、`.strict()` のスキーマが知らない項目を断ることを確かめた（表は #743）
- **教訓**: resolver の `input`（と `...rest`）は、検査を通った項目だけとは限らない。DB の書き込み・監査・外への送信・ログには、項目を名前で取り出して渡し、`input` やその残りを広げない。型チェックはこれを守らない。passthrough の出力の型に `[k: string]: unknown` が付くので、resolver で宣言していない `input.<名前>` を直接読んでも型エラーにならない（打ち間違いも通る）。スキーマにない optional の項目を引数の型に持つ関数に `input`・`...input`・`...rest` を渡しても、TS はエラーにせず、呼び出し先ではその項目が型付きで読める（#773 のレビュー）。今ある32か所の受け渡しも、実行時には宣言していない項目が呼び出し先まで届く。安全なのは、呼び出し先の引数の型にある項目がどれもスキーマで宣言されていて、ほかの項目を読まないからにすぎない（2026-10-26 の再レビューで確かめた）。オーナーの判断（2026-10-26、#743）：ルール（`.claude/rules/api-routers.md`）に1行足すのは今、passthrough を外す（strip。`.strict()` にはしない）のは 10/29 の公開の後（#743 は #773 では閉じない）

### [Performance] 空だった表に書き込みを足すときは、その表の外部キーの索引を確かめる
- **日付**: 2026-10-25
- **状況**: #41（PR #704）で、それまで書き込むコードのなかった `qr_scans` に、公開の入口から行を足すようにした。読み取り専用のレビューで、`qr_scans.lead_id`（`ON DELETE SET NULL`）に索引がなく、行が増えるほど、どの組織のリードの削除も遅くなると指摘された
- **原因**: PostgreSQL は外部キーの参照先の行を消すたびに、参照する側の表を外部キーの列で探す（CASCADE・SET NULL のため）。参照する側の列には自動で索引が付かない。表が空のあいだは目に見えない
- **解決策**: 索引はスキーマの変更なので、#702 に `lead_id` と `(organization_id, campaign_id)` を足して、本番に適用してからマージする形にした。公開の入口からの水増しには、キャンペーンごとの1日の上限を入れた
- **教訓**: 使われていなかった表に書き込みを足すときは、その表のすべての外部キー（特に `ON DELETE` で参照先の削除から探されるもの）に索引があるかを `lib/db/schema.ts` で確かめる。公開の入口から増える表なら、日ごとの上限と保存期間も一緒に決める
