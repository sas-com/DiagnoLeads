### [Test] 浮動小数点の計算誤差

- **状況**: hierarchy-router.test.tsで加重平均計算のテストが失敗

### [Test] `*.integration.ts` は vitest に拾われない
- **日付**: 2026-10-24
- **状況**: 決定（2026-02-07）と TESTING.md が結合テストの名前を `*.integration.ts` としていたが、vitest の include は `test/**/*.{test,spec}.{ts,tsx}` だけだった

### [Test] 検証にかかる時間（2026-10-24 時点）
- **日付**: 2026-10-24
- **状況**: クラウドのセッション（4コア）で、全ユニットテスト約6分（約6,500件）、型チェックは初回56秒・2回目以降8秒（`tsconfig.tsbuildinfo` が効く）、lint 1秒、テスト1ファイル2秒。CI はテストを4分割して約2分
- **教訓**: 作業中は関係するテストだけ（`bunx vitest run <path>`）を回し、全体はコミットの前に1回流す

### [Test] ほかのセッションと CPU を取り合うと、関係のない画面のテストが時間切れで落ちる
- **日付**: 2026-10-24
- **状況**: 複数のセッションが同じマシン（4コア）で動き、load average が 14〜21 のときに全体のテスト（`bun run test:run`）を流すと、変更と関係のない画面のテスト（`hearing-settings-card`・`lead-hearing-editor-inputs`・`lead-filter-toolbar` など）が上限の20秒を超えたり、デバウンスの判定で落ちたりした。全体は約23分かかった（#542）。型チェックと並べて流したときも同じことが起きた（#528）
- **原因**: 画面のテストは描画とタイマーに時間がかかり、CPU が足りないと `testTimeout`（20秒、`vitest.config.ts`）に届く。コードの問題ではない
- **解決策**: 落ちたファイルだけを単独で流し直して通ることを確かめ、そのことを PR に書いた（#542 では5ファイル82件が通った。#528 では単独で15秒で通った）
- **教訓**:
  - 全体のテストで画面のテストが時間切れになったら、そのファイルだけを流し直す。落ちたファイルと流し直した結果を PR に書く（黙って流し直さない）
  - 重い処理（全体のテスト・型チェック・ビルド・E2E）は並べずに1つずつ流す

### [Test] E2E のテストは同じアドレスから来るので、アドレスごとの回数制限に互いに当たる
- **日付**: 2026-10-24
- **状況**: #23 で認証の E2E を `@smoke` にして本番ビルド（`next start`）で流すと、ログインしたのに画面が未ログインの表示になる（get-session が 429）ことがあり、テストがまれに落ちた
- **原因**: `proxy.ts` の回数制限（`lib/middleware/rate-limit.ts`。get-session は1分5回、#519）と better-auth の回数制限（本番だけ有効。sign-in と sign-up は10秒に3回）は、どちらもクライアントのアドレス（X-Forwarded-For）ごとに数える。E2E のテストはどれも同じマシンから来るので、ほかのテストの分まで合わせて数えられる
- **解決策**: テストごと（招待された人のブラウザも）に、`uniqueClientAddress()`（`test/e2e/helpers/auth.ts`）で X-Forwarded-For を変えた。本番で人ごとにアドレスが違うのと同じ形になる
- **前提**: `lib/middleware/rate-limit.ts` の `getIdentifier` は X-Forwarded-For の先頭をそのまま信用する。本番で安全なのは、Vercel が X-Forwarded-For を書き換え、クライアントが送った値を渡さないから（https://vercel.com/docs/headers/request-headers の `x-forwarded-for`）。Enterprise の Trusted Proxy を有効にするか、Vercel の前に別のプロキシを置くと、この前提が崩れる。E2E でアドレスを変えられるのは、`next start` の前にプロキシがないから
- **教訓**: 本番ビルドに対する E2E でログインや画面の読み込みを足すときは、アドレスごとの回数制限を考える。待ち時間（`waitForTimeout`）で避けない

### [Test] 実 DB のテストだけで確かめているモジュールは、カバレッジが低く出る
- **日付**: 2026-10-24
- **状況**: #28 で `lib/features/members/invitations.ts` のカバレッジが 11% だった。本物の PostgreSQL での振る舞い（ロック・一意制約・同時の承認）は `test/unit/integration/member-invitations.db.test.ts` で確かめていた
- **原因**: `*.db.test.ts` は `TEST_DATABASE_URL` がないと飛ばされる。CI の Test Coverage Report（`bun run test:coverage`）には DB がないので、数に入らない
- **解決策**: 偽の DB（受けたクエリを記録し、用意した結果を返すもの）でユニットテストを足し、100% にした（#528）。実 DB のテストはそのまま残した
- **教訓**: カバレッジが低いモジュールを見たら、先に `*.db.test.ts` で確かめていないかを探す。数字だけで「テストがない」と決めない。ユニットテストを足すときは、確かめる内容を実 DB のテストと分ける（ユニットはクエリの組み立てと分岐、実 DB はロック・制約・同時の操作）

### [Test] `describe.skipIf` の中身は、スキップされても収集のときに流れる
- **日付**: 2026-10-25
- **状況**: #673 で足した `test/unit/integration/migration-ledger.db.test.ts` が、`TEST_DATABASE_URL` のない環境（ユニットのシャードと手元）で、スキップされずにファイルごと落ちた
- **原因**: `describe.skipIf(!url)` でも、vitest はテストを集めるために describe の中身を流す。中身で `drizzle(client!)`（client は null）と `fs.mkdtempSync` を呼んでいた
- **解決策**: ほかの `*.db.test.ts` と同じく `(client ? drizzle(client) : null)!` にし、一時ディレクトリは `beforeAll` で作った
- **教訓**: 新しい `*.db.test.ts` は、コミットの前に `TEST_DATABASE_URL` なしでも1回流し、「skipped」になるのを確かめる。describe の中身では、接続や副作用のある処理を呼ばない（`beforeAll` に置く）

### [Test] 本物の auth client を購読するテストは、セッションの store を止めてから終える
- **日付**: 2026-10-25
- **状況**: #706。`bun run test:run --maxWorkers=2` で全部のテストが通ったのに、未処理の例外 `ReferenceError: window is not defined`（better-auth の `client/broadcast-channel.mjs`）1件で終了コードが1になった。本物の `lib/auth/client.ts` をスタブしたネットワークで動かす `sign-out-other-devices.test.tsx` と `password-change.test.tsx` で起きる。1ファイルだけ流すと出ない
- **原因**: better-auth のセッションの store（nanostores の atom）は、最後の購読が外れてから1秒後（nanostores の `STORE_UNMOUNT_DELAY`）に止まり、止まるときに `window` から自分のリスナーを外す。画面の unmount の後と、購読のないときの `sessionStore.get()` の後に、このタイマーが残る。CPU が混んでワーカーの終了が1秒より遅れると、jsdom が片付いた後にタイマーが動く
- **解決策**: `beforeAll` で空のリスナーを付けて store をファイルの間ずっと動かし（開いたままのタブと同じ）、`afterAll` で偽のタイマー（`setTimeout`・`clearTimeout`）の下でリスナーを外し、`vi.runOnlyPendingTimers()` で jsdom があるうちに止めた。nanostores の `cleanStores` は、nanostores が直接の依存でないので使わない
- **再現の仕方**: 組み込みの jsdom を包み、片付けの後に1.5秒待つ環境のファイルを作り、`--environment <そのファイルの絶対パス>` で、対象のファイルともう1つ時間のかかるファイルを `--maxWorkers=2` で流すと、毎回出る（ほかのファイルが流れている間は、終わりかけのワーカーの例外も拾われる）
- **教訓**: 本物の auth client（nanostores の store）を購読するテストを足すときは、同じ形で store を止める。`@/lib/auth/client` をモックするテストには要らない。全体の実行だけで出る未処理の例外は、報告されたファイルの片付けの後に残るタイマーを疑う

### [Harness] 専門エージェントの「読み取り専用」はフックで守る
- **日付**: 2026-10-24
- **状況**: 認証・セキュリティの PR はマージ前に読み取り専用のレビューを通す決定（`2026-10-19-security-review-gate`）があるのに、専門エージェントの tools に Bash があり、本文の指示だけに頼っていた。公式も「Bash を含む許可リストは厳密には読み取り専用でない」と言う
- **原因**: 「変更しない」を仕組みでなく文章で頼んでいた
- **解決策**: PreToolUse のガードが、入力の `agent_type` が `-specialist` のとき読み取り専用のルールを掛ける（#461）。書き込みは `/dev/null` だけ、依存の変更・インラインのスクリプト・外部への送信・書き込み系の MCP を止める
- **教訓**: 文字列の解析で作るガードは抜け道が多い。許可したコマンドのオプション（`sort -o`・`sed` の e/w・`git --upload-pack`・`vitest --outputFile`）、変数（`GIT_EXTERNAL_DIFF`・`NODE_OPTIONS`・`PATH`）、ループや条件のキーワードに付けたリダイレクト、`>&`・`<<<` まで見る。読み取り専用のレビューを2回通し、各抜け道を実際のフックの入口（`agent_type` を付けた入力）に流して塞いだ。意図した回避までは防げない前提で、既知の限界を決定に書く

### [Harness] ガードは壊れたときに止める（fail-closed）
- **日付**: 2026-10-24
- **状況**: 秘密情報を書く事故（violations.md 2026-10-18 CRITICAL）の再発防止がガードなのに、公式では異常終了やパスの間違いのポリシーのフックは全部を素通しにする

### [Harness] `pkill -f` は、それを実行したシェル自身にも、ほかのセッションのプロセスにも当たる
- **日付**: 2026-10-24
- **状況**: `pkill -f "next start"` を含むコマンドを実行したら、そのコマンドのシェルが止まり（終了コード 144）、サーバーは残った。同じ日、別の作業で開発サーバーを `pkill -f "next dev"` や `ps | grep | xargs kill` で止めた（violations.md 2026-10-24）
- **原因**: `pkill -f` はコマンドの行全体で探す。実行中のシェルの行にも同じ文字列が入っている。同じマシンではほかのセッションも `next dev` を動かしているので、名前で探すとそれにも当たる
- **解決策**: `ps` で PID を確かめて `kill <PID>` で止めた
- **教訓**: 止めたいプロセスは PID で指定する。起動したときに PID を控え、自分が起動したものだけを止める。名前で探して止める形（`pkill -f`・`ps | grep | xargs kill`）は使わない

### [Harness] Issue・PR の本文が、書き込みの途中で書き換わることがある
- **日付**: 2026-10-24
- **状況**: クラウドのセッションで、`gh api -X PATCH` で Issue・PR の本文を書き換えると、末尾に「Generated by Claude Code」の行が足された。書き込みのときに、`yusuke-kurosawa/DiagnoLeads-v1-legacy` へのリンクがバッククォートで囲まれ、リンクでなくなることもあった。GitHub MCP の `create_pull_request` で PR を作ったときも、本文の末尾の「🤖 Generated with Claude Code」とセッションの URL の行が、署名の1行に置き換わった（#582）
- **原因**: 未確認。リポジトリのフック（`.claude/`）とスクリプトには本文を書き換える処理がないので、セッションの環境の側で起きている
- **解決策**: Issue の本文は GitHub MCP の `issue_write` で書いた。#582 は `update_pull_request` で同じ本文を書き直すと、末尾がそのまま残った。どちらも、書いたあとに本文を読み直して確かめた
- **教訓**: Issue・PR の本文は `gh api` で書き換えない。どの方法で書いても、書いたあとに本文を読み直し、署名の行が足されていないこと・末尾の行とリンクが崩れていないことを確かめる。崩れていたら GitHub MCP の `issue_write`・`update_pull_request` で書き直す（コメントの末尾の署名は決まりで付けるもので、これとは別）

### [Test] 手元で診断を続けて送ると、回数制限に当たる
- **日付**: 2026-10-24
- **状況**: E2E の直後にスクリーンショット用のスクリプトで診断を送ったら、結果画面が出ずにタイムアウトした。時間を空けて流し直すと通った
- **原因**: `proxy.ts` の回数制限（`diagnostic` は1分に30回）に当たったとみられる。手元の送信は、すべて同じアドレスから来る

### [Test] 検査のためにコードの import を読むときは、ts.preProcessFile でなく構文木で読む
- **日付**: 2026-10-24
- **状況**: #468 で、`test/` の import を速く読むために `ts.preProcessFile` を使った。読み取り専用の反証で、正規表現の中のバッククォートや引用符で読み違えて本物の import を取りこぼし、テンプレート文字列の中の import を拾うこと、`'@/locales/' + locale` の頭の部分をパスとして拾うことが分かった。例外なしのルールなので、正しいテストでも CI が止まる

- **日付**: 2026-10-24

### [Git] main へ続けてマージすると、途中の CI が取り消される
- **日付**: 2026-10-24
- **状況**: #440・#463・#499・#485 を数分おきにマージした。main の push の CI は、#440・#463・#485 の run が cancelled になった。#499 の run と、#485 を含む後の run（#551 のマージ）だけが最後まで走った
- **原因**: CI の concurrency は main で1つにまとまる。走っている run の後ろに待てるのは1本だけで、新しい push が来ると、待っている run は取り消される（push の run は `cancel-in-progress` ではないので、走っている run は止まらない）
- **解決策**: マージした変更を含む、最新の完了した run が緑なのを確かめた（#499 の run は 4ee6537、#485 を含む run は 4db00b3）
- **教訓**: main で通ったかは、そのマージの run ではなく、そのマージを含む最新の完了した run で確かめる。取り消された run を、失敗と取り違えない

### [Git] main の arch:check が落ちたら、直す前にほかのセッションの動きを確かめる
- **日付**: 2026-10-25
- **状況**: #666 が `ax-boundary` を足した後に、その前の main で CI が緑だった #603 がマージされ、main の Lint & Type Check が落ちた。直す PR が3つのセッションでほぼ同時に動いた（#682・#683・#685）。#682 は push の前に取り下げた
- **原因**: ブランチ保護は strict:false なので、古い main の上で緑だった PR がそのままマージできる。#603 のマージは、ship §5（マージの直前に main を取り込んで arch:check を流す）が入った直後だった。main が落ちるとすべての PR が落ちるので、気づいたセッションが一斉に直しに来る
- **解決策**: 1行の許可リストの PR（#683）で main を先に戻した。import を消す本当の直し（#685）は後から入れ、`--update` で行を消す
- **教訓**: main が落ちたら、直す前に開いている PR（`fix`・`chore(ci)`）と、ほかのセッションの連絡を確かめる。直すと決めたら、着手する前に send_message で範囲を知らせる。arch:check に規則を足す PR は、マージの前に開いている PR を main と合わせて流し、落ちる PR の持ち主に知らせる（#549・#675 で行った手順）

### [API] Route Handler の GET は、HEAD の要求でも呼ばれる
- **日付**: 2026-10-25
- **状況**: #41 で QR の入口（`app/q/[code]/route.ts`、GET だけを定義）にスキャンの記録を足すとき、リンクの確認ツールなどの HEAD の要求も記録に入るかを確かめた
- **原因**: Next.js は、HEAD を定義していない Route Handler の HEAD を GET の関数で答える（`node_modules/next/dist/server/route-modules/app-route/helpers/auto-implement-methods.js`）。`req.method` は `HEAD` になる
- **解決策**: 記録の前に `req.method !== 'GET'` なら記録しないようにし、ユニットテストで HEAD を流して確かめた
- **教訓**: GET の Route Handler で書き込む（数える・記録する）ときは、HEAD でも同じ関数が動くことを前提にし、書き込みを `req.method` で分ける

### [Performance] 空だった表に書き込みを足すときは、その表の外部キーの索引を確かめる
- **日付**: 2026-10-25
- **状況**: #41（PR #704）で、それまで書き込むコードのなかった `qr_scans` に、公開の入口から行を足すようにした。読み取り専用のレビューで、`qr_scans.lead_id`（`ON DELETE SET NULL`）に索引がなく、行が増えるほど、どの組織のリードの削除も遅くなると指摘された
- **原因**: PostgreSQL は外部キーの参照先の行を消すたびに、参照する側の表を外部キーの列で探す（CASCADE・SET NULL のため）。参照する側の列には自動で索引が付かない。表が空のあいだは目に見えない
- **解決策**: 索引はスキーマの変更なので、#702 に `lead_id` と `(organization_id, campaign_id)` を足して、本番に適用してからマージする形にした。公開の入口からの水増しには、キャンペーンごとの1日の上限を入れた
- **教訓**: 使われていなかった表に書き込みを足すときは、その表のすべての外部キー（特に `ON DELETE` で参照先の削除から探されるもの）に索引があるかを `lib/db/schema.ts` で確かめる。公開の入口から増える表なら、日ごとの上限と保存期間も一緒に決める
